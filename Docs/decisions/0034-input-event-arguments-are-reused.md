# ADR-0034: The input event arguments are reused

- **Status**: Accepted
- **Date**: 2026-11-16
- **Source**: CasaEngine plan `ai-agent/tasks/mgui-nonalloc-suite-tasks.md`, decisions D13 to D15, taken by the author on 2026-11-16

## Context

The input of `MGUI.Shared/Input` creates a new event object for most physical events. Read in the code and measured on 2026-11-16:

- Mouse (`Mouse/MouseTracker.cs`, `Update`): a press (`BaseMousePressedEventArgs`), a release (`BaseMouseReleasedEventArgs`), a click (`BaseMouseClickedEventArgs`), a drag start (`BaseMouseDragStartEventArgs`) and a drag end (`BaseMouseDragEndEventArgs`) are created with `new` at each event, and a click sequence (`MouseClickSequence`, with its `MouseClickSequenceRoutingMetadata`) at the first click of a sequence. The wheel event (`BaseMouseScrolledEventArgs`) was created at each tick where the wheel moved.
- Keyboard (`Keyboard/KeyboardTracker.cs`, `Update` and `CreateTextInputOnlyPressedEvents`; `Keyboard/KeyboardHandler.cs`): a key press (`BaseKeyPressedEventArgs`) with its input stream (`KeyboardInputStream`), a release (`BaseKeyReleasedEventArgs`) and a click (`BaseKeyClickedEventArgs`) are created with `new` at each key, a press and a stream also for a text-input-only event, and a key repeat (`BaseKeyRepeatedEventArgs`) at each repeat of a handler (`KeyboardHandler.cs`, `GetCurrentKeyRepeatEvent`).
- `KeyboardTracker.IsShiftDown`, `IsControlDown` and `IsAltDown` went through `IsAnyPressed(params Keys[])`, which creates an array and a delegate (with its closure) at each read. `MGTextBox` had a private `IsControlDown(KeyboardTracker)` that avoided the property for this reason.
- The move event (`BaseMouseMovedEventArgs`, `MouseTracker.CurrentMoveEvent`) and the dragged events (`MouseTracker.CurrentDraggedEvents`, one per drag start condition and button) were already refilled and reused (ADR-0022). Neither has a handled state.
- Links between event objects exist: a release holds its press, a click holds its release, `BaseMouseClickedEventArgs.PreviousClickInSequence` holds the previous click, and `MouseClickSequence.FirstClick` and `LatestClick` hold clicks of the sequence; a key release holds its press, a key click its release, a key repeat its initial press. A reused object makes such a link point to a rewritten instance.
- Measured allocation of one event: 56 B for a wheel tick, 464 B for a mouse click (press, release, click, sequence and metadata), 696 B for a key (press, stream, release, click and the modifier reads).
- Who keeps an event after the handler returns: for the wheel event, nobody. The search of both repositories (MGUI and `CasaEngine`, `CasaEngine.Editor`, `CasaEngine.EditorServices`) found only handlers that read the event during the call: no field, property or collection of the type, no lambda that stores or captures it for later, no asynchronous use (the lambda of `MGOverlay` that sets the handled state runs inside the handler). The keepers of the mouse button events and of the key events are listed by the tasks that reuse them (first step of each), before any change.

## Decision

The input event arguments of `MGUI.Shared/Input` are reused. A handler that needs a value after the event is over copies the value.

- Validity of a reused object (written in this ADR and in the doc comment of each type):
  - wheel: during the tick (it is null on a tick without wheel movement, and its handled state is reset at each tick where the wheel moves);
  - press, release, click, drag start and drag end of a mouse button: until the next event of the same kind for the same button (a press stays valid while the button is held and during its release);
  - press, release and click of a key: likewise, per key.
- Two instances stay separate, so that nothing changes: the key repeat (one instance per handler and per key, with its own handled state), and the press created for a text-input-only event (its own instance and its own stream, distinct from those of the held press, so that the release and the click of the same frame keep their press, time and stream).
- At each reuse the handled state is reset and the identity restarts as the one of a new object:
  - a key stream receives a new id, its start time and its initial press, and its owner (`OwnerHandlerId`) is cleared;
  - a click sequence receives a new id, its button and its start time, and its adopted target (`ValidatedTargetId`, `ValidatedTargetHost`) is cleared;
  - a click sequence of a button is valid until the next sequence of that button.
- The members that would designate a rewritten instance are removed, with no alias: `BaseMouseClickedEventArgs.PreviousClickInSequence`, `MouseClickSequence.FirstClick` and `MouseClickSequence.LatestClick`. `ClickCount` and the sequence stay; a caller that needs a value of the previous click gets it as a value.
- `KeyboardTracker.IsAnyPressed(params Keys[])` stays public and unchanged. `IsShiftDown`, `IsControlDown` and `IsAltDown` no longer go through it: each is two `IsPressed` calls (left or right key).

Scope by task of the plan (this ADR records the whole decision, the code follows task by task):

- Implemented with this ADR (T5.1): the wheel event (`MouseTracker` refills one `BaseMouseScrolledEventArgs`, its handled state reset, its setters private) and the three modifier properties; the private workaround of `MGTextBox` is removed.
- Implemented by T5.2: the mouse button events. `MouseTracker` keeps one `BaseMousePressedEventArgs`, `BaseMouseReleasedEventArgs` and `BaseMouseClickedEventArgs` per button, one `BaseMouseDragStartEventArgs` and `BaseMouseDragEndEventArgs` per drag start condition and button, and one `MouseClickSequence` (with its routing metadata and its weak reference, re-armed by `SetTarget`) per button; each is created at its first use and refilled afterwards, with its handled state reset. A click that does not continue the sequence of its button restarts that sequence (new `Id`, button, start time, adopted target cleared); a click that continues it keeps it, with its adopted target. The multi click is detected on values kept per button (click count, release time, position of the previous click). The doc comment of each type carries its validity. `PreviousClickInSequence`, `FirstClick` and `LatestClick` are removed with no alias.
- Implemented by T5.3: the key events. `KeyboardTracker` keeps, per key, one `BaseKeyPressedEventArgs` with its `KeyboardInputStream`, one `BaseKeyReleasedEventArgs` and one `BaseKeyClickedEventArgs`, and, as separate instances, one press and one stream for the press that a native text input creates alone; each is created at its first use and refilled afterwards, with its handled state reset. At each new press of a key the stream restarts as a new object would (new `Id`, start time, initial press, owner cleared). Each `KeyboardHandler` keeps one `BaseKeyRepeatedEventArgs` per key that it has repeated, refilled at each repeat with its own handled state (a repeat marked handled by one handler is not handled for another). The release and click built in the frame of a native text input of the same key keep the held press, its time, its stream and its owner, because the text input press is another instance with another stream. The doc comment of each type and handler event carries its validity.
- Not implemented: the three `Alphanumeric` regular expressions of the key events are left as they are (a static `Regex` per type, no allocation per call, measured), and `IsAlphanumeric` has no caller in the two repositories.

## Consequences

- A handler that keeps an event object after its call (in a field, a list, a closure that runs later) sees it rewritten by the next event of its kind: it must copy the values it needs (`Position`, `ScrollWheelDelta`, `Button`, times, `ClickCount`, key, printable value). For the wheel event this concerns external code only; no code of the two repositories keeps it.
- The handled state of a reused wheel event is reset by the tracker at each tick where the wheel moves, so a handler that marked the previous tick's event handled does not hide the next tick from the other handlers. The events delivered, their values and the handled routing are the same as before; only the object identity changes.
- `CurrentScrollEvent` keeps its meaning: null on a tick without wheel movement.
- Public API: `BaseMouseScrolledEventArgs.ScrollWheelDelta` and `Position` now have a private setter (they were get-only; no change for callers). The removal of `PreviousClickInSequence`, `FirstClick` and `LatestClick` (T5.2) is a breaking change of the public API, accepted by the author (modern design over compatibility); external code that reads them must be updated, and any value of the previous click that a caller needs is exposed as a value. Also changed by T5.2, all breaking for an external caller and none used by the two repositories: the public constructor of `BaseMouseClickedEventArgs` loses its `PreviousClickInSequence` parameter; `MouseClickSequence.ClickCount` is now a stored value (it was `LatestClick?.ClickCount`); `MouseClickSequence.Id`, `Button` and `StartedAt` have a private setter (the sequence is restarted by the tracker); the properties of the press, release, click and drag start and end events that a refill rewrites have a private setter (they were get-only; no change for callers); and the public static `MouseTracker.GetMultiClickCount` reads the values of the previous click (`int PreviousClickCount, TimeSpan PreviousReleasedAt, Point PreviousPosition`, then the release, as before, and the two thresholds) instead of the previous click object, which the tracker refills for the new click: a previous click count of 0 or less means no previous click.
- Links between events: `BaseMouseReleasedEventArgs.PressedArgs`, `BaseMouseClickedEventArgs.ReleasedArgs`, `PressedArgs` and `Sequence`, and the `DragStartArgs` of the dragged and drag end events designate the instance of the same button (and condition), which is rewritten by the next event of its kind: a kept click whose button is released again without a click sees that later release through `ReleasedArgs`. `BaseMouseReleasedEventArgs.HeldDuration` is a value written at each refill, so it stays the duration of its own press.
- Keepers of a press: `MGButton`, `MGCheckBox`, `MGRadioButton` and `MGToggleButton` keep the press that began a click until the release (or the release outside). The check box, the radio button and the toggle button only test it for null, so a rewrite is invisible to them. The button also reads its handled state to repeat; it stays valid for the whole hold (a press is rewritten only by the next press of its button). Only if the release is never delivered to the button, which then keeps a stale press until its next press, can the kept reference designate a newer press of the same button; the repeat is gated by the button being pressed again, which is that newer press. `MGResizeGrip` and `MGTextBox` read the drag start and the press of the event they receive, and `MGTreeViewItem` keeps the identifier of a sequence, a value.
- The zero test of a wheel frame (`ScrollViewerWithTallContent_Update_WithTheMouseWheel_AllocatesNothing`), the zero test of the modifier reads and the tests of the identity, values and handled state of the wheel event cover this decision; the click frames of each button and the drag frames of each drag start condition allocate exactly 0 (`MouseButtonEventsReuseTests`), the grid click of phase 2 reads 0 (`GridWithASelection_Update_WithTheSelectionMovedByClicks_AllocatesNothing`), and `MouseButtonEventsReplayTests` replays a scripted session of 2397 lines, frozen on the code before the reuse, identically. The key frames (press, hold with repeats, release, click, with pressed, repeat, released and clicked subscribers on two handlers, for a printable key, a non printable key and two modifier combinations) and the native text input frames of a Latin character, with and without a key press, allocate exactly 0 (`KeyboardEventsReuseTests`); the text box that ignores the keys reads 0 (it read 312 B per key), and the typing test now reads the remainder alone (1,300,000 B over 500 frames, the text layout, T5.8). `KeyboardEventsReplayTests` replays a scripted session of 1038 lines, frozen on the code before the reuse, identically, and `KeyboardEventsReuseTests` pins the three delicate cases (the release in the frame of a native text input of the same key keeps the press time, the stream and its owner and reaches the same handlers; the owner of a stream does not survive into the next press of the key; the repeat of a key belongs to each handler).
- Keepers of a key event: none in the two repositories. `MGTextBox` keeps stream identifiers (`ShortcutOriginStreamIds`, a set of `long`), which are values: a new press of a key restarts its stream with a new id, as a new stream would have had. Every other handler reads the event it receives during the call.
- Public API changed by T5.3: the properties of the press, repeat, release and click events and of `KeyboardInputStream` that a refill rewrites have a private setter (they were get-only; no change for callers); `BaseKeyReleasedEventArgs.HeldDuration` is a value written at each refill (it was computed from the press, null safe now); `BaseKeyRepeatedEventArgs.HeldDuration` is the repeat time minus the press time of the repeat, which is the one of the initial press (same value). No member is removed and no signature changes. A native text input of a character below 256 reuses a cached string instead of making one (the value is the same).
- Left for later tasks: an independent verification of T5.1 to T5.3 (T5.4).
