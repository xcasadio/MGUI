# ADR-0037: The caret geometry of a text box reads the text layouts

- **Status**: Accepted
- **Date**: 2026-11-16
- **Source**: CasaEngine plan `ai-agent/tasks/mgui-nonalloc-suite-tasks.md`, decision D19 (open point O13), recommended by the agent and decided on 2026-11-16, task T5.8

## Context

`MGTextBox` shows its text in an internal `MGTextBlock`, and the caret, the selection and the clicks work on the geometry that `TextRenderInfo` builds from the lines of that block: one `LineRenderInfo` per line, one `CharRenderInfo` per character, with its position, its width, its index in the original text (`IndexInOriginalText`) and its index in the parsed text (`IndexInParsedText`). Read in the code and measured on 2026-11-16:

- `TextRenderInfo.UpdateLines` read `MGTextBlock.Lines`, the public `MGTextLine`s, and from each line its runs (the text of each run, its bold and italic flags), its width and height, and `MGTextLine.OriginalCharacterIndices`, a table that only `MGTextLine.ParseLines` fills: one index per character of the line, where the hyphen that wrapping inserts at the end of a piece of a word shares the index of the character that follows it, a line break takes one entry per character of the break (2 for `\r\n`), an empty line has one entry, and a line made of a single space that wrapping ignores is not in the lines but still takes its index.
- The internal layouts of the block (`PlainTextLayout` for a text without markup, `FormattedTextLayout` for a text with markup) lay the text out without objects, and their pieces pointed into their own character buffer, with no index in the text they were built from. So `MGTextBlock.Lines` was built again from the layout's source with the legacy parser each time it was read after a change of text (`new string(PlainLines.Source)`, the tokenizer, `ParseRuns`, `ParseLines`), and `TextRenderInfo` read it at each change of the text: about 1.6 KB of the 2.6 KB that a key allocated (`MGTextBox` is markup-enabled, with an escaped text, so its block takes the formatted layout).
- Two readers depended on the lines themselves: `MGTextCaret.MoveToApproximateScreenPosition` chose the left or the right edge of a character from `CharInfo.Line.Source` (the `MGTextLine` kept by the `LineRenderInfo`: null for the line of a text that has no line, and its runs: "all of them are empty texts" for an empty line, whose single character is a placeholder as wide as a default character); and a `MGRichTextBox` that has styled spans or a colouriser sets explicit runs on its block (`SetTextRuns`), so the block has no internal layout (`MGTextBlock.UpdateLines` takes its third branch and builds the `MGTextLine`s directly). A selection alone does not set explicit runs: it is written as markup tags in the text, like the selection of an `MGTextBox`, and the block keeps its formatted layout.
- No test checked the geometry of the caret.

## Decision

When the block of a text box has an internal layout, `TextRenderInfo` reads that layout, and `MGTextBlock.Lines` is not read nor built. When it has none (explicit runs), it reads `MGTextBlock.Lines` as before. `MGTextBlock.Lines` and every public member stay.

- The pieces of the layouts carry what the table needs. `PlainTextPiece` and `FormattedTextPiece` hold `OriginalStart`, the index in the text of the first character of the piece, and `HasSuffix`, the mark of the character that wrapping inserted at the end of the piece (the hyphen): it takes the index of the character that follows the piece, `OriginalStart` plus the length of the piece without it. `PlainTextLine` and `FormattedTextLine` hold `LineBreakCharacterCount` (0, or the number of characters of the break that ends the line) and `OriginalEnd`, the index that follows the characters of the line. The layouts count the index of the next character as `MGTextLine.ParseLines` does: each piece takes the characters it holds from the counter, the characters of a line that wrapping then ignores are counted too, and a line break takes its characters when its line ends.
- `AppendOriginalIndices(lineIndex, list)` of each layout rebuilds the table of a line, entry by entry as `OriginalCharacterIndices` has it: one index per character of the pieces (the suffix with the index of the next character), then the characters of the break when the line ends in one, or, for a line without a break and without a character, one index (`OriginalEnd`). The table is written into a list that `TextRenderInfo` keeps and clears for each line: nothing is allocated once it has grown.
- `MGTextBlock` gives `TextRenderInfo` access to the layouts that are the lines of the block (`KnownPlainLines`, `KnownFormattedLines`, internal; null when the lines are not those of a layout) and the start Y of a layout (`GetRenderedTextStartY` overloads, the same computation as for the lines). The layout read is the one `MGTextBlock.Lines` would be built from: `UpdateLines` of the block builds it, and the measure steps use scratch layouts.
- `TextRenderInfo.UpdateLines` has three readers of one shape, for a plain layout, a formatted layout and the public lines: the same positions, the same advances (the per-glyph advances reconciled with the whole-string measure), the same line and character counters. A piece of an image makes `UpdateLines` throw `NotImplementedException`, as a non text run of `MGTextLine` did. The text of a piece reaches the text engine as a span (`ITextMeasurementEngine.MeasureText(ResolvedFont, ReadOnlySpan<char>)`); the lines of the third reader still pass their string.
- What `MGTextCaret` reads instead of `LineRenderInfo.Source` and its runs: `LineRenderInfo` itself says it. `HasSource` is false only for the single line of a text that has no line (the old `Source == null`), and `HasOnlyEmptyText` is true when the line has no character of text, so that its single character is the placeholder (the old "all the runs are empty texts"; it is computed when the line is laid out, from the pieces, or from the runs for the public lines). `MoveToApproximateScreenPosition` takes the left edge when the point is in the left half of the character, when the line has no character, when `HasSource` is false or when `HasOnlyEmptyText` is true, and the right edge otherwise: the same rule. `LineRenderInfo.Source` (internal) is removed.
- Not changed: the public API (`MGTextLine`, `MGTextBlock.Lines`, `MGTextCaret`, the layouts and `TextRenderInfo` are internal or keep their signatures; new members are internal), the legacy code (`MGTextLine.ParseLines`, the tokenizer, `ForceLegacyTextPath`) which is the reference of the differential tests, the text box (`MGTextBox.cs` is not touched), the clicks and the selection (`TryGetCharAtScreenPosition` still orders with LINQ, once per click).

## Consequences

- Typing in a focused `MGTextBox` (A then Backspace, one key per frame), `Update` of 500 frames after 500 of warm-up, steady caret or default blink: 2600 B per frame before (1,300,000 B), 356 B per frame after (178,000 B). The new remainder is the results of the change of the text, named in `ControlFamilyZeroAllocationTests`: the geometry that the caret keeps (a `LineRenderInfo`, its list and the array of its characters, 200 B per change, 100,000 B, measured on its own: the rebuild of the geometry allocates exactly that and nothing else), the arguments of `TextChanged` (32 B per change, 16,000 B), the arguments of the layout bounds change of the text block (48 B per change, 24,000 B), the markup text that `FTTokenizer.EscapeMarkdown` builds for "a" (a `StringBuilder`, its chunk and its result, 128 B on the key A, 32,000 B, measured on its own) and the string "a" of the key (24 B on the key A, 6,000 B). The sum is the measured total. The draw stays at 0, the at-rest cases stay at 0.
- The frozen geometry. `TextBoxCaretGeometryTests` freezes, for 188 scenarios on two text engines (the fractional one of `FractionalTestTextEngine` and the default one of `GraphTestRuntime`, 376 texts), the position, the width, the original and parsed index of every character; the character and the caret position (line, original index, parsed index, bounds) of every point of a grid of screen positions that goes beyond the text on every side (left and right halves of characters, empty lines, lines of white space, margins); the lookups by original and parsed index and the moves of the caret by index and by arrows. The corpus: one line, several lines, `\r\n`, wrapping at four widths and a sweep of widths over texts with runs of spaces (lines that hold one space), a word longer than the line with its hyphens, hyphens and spaces in the text, empty lines, a trailing line break, escaped characters `[` and `\`, an empty text, a text of spaces, a tab, no wrapping, centre and right alignment, a selection (markup), `MGPasswordBox`, `MGRichTextBox` alone, with a selection (markup), with bold and italic styled spans, with styled spans and a selection, with a colouriser (explicit runs), and a text box whose block does not allow inline formatting (plain layout). The texts were captured on the code before this change, by running the class with `MGUI_CAPTURE_CARET_GEOMETRY` set to a folder (each text is written to a file there, and its line count and SHA-256 prefix to `frozen.txt`, pasted into `TextBoxCaretGeometryFrozen`); the plain layout scenarios were captured the same way with the two readers (`TextRenderInfo`, `MGTextCaret`) put back to their version before the change, which still compiles with the additive changes of the layouts. All 376 texts are identical after the change, and the draw journal of the text box is unchanged. The test also checks which scenarios have an internal layout and which have explicit runs, so the coverage cannot silently move.
- The table of original indices is checked against `OriginalCharacterIndices` of `MGTextLine.ParseLines` in `OriginalIndexTableTests`: line count and, line by line, every entry, with and without wrapping, ignoring or not the lines of one space, at twelve widths (including 0, fractions, 100000 and `double.MaxValue`) for the corpora and at four widths per text for the seeded draw (three drawn at random, and 100000). Plain layout: the 301 texts of the plain text tests (28,896 layouts, 220,872 lines), and 700 texts drawn from seed 20261116 (11,200 layouts, 111,066 lines). Formatted layout: the 1,890 texts of `FormattedTextCorpus` (fixed and 1,500 generated from its seed 20261115, with images, several runs, broken markup), 3,780 texts read by both pipelines in regular and bold (181,440 layouts, 632,207 lines). No difference.
- Mutations, checked then undone: adding one to the original index that follows a hyphen fails the table tests (the formatted one, and the two plain ones for the plain layout) and the frozen geometry (`textbox-wrap-long-word-60`, `plainblock-wrap-long-word-60`); making the caret always take the left edge fails the frozen geometry (`textbox-wrap-one-line-60`); ignoring `HasOnlyEmptyText` (the right half of an empty line takes the right edge) fails the frozen geometry (`textbox-wrap-empty-lines-60`).
- A rich text box with explicit runs keeps its cost: `MGTextBlock.Lines` is read at each change, with the legacy parser. Not part of this decision: its caret geometry through the layouts, which would need a layout of explicit runs.
- `FormattedTextLayout.Build` and `PlainTextLayout.Build` do a little more work per piece (one counter), which allocates nothing.
