# ADR-0027: A clip scope can be re-armed, so a backend pushes clips without allocating

- **Status**: Accepted; the class `ClipScope` it describes is replaced by the handle of ADR-0031, its goal (a rectangle clip without allocation) is kept
- **Date**: 2026-11-15
- **Source**: this chantier: the allocation-free desktop frame (decision D7 and task T3.1 of the CasaEngine plan `ai-agent/tasks/mgui-desktop-frame-nonalloc-tasks.md`, answered by the author on 2026-11-15)

## Context

`DrawTransaction.PushRectangleClip` and `PushClipTemporary` returned a new `ClipScope` for every push: a sealed class built from a `ClipResolveResult` and an `Action`, the action being a closure over the state to restore (previous scissor rectangle, previous scissor state). Each push also created a `ClipDefinition` (a sealed record class), and turning the scissor test on or off created a `DrawSettings` (a record class) through `with`. Measured on a real GPU, 500 push and dispose pairs on `DrawTransaction` after warm-up allocated 136000 bytes for a rectangle with bounds, 328000 for `PushRectangleClip(null, ...)`, 88000 for `PushClipTemporary` with a kept rectangle definition and 32000 for `PushClipTemporary` with a kept `None` definition.

`ClipScope`, `ClipDefinition` and `ClipResolveResult` are public in `MGUI.Shared`, and other backends build their scopes with `new ClipScope(resolution, action)` (the engine's `CasaDrawTransaction` and its clip executors, and the test doubles). A `ClipDefinition` holds the bounds, so a scope cannot report the rectangle it was pushed with without one, and the record has no way to be modified.

## Decision

- `ClipScope` gains three public members and nothing else changes in the public API: `ClipScope(Action disposeAction)` creates a scope that is not armed (it holds no clip and its first `Dispose` does nothing); `Reset(ClipResolveResult)` arms a disposed scope with a new `Resolution`; `ResetRectangle(Rectangle bounds, bool intersectWithCurrentClip)` arms it with the resolution of a rectangle clip, and `Resolution` then builds the `ClipDefinition` and the `ClipResolveResult` the first time it is read, not at the push. `ClipDefinition` and `ClipResolveResult` do not change.
- The constructor `ClipScope(ClipResolveResult, Action)` and `Dispose()` keep their signature and behaviour. A scope is armed from its creation by that constructor; `Dispose` runs the action on the first call after each arming and does nothing on the others.
- `Reset` and `ResetRectangle` throw `InvalidOperationException` when the scope is armed, that is, when it was not disposed since it was created or last armed. Re-arming is the owner's job; the code that received the scope only disposes it.
- `DrawTransaction` keeps its scissor scopes in slots: a slot holds the scope, the restore state (previous scissor rectangle, previous scissor state, whether the clip changed anything) in fields, and the scope's action is the slot's own method, created once with the slot. A slot is taken from a free stack when a clip is pushed and goes back to it when its scope is disposed. Nested clips therefore use one slot per level, as a stack by depth would, and a scope disposed out of order is still never handed out while it is armed. `ClipManager` does the same for the scopes of the `None` strategy.
- `PushRectangleClip` with bounds reaches the scissor through an internal `ClipManager.PushRectangle` that counts the clip in the diagnostics like `Push(ClipDefinition)` and arms the scope with `ResetRectangle`. `PushRectangleClip(null, ...)` arms it with a `None` resolution kept in a static field.
- `DrawTransaction.SetClipTarget` and the scissor restore take their `DrawSettings` through a helper that remembers the last pair of settings that differ only by their rasterizer type: turning the scissor test off and back on finds the same two objects. Settings equal to the ones the old code created are used, so the observable state does not change.

## Consequences

- A backend can keep one scope per nesting level and arm it again at each push: no scope, no closure and no definition is allocated per push. After warm-up, 500 push and dispose pairs on `DrawTransaction` allocate 0 bytes for `PushRectangleClip` with bounds and with `null`, and for `PushClipTemporary` with a rectangle definition and with the `None` strategy, as does a nested sequence of four levels (`MGUI.Tests/Integration/ClipScopeReuseGpuTests.cs`, real GPU, which fail on the code before this ADR with the bytes above). The scissor rectangle and the rasterizer state after every push and every dispose of nested sequences are frozen from the code before this ADR in the same file.
- A reference to a scope that was disposed and armed again designates the new clip: disposing it a second time after the re-arm disposes the new clip. The caller of a push owns the scope until it disposes it and drops its reference then. A scope that is disposed twice without being armed in between is unaffected: the second `Dispose` does nothing.
- `ClipScope.Resolution` is not thread-safe once it builds its value lazily. Clips were already pushed and disposed from the UI thread only.
- A scope armed by `ResetRectangle` reports a `Resolution` equal, by value, to the one the strategy resolver gives for `ClipDefinition.Rectangle(bounds, intersectWithCurrentClip)`; it is not the same object as the one `ResolveClip` returns.
- Not done here: the stencil clip still creates a scope, two closures and a copy of its `ClipResolveResult` per push (1112 bytes per pair measured), and `SetDrawSettingsTemporary` and `SetTransformTemporary` still create a `TemporaryChange` (112 and 304 bytes per pair measured; `MGUI.Tests/Integration/ClipScopeRemainingAllocationMeasurements.cs`). With the capabilities `DrawTransaction` uses, the strategy resolver always prefers the stencil to the mask, so the mask clip is never reached through it. A backend other than `DrawTransaction` benefits only once it keeps its own scopes and arms them with `Reset` or `ResetRectangle`.
