# ADR-0038: A polygon is triangulated by a public triangulator that keeps its buffers, with the same algorithm as MonoGame.Extended

- **Status**: Accepted
- **Date**: 2026-11-17
- **Source**: CasaEngine plan `ai-agent/tasks/mgui-polygon-triangulation-tasks.md`, points P1, P2 and P5 (approved with the plan on 2026-11-17) and decision D2 (convex fast path under proof of identity), task T1.1

## Context

`PrimitiveDrawing.DrawSolidPolygon` of MonoGame.Extended 6.1.1, which `FillPolygon` of both backends calls, allocates at each polygon (read in the decompiled DLL with `ilspycmd`, measured on a real GPU: 376 bytes for a triangle, 928 to 992 for seven or eight vertices). The allocation is in `Triangulator.Triangulate`: a `LinkedListNode` per vertex in static lists, a reversed copy of a clockwise polygon, an `int[]` of indices. Measured by `PolygonTriangulatorTests` on 2026-11-17, bytes per call of `Triangulator.Triangulate` (500 calls after 500 of warm-up): triangle 376 (424 clockwise), arrow of 7 vertices 928 (952), concave of 8 vertices 992 (1080), ellipse of 32 segments 3968 (4248).

What decides the result of `Triangulator.Triangulate(vertices, WindingOrder.CounterClockwise, ...)`, read in `Triangulator`, `Triangle`, `Vertex`, `CyclicalList<T>` and `IndexableCyclicalLinkedList<T>`:

- `DetermineWindingOrder` sums `(v.X - previous.X) * (v.Y + previous.Y)` in `float`, starting with the last vertex as previous; the polygon is clockwise only when the sum is greater than 0 (a NaN sum or a null sum is counter-clockwise). A clockwise polygon is copied with its first vertex kept and the others reversed (`output[i] = input[length - i]`); the indices refer to that copy.
- The polygon list is a cyclic linked list in the order of the polygon, indexed from its first node; `IndexOf` finds a vertex by `Vertex.Equals`, which compares the position and the index. The indices of one polygon are all different, so an equal vertex is the same vertex (a vertex with a NaN coordinate is never equal to itself: the original cannot find it again, and this triangulator does not support it). `list[i - 1]` and `list[i + 1]` are the neighbours in the ring, wrapped; `RemoveAt(i)` removes the node at the index; the remaining vertices keep their order, so the first three of the list at the end are the three of lowest index.
- `FindConvexAndReflexVertices` classifies every vertex of the full ring before any ear is searched: convex when the dot product of the normalised incoming direction and the left normal of the normalised outgoing direction is less than or equal to 0, reflex otherwise, so two coincident consecutive vertices (a zero direction normalises to NaN) give reflex vertices. `FindEarVertices` then scans the convex list in the order of the polygon and `AddLast`s every convex vertex that `IsEar` accepts.
- `IsEar(c)` is true when no reflex vertex, other than the previous, `c` and the next ones, is in the triangle (previous, c, next) according to `Triangle.ContainsPoint`: a parity of three segment crossings (`checkPointToSegment`), whose result does not depend on the order in which the reflex vertices are visited. A reflex vertex at the same position as one of the three but with another index is tested like any other.
- `ClipNextEar` takes the first ear (`earVertices[0]`), makes the triangle (ear, next, previous), removes the ear from the ear list and from the ring, then validates the previous and then the next vertex. `ValidateAdjacentVertex(v)` moves a reflex vertex that has become convex from the reflex list to the end of the convex list (a convex vertex is never tested for convexity again, and a clipped vertex stays in the convex list), then, for a convex vertex, removes it from the ear list if it was an ear and no longer is one, or `AddFirst`s it if it was not an ear and now is one. So the ear list is ordered: the next vertex first when it is a new ear, then the previous one when it is a new ear, then the older ears.
- The loop runs `while (ring count > 3 && ear count > 0)`, then adds the triangle of the first three vertices of the ring if exactly three are left. A polygon with no ear, or one that runs out of ears, stops there: only the triangles clipped so far are returned (partial fill, possibly none).

## Decision

- **P1. The same algorithm.** `PolygonTriangulator` ports `Triangulator.Triangulate`, not another algorithm: the same winding sum, the same reversal, the same classification, the same ear test with the same `float` expressions (`Vector2.Normalize`, `Vector2.Dot`, the crossing test written as in `Triangle.checkPointToSegment`), the same ear order, the same stop. Its result is the same ordered vertices and the same indices, entry for entry, bit for bit, for any polygon, degenerate ones included: the triangles that a backend sends to the batch are the ones it sends today. The container operations are replaced by arrays indexed by vertex: a previous and a next array for the ring, a doubly linked list for the ears (`AddFirst`, `AddLast`, `Remove`, first), a kind per vertex for the convex and reflex lists. The order of the reflex list and of the convex list is not observable (the reflex list is only searched for any vertex in a triangle; the convex list is only scanned once, in the order of the polygon, which is the index order), so the convex list is a flag per vertex and the reflex list keeps its entries in an array only to iterate them.
- **P2. A public sealed class, an instance per user.** `MGUI.Shared.Rendering.PolygonTriangulator` is a public sealed class in `MGUI.Shared` (referenced by `MGUI.MonoGame.Integration` and by `CasaEngine`), with no static state: each transaction of MGUI and each renderer of the engine owns one. An instance serves one thread at a time. It uses only `Vector2` and integers, so `MGUI.Shared` still names no `GraphicsDevice`, `PrimitiveBatch` or other backend type (`Phase4RenderingArchitectureTests`).
- **Result access.** `int Triangulate(Vector2[])` and `int Triangulate(IReadOnlyList<Vector2>)` (read through the indexer, no enumerator) return the triangle count; `TriangleCount`, `ReadOnlySpan<Vector2> Vertices` and `ReadOnlySpan<int> Indices` read the result in place. **Validity**: the vertices and indices are valid until the next call to `Triangulate` on the same instance, which overwrites them and may replace the buffers; a span must not be kept across that call. The vertices are always a copy (the array or list of the caller is neither modified nor kept). Fewer than three vertices give no triangle and the vertices as given; a null argument throws `ArgumentNullException`, an empty one `ArgumentException` (the original throws `IndexOutOfRangeException` or `NullReferenceException`: a caller that must keep that behaviour guards before calling).
- **P5. Buffers grow, never shrink.** The buffers hold the biggest polygon seen so far; a call allocates only when its polygon is bigger than every previous one, and never after warm-up on the same polygons. No ceiling.
- **D2. Convex fast path, under proof.** When the classification finds no reflex vertex, `IsEar` is true for every vertex, now and after every clip, and the original clips the vertices 0, 1, 2, ... in turn, each with the last vertex as previous and the next vertex as next, then adds the three left: the fan (k, k + 1, last) for k = 0 .. count - 3. The triangulator returns that fan directly. The condition is the classification of the original itself, so a polygon with aligned vertices that the float test calls convex takes the path and one that it calls reflex does not, and coincident consecutive vertices (NaN, reflex) never take it. `PolygonTriangulatorTests` runs the whole corpus with and without the path and compares both to `Triangulator.Triangulate`: identical.

## Consequences

- Why the same algorithm and not a faster one: the triangles of a polygon are what the pixels of a fill depend on, including for a self-intersecting polygon or one with no ear, where the original fills only a part. Another algorithm would be proven only by pixels and could fill such a polygon differently.
- Proof, in `MGUI.Tests/Rendering/PolygonTriangulatorTests.cs`: 72,921 polygons, each compared four ways (array and list, one triangulator kept for the whole corpus and one per polygon), with and without the fast path, with no difference, vertices compared bit for bit. The corpus: triangle and rectangle in both windings, the arrows of `UISymbolDrawing` (four directions, twelve rectangles), the shapes of `MGRatingControl` (`ShapeVertices256`, eight item sizes), `MGVectorShapeHelper.CreateEllipseVertices` (32 segments in seven sizes and five strokes, other counts of segments in some), concave shapes, aligned vertices, coincident consecutive vertices, bow-ties and stars made of one stroke, every polygon of 3, 4 and 5 vertices on a 3x3 grid (66,339), and 5,900 polygons drawn from seed 20261117 (any points, whole coordinates on a small grid, star-shaped, convex). 12,180 of them are polygons that the original fills only in part, 2,626 with no triangle at all.
- `Triangulator` keeps its working lists in static fields: every test that calls it, directly or through `DrawSolidPolygon`, runs in the non-parallel `GpuDeviceCollection` of `MGUI.Tests`.
- Zero: 0 bytes over 500 calls after 500 of warm-up, for a triangle, an arrow, a concave shape and an ellipse of 32 segments, in both windings, from an array and from a list. The original allocates 376 to 4248 bytes per call on the same polygons.
- Mutations, checked then undone: taking the last ear instead of the first, not reversing a clockwise polygon, and starting the fan from another vertex each fail the differential.
- The fast path costs one pass less and no ear list for a convex polygon (the common case of the polygons that MGUI fills: arrows, ellipses, diamonds, rectangles); a concave polygon pays the general ear clipping, in O(vertices x reflex vertices) instead of the original's list scans.
- `ConvexFastPathEnabled` and `UsedConvexFastPath` are internal seams for the tests (`InternalsVisibleTo("MGUI.Tests")`), not API.
- Not supported: a NaN coordinate (see Context). Not part of this decision: wiring the backends (`DrawTransaction`, `CasaLegacyShapeRenderer2D`), the outline of a polygon (`StrokePolygon`) and the clip geometry (`CreateTriangulatedClipGeometry`), which still call `Triangulator`.
