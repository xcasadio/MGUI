# ADR-0008: Animation V3: editor readiness, remaining pilot limits and ad hoc migrations

- **Status**: Proposed (2026-09-13, waiting for the author's answers to the ten questions of `Docs/Tasks/animation-v3-tasks.md`)
- **Date**: 2026-09-13
- **Source**: this chantier: read-only audit of the V3 scope deferred by ADR-0007 ("Deferred (V3 or later)") and of the two V2 limits recorded in its "Decisions taken during delivery", against HEAD `e52880c`; program plan `Docs/Tasks/animation-v3-tasks.md`

## Context

Facts verified at HEAD `e52880c` (read-only audit by three independent readers, V1 and V2 delivered by ADR-0006 and ADR-0007):

- Easings are resolved by name only: `UIEasing` (`MGUI.Core/UI/Animation/Easing/UIEasing.cs`) keeps nineteen `DelegateEasing` instances in a case-insensitive registry, `TryGet(name)` is a plain dictionary lookup (`:99`), `Register(name, function)` is the extensibility point (`:83`). The four consumers (XAML `Transition.Easing`, `MGThemeAnimationSettings.*Easing` strings, keyframe JSON `Easing`, fluent `Ease(string)`) all go through `TryGet`; no Bezier code exists under `Animation/`.
- Composition and keyframes are independent: `UIAnimationGroup` (`Composition/UIAnimationGroup.cs`) writes no property (`IsStoreBacked` false, `BaseValueBoxed` null, synthetic `TargetKey`) and only decides when to start its children, each ticked by the manager through its own delta-based `Advance`; `UIKeyFrameAnimation<T>` drives one path; `UIKeyFrameSerializer` serialises one `UIKeyFrameTrack<T>` per document (`UIKeyFrameTrackDto { Version, ValueType, Frames }`, no path, no shared duration). `MGUI.Samples/Features/AnimationDemo.xaml.cs` already hand-builds the storyboard-of-keyframes shape a timeline editor emits.
- No seek: `UIAnimation.Advance(TimeSpan delta)` is `internal` and incremental (`Elapsed += delta`), early-returns unless `Running` or `Delayed` (`UIAnimation.cs:215-220`); `InternalsVisibleTo` covers `MGUI.Tests` and `CasaEngine.Tests` only (`MGUI.Core/Properties/AssemblyInfo.cs:6-7`). A headless replay from zero through `IUIDesktopRuntime.ApplyFrame` reaches a time forward only, re-fires every event and re-lays out at every frame for a layout pilot.
- Applicability of a target is a runtime exception: `ForegroundTarget.Require` (`Targets/UIColorAnimationTargets.cs:142-144`) and `ProgressButtonValueTarget.Require` (`Targets/UIBuiltInAnimationTargets.cs:178`) cast and throw; `UIAnimationTargets` exposes `Paths` and `GetValueType` but no owner type; `IUIAnimationTarget<T>` has `Path` and `IsStoreBacked` only.
- Store-backed targets read the physical value: the four colour targets' `GetUnderlyingValue` forward to `GetValue` (`UIColorAnimationTargets.cs:94, 122, 157, 195`), so while an `Animation` (100) contribution runs, `UITransition<T>.HandleChanged` (`UITransition.cs:170-177`) sees the in-flight value and a `LocalValue` (90) write recorded meanwhile stays invisible until the run ends. `UIResolvedPropertyStore.TryGetWinner<T>` (`Styling/UIResolvedPropertyStore.cs:232`) returns the first precedence-sorted contribution; there is no "winner excluding a kind" query. Two workarounds exist: `UIVisualStateApplier<T>.CaptureBase` reads the attached transition's `SettledValue` (`States/UIVisualState.cs:200-206`), and `UIStoreBackedTargets.Restore` parks the base under the container's source while only `Animation` remains (`IUIStoreBackedAnimationTarget.cs:74-78`).
- Precedence (`Styling/UIValuePrecedence.cs:11-15`): `Template` 60, `VisualState` 70, `LocalBinding` 80, `LocalValue` 90, `Animation` 100; a state setter on a pilot is written at 70 (`UIVisualState.cs:187`) and a local value shadows it, locked by `VisualStatesTests.ALocalValue_ShadowsANamedStateOnAPilot`.
- `PrimaryVisualState` has four members (`VisualState.cs:17-27`); `MGElement.ResolvePrimaryVisualState` (`:2898-2916`) knows no `Checked`; `UIValueSlot` and `UIResolvedPropertyStore.SlotCount = 6` mirror the four sub-fields; only `MGToggleButton.IsChecked` writes `IsSelected` (`MGToggleButton.cs:93`), and its `CheckedBackgroundBrush` / `CheckedTextForeground` are documented aliases of the `Selected` slots (`:46-70`); `MGCheckBox` and `MGRadioButton` draw their checked look through child elements and never touch `IsSelected`. The V2 named state `Checked` (`UIVisualStateNames.Checked`, `IUICheckable`) already gives any element an animatable, store-integrated checked look.
- Hot style refresh is setter-only: `ElementStyleScope` (`XAML/ElementStyleScope.cs:9-44`) keeps neither the element's own `Transitions` / `VisualStates` nor the styles' animation lists; `ElementStyleRefresher.RefreshElement` (`:176-288`) collects `Setter` objects only; transitions and states are transferred once in `Element.ApplyBaseSettings` (`Element.cs:619-645`); `UITransition` and `UIVisualState` carry no provenance; `MGResources.OnStyleAdded` / `OnStyleRemoved` have no subscriber (pull model, `element.RefreshStyles()`).
- Ad hoc time consumers: `MGTextBlock.UpdateSelf` ramps `TextProgress` with `FrameElapsed * TextCharactersPerSecond / NumCharacters` (`MGTextBlock.cs:1398-1404`), reset only by the constructor and the `TextCharactersPerSecond` setter (`:711`, `:1237`), not on a `Text` change; `MGHighlightBorderBrush.Update` adds `UA.FrameElapsed / CycleDuration` (`Brushes/Border Brushes/MGHighlightBorderBrush.cs:504`) and is a shared, deduplicated paint-time brush, not an element; `MGTimer` (`:272-273` Flicker on `Opacity`, `:332` countdown with its own `TimeScale`, `:339-341` Shake), `MGStopWatch` (`:237`), the tooltip hover delay (`MGElement.cs:3727-3746`, wall clock), `MGTextCaret` blink (`Text/MGTextCaret.cs:370-371`, wall clock) and `MGButton.IsRepeatButton` (`MGButton.cs:318-345`) are timers. `MGProgressBar`, `MGScrollViewer`, `MGSpoiler`, the docking auto-hide drawer and the graph zoom consume no time.
- Tooling: `UIToolingService.CaptureElementDebugView` reports the element's animations, transitions and named state (read-only, current frame); `MGDesktop.Animations` exposes `Clock`, `ActiveCount`, `ActiveAnimations`.

## Decision

Proposed program (each point is a task of `Docs/Tasks/animation-v3-tasks.md`, open questions there):

1. Bezier easings: `UICubicBezierEasing(x1, y1, x2, y2)` (CSS `cubic-bezier` semantics, Newton iterations with a bisection fallback, `X1` / `X2` clamped to [0,1], `Y1` / `Y2` free like `BackOut`), parsed from `cubic-bezier(x1,y1,x2,y2)` by `UIEasing.TryGet` when the name lookup misses, cached in the registry under its literal. No DTO changes: XAML, theme, keyframe JSON and the fluent API accept it at once.
2. Applicability metadata: `IUIAnimationTarget<T>.RequiredOwnerType` (default interface member, null = any element) filled by the targets that cast today, and `UIAnimationTargets.GetOwnerType(path)`, so an editor lists the paths a selected element accepts without trial and error.
3. Store: `UIResolvedPropertyStore.TryGetWinnerExcluding<T>(property, slot, kind)`, exposed to the store-backed targets as `TryGetValueBelowAnimation`, used by `UITransition<T>.HandleChanged` for store-backed targets only, so a write made under a running transition retargets it at once; the two workarounds (`CaptureBase`, the `{Animation}` branch of `UIStoreBackedTargets.Restore`) are then simplified. `UIPropertyAnimation<T>.ReadCurrentValue` keeps reading the animated value (an explicit animation starts from the current value, ADR-0006).
4. Local value versus state: `UIVisualState.OverridesLocalValue` (default false), written at a new `UIValuePrecedence.VisualStateOverride = 95` with `Kind` still `VisualState`, exposed in XAML on `VisualStateDefinition`; the global order of ADR-0005 is untouched.
5. `Checked`: no new `PrimaryVisualState` member and no new store slot (the V2 named state already covers the general case); `VisualStateBrush<T>.CheckedValue` (fill and colour brushes only), `MGToggleButton.CheckedBackgroundBrush` / `CheckedTextForeground` backed by it with the `Selected` slot as fallback so existing themes and XAML keep their look; `MGCheckBox` and `MGRadioButton` unchanged; `IUICheckable` stays the source of truth.
6. Keyframe clip: `UIKeyFrameClipDto { Version, Duration, Tracks[] { Property, ValueType, Frames[] } }` and `UIKeyFrameClipSerializer` building a `UIStoryboard` of `UIKeyFrameAnimation<T>` for one element (shared duration authoritative, `Format` / `Parse` of `UIKeyFrameSerializer` shared). Time remap of a composite's progress is explicitly out of scope.
7. Seek: public `UIAnimation.Seek(TimeSpan elapsed)` factoring the progress and iteration maths of `Advance`, one `ApplyProgress`, no `Started` / `Repeated` / `Completed` event, forward and backward, allowed on a composite (positions every child); reserved to preview instances driven by the host, never to an animation registered with a live manager (design pass on the `Completed` state before implementation).
8. Storyboard serialisation: `UIAnimationNodeDto` tree (`Kind`, `Path`, `Duration`, `Delay`, `Repeat`, `AutoReverse`, `FillBehavior`, `From`, `To`, `Easing`, `Track`, `Children`) and `UIAnimationSerializer.Serialize(animation)` / `Deserialize(json, Func<string, MGElement> resolveElement)` next to the keyframe serialiser, same versioning and the same closed set of value types (an application target needs a registered `Format` / `Parse` pair).
9. Hot refresh of style transitions and states: provenance on `UITransition` and `UIVisualState` (the style kind that produced them), `ElementStyleScope.OwnTransitionPaths` / `OwnVisualStateNames`, a refresh pass mirroring the setter pass (implicit then named styles), replacing or removing only style-owned entries, counters on `UIStyleRefreshResult`; last task of the program.
10. Migrations: `MGTextBlock.TextProgress` on the engine (`TextBlock.TextProgress` target, `SyncTextProgressAnimation` from the `Text` and `TextCharactersPerSecond` setters, characters per second kept as the public contract, progress reset on a `Text` change) and `MGHighlightBorderBrush` on the desktop clock through `UpdateBaseArgs.AnimationDeltaTime` (scaled delta set by `MGDesktop.Update` after the animations tick); `MGTimer`, `MGStopWatch`, the tooltip delay, the caret blink and the repeat button keep their own time source (ADR-0006 decision 7).

Out of scope (the author's game engine): the timeline widgets, the scrubber, the curve editing UI, undo / redo, project files, element lookup by name.

## Consequences

- The engine becomes tool-ready without hosting any tool: paths per element type, a seek that fires nothing, a clip and a storyboard format, Bezier curves as text.
- A transition on a pilot reacts to a write made during its run; the "seen at the run's end" limit of V1 disappears for transitions.
- A state can be declared to win over a local value on the elements where that is the intended look; nothing changes by default.
- `Checked` keeps its V2 shape (named state); the built-in toggle stops overloading `Selected` for two meanings without touching the enums or the store layout.
- The typewriter reveal and the highlight brush follow `MGDesktop.Animations.Clock` (pause, time scale): a behaviour change to announce.
- Accepted costs: one registry entry per distinct Bezier literal; one `Type` per target; a linear scan of at most eleven contributions per transition notification on a pilot; provenance fields on transitions and states.
- Deferred again: time remap of composites, CSS named Bezier presets, `MGTimer` effects on the engine, a predicate-based applicability.

## Decisions taken during delivery

- Bezier (U1, 13 September 2026): the registry key for a resolved literal is the caller's text after `Trim()` only, never its canonical form — `cubic-bezier(0.42,0,1,1)` and `cubic-bezier(0.42, 0, 1, 1)` cache as two distinct entries with equal curves, so `Names` can grow one entry per distinct spelling an application or an editor ever passed, not one per distinct curve; this was already the plan's stated trade-off (decision 1's "one registry entry per distinct Bezier literal"), made concrete here as a `Trim`-only key. `UICubicBezierEasing.Parse` throws `FormatException` (not `ArgumentException`) to match the vocabulary of a text-to-value conversion failure, distinct from the constructor's `ArgumentOutOfRangeException` on an out-of-range or non-finite control point. `EasingTests.Names_ListsTheNineteenBuiltIns` needed no rewrite: it already asserted a subset (`BuiltInNames.All(UIEasing.Names.Contains)`), so it tolerates the registry growing with resolved literals without becoming order- or count-dependent under parallel test classes. Fix round 1 (13 September 2026): `TryParse` validated only `x1`/`x2` before constructing, so a non-finite `y1`/`y2` (`NaN`, `Infinity`, or an overflowing exponent such as `1e40`) reached the constructor's `RequireFinite` and threw `ArgumentOutOfRangeException`, breaking `TryParse`/`TryGet`'s documented never-throws contract and turning `Parse`'s `FormatException` into the wrong exception type. `TryParse` now also rejects a non-finite `y1`/`y2` before constructing, alongside the existing `x1`/`x2` unit-interval check.
- Applicability (U2, 13 September 2026): the registry entry became a private `Entry(Target, ValueType, OwnerType)` record built once at `Register<T>` (which knows `typeof(T)` and reads `target.RequiredOwnerType`), replacing `GetValueType`'s per-call reflection over the target's interfaces with a stored field; `GetOwnerType` and the new `IsApplicable` follow the same null-safe, case-insensitive, non-throwing contract as `GetValueType`. Only two targets declare a non-null `RequiredOwnerType`: `ForegroundTarget` (`MGTextBlock`) and `ProgressButtonValueTarget` (`MGProgressButton`), the two whose `Require` helper casts and throws. `BorderBrushTarget` was read closely per the brief's instruction and disposed as `null`: its `RequireBorder` calls `element.GetBorder()`, a virtual facade that `MGButton`, `MGWindow`, `MGListBox`, `MGComboBox` and most bordered controls override to return their own internal `MGBorder`, and that `MGBorder` itself overrides to return `this` — not a strict cast to `MGBorder`, so any element exposing a border accepts the path; declaring `MGBorder` here would have been a bug (it would exclude every one of those controls, which is exactly what the path is for). `UIElementDebugView.ApplicablePaths` is an `init` property added to the existing positional record, not a new positional parameter: no test in `MGUI.Tests` constructs the record positionally, and an `init` property keeps every existing call site untouched.
- Value below the animation (U3, 13 September 2026): `MGElement.TryGetResolvedPilotValue<T>` was refactored into one private core (`TryGetResolvedPilotValueCore<T>(property, slot, UIValueSourceKind? excluded, out UIResolvedValue<T>)`) shared with the new `TryGetResolvedPilotValueExcluding<T>` (`excluded` set, returns the plain `T` rather than `UIResolvedValue<T>` since that is exactly what a `TryGetValueBelowAnimation` implementation needs), so the two paths — and their Background/DefaultTextForeground dormancy branches — cannot diverge; a small private relay (`TryGetStoreWinner<T>`) picks `TryGetWinner` vs `TryGetWinnerExcluding` on the store, avoiding a conditional `out var` the compiler's definite-assignment analysis cannot follow through a short-circuited `&&`. `MGTextBlock.cs` (out of this slice's perimeter) was deliberately left untouched: its `TryGetResolvedPilotValue` override adds an Inherited/Theme fallback chain for the `Foreground` pilot that `TryGetResolvedPilotValueExcluding` does not reproduce, so `ForegroundTarget.TryGetValueBelowAnimation` reads the plain store winner below `Animation` for the `Normal` slot, exactly like `MGElement`'s own (non-overridden) `TryGetResolvedPilotValue` would for that pilot — the Inherited/Theme fallback only exists on the overridden path, so this is not a behaviour gap, just an intentionally unreplicated override.
- Value below the animation (U3, continued): `UITransition<T>.HandleChanged` reads the value a running transition must settle to via `TryGetValueBelowAnimation` (falling back to `GetUnderlyingValue`) **only** while the transition's own run is active (`ownRunActive`); a foreign explicit animation holding the same path (`foreignAnimationOwnsPath`, the pre-existing "stay quiet, but follow its values" branch) keeps reading the physical value instead — that branch exists specifically to track the *other* animation's value so the next transition starts where it left off, and reading below it would defeat that purpose while leaving `ExplicitAnimation_StartedWhileATransitionRuns_StartsFromTheAnimatedValue` accidentally still green (a P1-shaped correctness gap the plan's phrasing did not call out explicitly, caught by tracing the "stay quiet" branch during implementation). Every existing guard (the self-tick guard on `Animation.CurrentValue`/`Animation.To`, the `_HasSettledValue` guard) is unchanged; `UIPropertyAnimation<T>.ReadCurrentValue` is untouched (ADR-0006). Measured (not merely reasoned) frame timing, since animations tick at the head of the frame before visual states are evaluated (ADR-0006 decision 7): a non-tagged container write (e.g. `element.BackgroundBrush.NormalValue = x`) retargets synchronously, same statement; a tagged, precedence-gated pilot write (`Margin`, `Padding`, `MinHeight`, any pilot's tagged setter) retargets on the run's own next tick (a gated write raises no notification by itself); a named-state exit retargets two ticks after the call that triggers it (the base is recorded only after that frame's own animation tick, so a second tick is needed to see it) — in every case, no jump (the retargeted run always starts from its current animated value) and never later than the old run's own end (the V1 "seen at the end of the run" limit is lifted, not merely shortened).
- Value below the animation (U3, simplifications): `UIVisualStateApplier<T>.CaptureBase` was simplified for store-backed targets exactly as planned (`TryGetValueBelowAnimation`, falling back to the previous read when it returns false), dropping the `SettledValue` special case for those targets since the new read stays correct mid-run; the special case is kept, and documented as still needed, for plain (non-store) targets, whose physical value *is* the animated one while a run is in flight. `UIStoreBackedTargets.Restore`'s three-way branch (another contribution remains / only `Animation` remains / nothing remains) was **not** simplified, unlike the plan's proposal to merge the last two into "park the base under the container source whenever no non-`Animation` contribution remains": tracing that merge against `VisualStatesTests.LeavingAStateOnAThemeBackground_PutsTheThemeColourBack` (no run in flight, plain state exit) showed it would leave a stray `Theme` contribution on the exited sub-slot instead of the empty list that test asserts (`WholeSource` reads the pilot's Whole slot, not the sub-slot being restored, and a Theme-written container has its own Whole contribution to surface there) — reverted before committing; only the *read* side (`TryGetValueBelowAnimation`) changed, not this write path. Both decisions were verified by running the full suite with and without the attempted change, not by reasoning alone.
- Value below the animation, Fix round 1 (13 September 2026): the "falling back to the previous read when it returns false" claim above did not hold for store-backed targets before this fix — `CaptureBase`'s `SettledValue` fallback was gated `_StoreTarget == null`, so a store target that failed `TryGetValueBelowAnimation` fell straight through to the plain physical read (`GetUnderlyingValue`/`GetValue`), the very in-flight value the U3 read was meant to avoid. `TryGetValueBelowAnimation` itself could also wrongly return **true** with that in-flight value: `TryGetResolvedBackgroundSubSlotValue`/`TryGetResolvedDefaultTextForegroundSubSlotValue`'s physical-fallback branch (`MGElement.cs`, R6) attributed the container's current physical sub-field to the Whole winner's source whenever a Whole winner existed under the exclusion, without checking whether the *excluded* kind itself still had a live contribution on that very sub-slot — exactly the configuration a Whole-container swap (a theme change) produces: the transition's `Animation` contribution is the sub-slot's only contribution, so excluding it should read "nothing recorded", not the physical field the animation is actively driving. Both methods now skip that physical fallback when `TryGetResolvedContribution<T>(property, slot, excluded.Value, out _)` finds a live contribution of the excluded kind on the sub-slot, via the existing `TryGetResolvedContribution` helper (no new store API); `CaptureBase`'s `SettledValue` fallback is now unconditional (store-backed or not) so this now-correctly-`false` case is caught the same way a plain target's mid-run capture always was. Reproduced directly (unit-level `TryGetResolvedPilotValueExcluding` on an Animation-only sub-slot, `PilotValueBelowAnimationTests.Background_ExcludingAnimation_ReturnsFalse_WhenTheSubSlotsOnlyContributionIsAnimation`) and end-to-end (`VisualStatesTests.EnteringAStateMidTransitionStartedByAWholeContainerSwap_ComesBackToTheSwappedInColour`: a Whole theme swap starts the run, `Checked` is entered mid-run, the base is captured then, and after exit and the run's natural end the background settles on the swapped-in colour, not the in-flight one) — both fail without the fix and pass with it; full suite green (2115/2115) with the fix. `UITransition<T>.HandleChanged` needed no change: its own self-tick guard (`_Comparer.Equals(underlying, Animation.CurrentValue)`) already made the previously-wrong `true` result and the corrected `false` result compute the same `underlying` value in that branch, so retargeting behaviour is unaffected — only `CaptureBase` (a visual state's base) was ever reading a genuinely wrong value.
