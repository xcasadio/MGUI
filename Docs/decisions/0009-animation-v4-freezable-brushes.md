# ADR-0009: Animation V4: brushes as freezable, animatable data objects

- **Status**: Proposed (2026-09-14, waiting for the author's approval of `Docs/Tasks/animation-v4-tasks.md`)
- **Date**: 2026-09-14
- **Source**: this chantier: the author's question "how does Noesis handle animated brushes" after the V3 program, two read-only discoveries at HEAD `23cab97` and the author's answers to the four questions of `Docs/Tasks/animation-v4-tasks.md`

## Context

Facts verified at HEAD `23cab97` (V1 to V3 delivered by ADR-0006, ADR-0007 and ADR-0008):

- Ten value brushes are `readonly struct`s: `MGSolidFillBrush` (with a static palette `SolidFillBrushes` of 147 shared instances), `MGGradientFillBrush`, `MGDiagonalGradientFillBrush`, `MGTextureFillBrush`, `MGNineSliceFillBrush`, `MGProgressBarGradientBrush`, `MGUniformBorderBrush`, `MGDockedBorderBrush` (with a constructor-time `IsSolidColorsOnly` cache), `MGBandedBorderBrush`, `MGTexturedBorderBrush`. Six brushes are mutable classes without any freeze notion (four composites, `MGHighlightFillBrush`, `MGHighlightBorderBrush`). Every brush exposes `Copy()`; none overrides equality; no test asserts value equality of a whole brush; `MGSolidFillBrush` is constructed at 169 sites (95 in tests) and type-tested at 21 sites (`MGDockedBorderBrush`, `RequireSolid`, `MGUniformBorderBrush`).
- The engine never mutates a brush: every brush-valued target (`Background` and its state slots, `Background.Gradient`, `Background.DiagonalGradient`, `BorderBrush`) allocates a new brush per tick and writes it into the `Animation` (100) contribution of the store (`UIColorAnimationTargets.cs:101, 240`, `UIExtraAnimationTargets.cs:106-172`); a colour transition costs 104 bytes per tick, documented as an accepted cost.
- Equality guards: the eleven store write sites for brush pilots already use `ReferenceEqualityComparer.Instance`; `VisualStateSetting<T>` slot setters and `MGControlTemplate.ApplyTemplateValueCore` ("current value still equals the previous template default") use `EqualityComparer<T>.Default`, which is value equality for boxed structs today.
- Sharing: `MGTheme` holds 78 brush properties, `ThemeManagedGetter.GetValue(true)` clones on every read, `MGTheme.Copy()` recopies 49 brushes; `UIResourceReferenceApplicator` hands a `StaticResource` brush to every element by reference; XAML DTOs create one instance per `ToFillBrush` / `ToBorderBrush`; no element observes a brush (invalidation flows through element setters and the `VisualStateFillBrush` container).
- `MGHighlightBorderBrush` is the only brush with a clock: `Update` accumulates `(UA.AnimationDeltaTime ?? UA.FrameElapsed) / CycleDuration` into `AnimationProgress`, applies `StopOnMouseOver` / `StopOnClick` by setting `IsEnabled = false` on the brush itself when `Target` is hovered or pressed, so a shared instance stops for every element; `UpdateBaseArgs.AnimationDeltaTime` (added by V3) has no other consumer.
- NoesisGUI / WPF model (docs `Gui.Core._Brush`, `Gui.DependencySystem._Freezable`, forum threads 2598 and 442): `Brush : Animatable : Freezable : DependencyObject`; a brush is an animatable data object with no clock; a storyboard animates its properties through a property path resolved from an element; a frozen brush is immutable and shareable; animating an unfrozen shared brush animates every element referencing it; `Clone` copies values but not animations.

## Decision

1. Freezable contract: `IUIFreezable` (`IsFrozen`, `CanFreeze`, `Freeze()`) carried by `IFillBrush` and `IBorderBrush` through default interface members, implemented by an abstract `UIFreezableBrush` base (`ViewModelBase`, `ThrowIfFrozen` in every setter, recursive `Freeze`, `Copy()` = unfrozen deep copy; `Copy` keeps its name). A frozen brush never notifies; an unfrozen one raises `PropertyChanged` without allocation.
2. The ten value brushes become sealed mutable classes deriving from `UIFreezableBrush`, with settable notifying properties and unchanged constructors, `Copy()` and `Draw`; the six mutable classes adopt the contract and propagate `Freeze` / `Copy` to their children. Equality is reference equality (as in WPF); the guards that relied on struct value equality (`VisualStateSetting<T>` slot setters, `MGControlTemplate.ApplyTemplateValueCore`) use an explicit `UIBrushEquality.ValueEquals` helper (per-type, recursive for composites) instead; the store keeps reference equality.
3. Freezing policy: theme brushes (frozen at the end of `ThemeDefinitionBuilder.Build` and by every `MGTheme` setter), the static palette and static-resource brushes are frozen and shared without copy (`ThemeManagedGetter.GetValue` returns the frozen instance, `MGTheme.Copy()` shares, `VisualStateFillBrush` copies share their frozen slots); XAML inline brushes and code-created brushes stay unfrozen and element-owned; `Copy()` of a frozen brush is unfrozen.
4. Clone on animate, one rule for every base: the animated value of a brush pilot lives in the `Animation` (100) contribution of the store as today, but it is one object created when the run starts (`Copy()` of the effective brush below the animation, or a fresh brush of the expected type) and mutated per tick by the run, with no store write and no allocation per tick; restoring removes the contribution and the base reappears untouched. MGUI does not reproduce the Noesis behaviour "an unfrozen shared brush animates every element": the store's contribution layer plays the role of the dependency property animated value. The `VisualStateFillBrush` container and `MGBorder` subscribe to an unfrozen slot brush (so to an animated clone) to invalidate drawing, never to a frozen one.
5. Highlight on the engine: `MGHighlightBorderBrush` becomes a freezable configuration; `AnimationProgress` (name kept) is the current progress in [0, 1) written by an engine run through the new target `BorderBrush.Highlight.Progress` (double, simple, not observable); `Update` no longer accumulates time; `CycleDuration` becomes public; `AutoStart` (default true) lets the element host start a `RepeatForever` run of duration `CycleDuration` when the effective border brush is an enabled highlight brush (on attach, on border change, on enable), cancel it (`KeepCurrent`) on detach, border change or disable; `StopOnMouseOver` / `StopOnClick` act on the element's own animated clone, never on the base brush; `MGElement.ResumeBorderHighlight()` restarts; `Target` stays as an obsolete no-op. Two elements sharing a frozen highlight brush each have their own cycle.
6. `UpdateBaseArgs.AnimationDeltaTime` and its assignment in `MGDesktop.Update` are removed (a host reads `Desktop.Animations.Clock.DeltaTime`).
7. Sample: `AnimationDemo` is rebuilt on the skeleton of the control pages (`MGUI.Samples/Controls/CheckBox.xaml`, `ComboBox.xaml`): one vertical page presenting each capability of the engine with an explanation and a live demonstration (transitions, explicit animations and the fluent API, render transform, clock, composition, keyframes and clips, named visual states, styles and theme, animatable brushes, highlight, preview and seek, serialisation, controls on the engine, diagnostics), with descriptive element names and no trace of the system's evolution (no V1/V2/V3/V4 column or mention); the per-program scenarios `SCN-ANIM-001..003` are merged into a single `SCN-ANIM-001` described by capability.
8. Closure: at the end of the program the four animation task files are deleted, the scenario index points at the architecture doc and the ADRs, and every code, test or sample comment citing a task file or a slice number is rewritten as a behaviour description; the history stays in ADR-0006 to ADR-0009.

Out of scope: generic property-path animation into a brush (`(Background).(SolidColorBrush.Color)`): the closed target registry stays, with existing paths and one new path; texture and nine-slice brushes stay non-interpolable; the highlight host does not look inside composite border brushes; the timers outside the engine (ADR-0006 decision 7) are untouched; the open points of ADR-0008 are not addressed here.

## Consequences

- No allocation per tick for any animation, colour and gradient targets included; a theme copy no longer deep-copies its brushes; a brush shared by a theme or a resource cannot be corrupted by application code (mutation throws).
- Behaviour changes to announce: a highlight brush shared by several elements gives each element its own cycle (aligned only when attached the same frame) and `StopOnMouseOver` / `StopOnClick` stop the hovered element only; assigning a brush to a theme freezes it; a struct-typed field or local that held a brush by value now holds a reference (null is possible); `AnimationDeltaTime` disappears from `UpdateBaseArgs`.
- Accepted costs: one `PropertyChanged` subscription per unfrozen brush held by a container or border, none for frozen brushes; one clone per animation run; a value-equality helper maintained per brush type.
- Risks tracked by the plan: the two value-equality guards (template default re-application, visual-state slot notification) must keep their current observable behaviour; `MGDockedBorderBrush` caches must follow property changes; the 169 construction sites compile unchanged but any code that assumed a non-null struct must guard against null.
- Deferred: generic brush property paths, interpolation of textures, a shared-cycle option for highlight brushes, freezing of `VisualStateFillBrush` containers themselves.

## Decisions taken during delivery

### W1

- The default interface members added to `IFillBrush`/`IBorderBrush` (`IsFrozen => true`, `CanFreeze => true`, `Freeze() {}`, `ValueEquals(other) => Equals(other)`) are explicitly transitional: every concrete brush is expected to override them once it derives from `UIFreezableBrush` in a later slice. Kept as default interface members (rather than, say, extension methods) so the ten structs and six classes keep compiling with zero changes, which is the whole point of splitting the contract from the conversion.
- `UIBrushEquality.ForGuards<T>()` is a static-generic cache (`GuardComparerCache<T>`) rather than a runtime type switch on every call: the two call sites (`VisualStateSetting<T>`'s field initialiser, `MGControlTemplate.ApplyTemplateValueCore`'s `Comparer ??= ...`) run once per closed `T`, so a static generic field costs nothing per call and needs no lock. The `VisualStateSetting<>` generic case is resolved once through reflection (`Activator.CreateInstance`) the first time that particular `T` closes, not per call.
- `VisualStateFillBrush.ValueEquals` compares every field the container's own copy constructor treats as part of its identity (the four slots, `HasCheckedValue`/`CheckedValue`, `FocusedColor`, `PressedModifierType`, `PressedModifier`, `OverlayOpacity`), not just the four visible slots, since two containers that differ only in the pressed-modifier scalar are not the same value.
- Test files stay under `MGUI.Tests/Architecture/` (`FreezableBrushTests.cs`, `BrushGuardEqualityTests.cs`) rather than a new `MGUI.Tests/Drawing/` folder, since that is where the existing brush test (`FillBrushLifecycleTests.cs`) already lives and no `Drawing` folder exists in the test project.
- The mutation proof (pointing `ForGuards<T>()` at `ReferenceEqualityComparer.Instance` for brush `T`) was run by hand and reverted; see the W1 status note in `Docs/Tasks/animation-v4-tasks.md` for the exact result.
- Reviewed by the main session after the fresh verifier's CONFIRMED verdict (one P3): for `T = VisualStateFillBrush` the template-refresh guard of `MGControlTemplate` compared containers by reference before this slice (the container is a class) and compares them by value now, so a distinct but value-equal container assigned by an application is treated as "still the previous default" and re-applied on theme refresh. Accepted deliberately: it is the alignment the plan wants for every brush-typed guard and it closes the known gap where a recreated part's reference-typed template value was never re-applied; the ordinary catalogue path stores the very instance it applies and is unaffected.

### W2

- `MGSolidFillBrush`, `MGGradientFillBrush` and `MGDiagonalGradientFillBrush` became sealed classes deriving from `UIFreezableBrush`, each with its own `ValueEquals(IFillBrush)` (by-colour comparison) instead of the transitional default interface member. `SolidFillBrushes` freezes every palette field from its static constructor by reflecting over `typeof(SolidFillBrushes).GetFields(Public | Static)`, rather than calling `.Freeze()` on each of the 147 field initialisers by hand, so a future addition to the palette needs no matching freeze line.
- Null-safety audit (grep of every `MGSolidFillBrush`-typed declaration across `MGUI.Core`, `MGUI.Samples`, `MGUI.Tests`, excluding the interface-typed `IFillBrush` sites and pattern matches): the only fields that are not interface-typed and were not already guarded are `VisualStateBrush<TDataType>.HoveredFillOverlay` / `PressedFillOverlay` (`MGUI.Core/UI/VisualState.cs`, both private). They can now be `null` (before W2 their struct default was an implicit transparent colour) in the one case where the constructor's `FocusedColor` setter never fires because the incoming value already equals the field's own default (`null == null`), which happens whenever a control passes no hover colour. This is not a behaviour change: `GetFillOverlay` already returned `null` for `SecondaryVisualState.None`, so every caller already null-checks (`?.Draw(...)`) or assigns straight into the `IFillBrush` interface (a class-to-interface reference conversion accepts `null`); a transparent draw was a no-op anyway (`MGSolidFillBrush.Draw` skips `Color.Transparent`). No other type or file needed a guard: `MGDockedBorderBrush`, `MGUniformBorderBrush`, `MGGraphSurfaceCanvas`, `MGGraphControls`, `MGShapeElementBase`, `IFillBrush.TryDarken` only ever use `is`/`as` pattern matches against the interface, which stay correct for `null` (a pattern match against `null` is `false`, never a throw).
- `VisualStateBrush<TDataType>.GetFillOverlay(SecondaryVisualState)` changes its return type from `MGSolidFillBrush?` (`Nullable<MGSolidFillBrush>`, meaningful while the type was a struct) to plain `MGSolidFillBrush`, since a reference type is already nullable; the two internal callers in the same file (`DrawFillOverlay` fill overloads) that used to unwrap with `.Value.Draw(...)` now call `.Draw(...)` directly (they already null-check `overlay == null` first). Every external caller was already written as `?.Draw(...)` or a plain assignment into an `IFillBrush`-typed target, so none needed a change.
- Decision beyond the literal ADR wording above ("Equality is reference equality, as in WPF"): `MGSolidFillBrush`, `MGGradientFillBrush` and `MGDiagonalGradientFillBrush` also override `object.Equals(object)`/`GetHashCode()` with the same by-colour comparison as `ValueEquals`, rather than leaving the inherited reference equality as the ADR's general rule would suggest. Reason: the codebase's own test suite turned out to already rely on structural equality of these three types through plain `Assert.Equal` at several sites outside this slice's perimeter and outside the two guards the ADR names (`ResolvedBackgroundPilotTests`, `ResolvedThemeChangeTests`, `ResolvedScalarPilotsTests`) — one of them (`ResolvedBackgroundPilotTests.TreeViewItem_Selection_Writes_VisualState_Background_And_Deselection_Restores_The_Previous_Instance`) documents in its own comment that it deliberately asserts "value-equivalence" rather than reference identity (ADR-0005/S5), and a second (`ResolvedThemeChangeTests`) explicitly comments "MGUniformBorderBrush is a value type: two independently-boxed copies compare structurally equal but are never ReferenceEquals" as the reason it uses `Assert.Equal`. Converting only `ValueEquals` while leaving `Equals` as reference equality broke six tests (surfaced by the full-suite run, not anticipated by the ADR's "no test asserts value equality of a whole brush" fact, which was true only while every brush stayed a struct): five through `MGUniformBorderBrush`'s own default `Equals` (a struct, unconverted, whose memberwise comparison forwards to its `IFillBrush` field's `Equals`) and one through a direct `MGSolidFillBrush` comparison. Overriding `Equals`/`GetHashCode` by value on the three converted types fixes both categories at the root, in the two files already in this slice's perimeter, without touching any test or any not-yet-converted border-brush struct. Reference identity remains available and is still what the store's pilot writes and the paint per-frame dedup actually rely on (both already use an explicit reference-equality comparer, never `object.Equals`), so nothing that needs "the exact same instance" lost that ability.
- Fix round (W2-fix, main session, P2 found by the W2 verifier): `VisualStateSetting<T>`'s slot setters kept comparing by VALUE for a brush-typed `T` (`ForGuards<T>()`) after W2 turned the brushes into classes, so `container.NormalValue = mine` with `mine` a distinct instance equal in value to the current slot was a silent no-op — the container kept the OLD instance, and a later `mine.Color = ...` (the whole point of a mutable, element-owned brush, W4) could never reach the element. Before W2 the brushes were structs with no identity, so nothing was lost; with classes, identity is part of the value. Decision: slot setters now compare by REFERENCE for a brush-typed `T` (new `UIBrushEquality.ForSlots<T>()`, reference equality for a reference type implementing `IUIFreezable`, value equality otherwise), while `MGControlTemplate`'s theme-refresh guard keeps `ForGuards<T>()` (value equality: it decides whether the user diverged from a template default, identity irrelevant there). `Equals`/`GetHashCode` by value on the W2 brushes are unchanged. The background pilot's physical re-application path (`ApplyBackgroundBrushSlotPhysical`, `ReapplyBackgroundSubSlots`, `ApplyBackgroundFocusedColorPhysical`) was already guarded on every write by `_suppressBackgroundContainerNotify`, so no feedback loop appeared and `MGElement.cs` needed no change. `BrushGuardEqualityTests.cs` rewritten: a distinct-but-equal-valued instance is now stored (`Assert.Same`) and notifies once, re-assigning the same instance still does not notify, and an end-to-end case (`AnimationTestScene`) proves a mutation of the newly assigned instance changes the next drawn frame; the template-guard tests are untouched. Mutation proof: pointing `ForSlots<T>()` at the value comparer makes exactly those two new tests fail; reverted after confirming. Full suite green: 2283/2283 (2281 + 2).

### W3

- Correctness fix made during delivery (not a design choice, but worth recording): `MGTextureFillBrush.Source`, `MGNineSliceFillBrush`'s nine patches and `MGTexturedBorderBrush.EdgeTexture`/`CornerTexture` are all typed `MGTextureData`, a `readonly record struct`. An initial draft compared them with `ReferenceEquals` in `ValueEquals` (matching the "shared by reference on `Copy`" wording of the brief) — but `ReferenceEquals` on a struct always boxes both operands and is therefore false for two separately-obtained property reads even when they hold the same value, silently breaking `ValueEquals`/`Equals`/`GetHashCode` for every one of these three types. Fixed to use the record struct's own generated `.Equals(...)` (which itself compares the `Image` field by reference — `IUIImageResource` is a reference type — and the other fields, `SourceRect`/`Opacity`/`RenderSizeOverride`, by value), which is what "the same underlying texture data" actually means for a struct. Caught by hand before the test pass (not by a failing test): worth a dedicated `Assert.True(a.ValueEquals(b))` with two independently-constructed `MGTextureData` wrapping the same image in a later slice if this code is touched again.
- Collection-freezing choice for `MGCompositedFillBrush`/`MGCompositedBorderBrush` (brief point 2, "wrap or guard"): chose WRAP over guard — a private nested `GuardedList` implementing `IList<T>` around the actual `List<T>`, with every mutating member (`Add`, `Insert`, `Remove`, `RemoveAt`, `Clear`, the indexer setter) calling the owning brush's `ThrowIfFrozen` before touching the inner list, and `IsReadOnly` reporting the owner's `IsFrozen`. Rejected alternative: guarding the existing public `List<IFillBrush>` field in place (e.g. replacing it with `ReadOnlyCollection<T>` once frozen) would have required either a mutable/immutable type swap on the public property (a breaking API change for any external `.Brushes.Add(...)` call site) or exposing two properties (a mutable one pre-freeze, read-only post-freeze), both worse than one property whose behaviour changes with `IsFrozen`, matching how every other freezable property in this codebase already behaves. The public field became a `IList<IFillBrush> Brushes` property (was `readonly List<IFillBrush>`); no call site depended on `List<T>`-specific members (`Capacity`, `AddRange`, ...), confirmed by a full-solution build. Duplicated verbatim between the two composite files rather than factored into a shared generic type, since `MGCompositedFillBrush`/`MGCompositedBorderBrush` implement different brush interfaces and `UIFreezableBrush` (where a shared helper would naturally live) is outside this slice's perimeter.
- `XAMLBindableBase` disposition (brief point 2): `MGHighlightFillBrush` derives from `XAMLBindableBase` for its XAML data-binding support (`Bindings`, `ResourceReferences`, `DataContext`, `IObservableDataContext`) and C# has no multiple inheritance, so it cannot also derive from `UIFreezableBrush`. Decision: implement `IUIFreezable` directly on `MGHighlightFillBrush` (a private `_IsFrozen` field, `IsFrozen`/`CanFreeze` properties, a `Freeze()` method and a private `ThrowIfFrozen([CallerMemberName])` helper — the same three members and the same discipline as `UIFreezableBrush`, duplicated rather than shared since there is no common non-`ViewModelBase` base to hang them on) and add a `ThrowIfFrozen()` call to the start of every property setter. `CanFreeze` is always `true`: this brush owns no nested `IUIFreezable` paint to propagate to (`FocusedElements`/`FocusedBounds` are plain data, not paints). No `ValueEquals`/`Equals` override added (matches the pre-existing rule from `UIBrushEquality`'s own doc comment: the composite/highlight classes use reference equality). `MGHighlightBorderBrush` had no such constraint (it derived from plain `ViewModelBase`), so it was switched to derive from `UIFreezableBrush` directly instead, gaining `Freeze`/`CanFreeze`/`ThrowIfFrozen`/`SetProperty` for free; every setter except `AnimationProgress` (explicitly out of scope, W6 owns its per-frame accumulator) now calls `ThrowIfFrozen()`. `Copy()` on both classes is untouched (its semantics were not part of this slice's claim).
- Null-audit findings (brief point 4, grep of every declaration typed with one of the seven converted structs across `MGUI.Core`, `MGUI.Samples`, `MGUI.Tests`, excluding interface-typed sites and pattern matches): the only stale nullable-of-struct usage was `VisualStateBrush<TDataType>.GetBorderOverlay(SecondaryVisualState)`, still returning `MGUniformBorderBrush?` (meaningful pre-W3, meaningless for a class); fixed to plain `MGUniformBorderBrush` and its two internal callers' `overlay.Value.Draw(...)` to `overlay.Draw(...)` — the exact same pattern W2 already applied to `MGSolidFillBrush`/`GetFillOverlay`. One pre-existing, not-introduced risk noted rather than fixed (out of this slice's perimeter): `MGGroupBox.BorderBrush`'s getter does an explicit cast `(MGUniformBorderBrush)BorderElement.BorderBrush`; if `BorderElement.BorderBrush` (an `IBorderBrush`) were ever `null`, this already threw `NullReferenceException` before W3 (unboxing a null interface reference to a struct throws) — after W3 the cast itself no longer throws on `null` (a reference-type down-cast of `null` is `null`), but the very next read of `.Brush` on the result (`MGGroupBox.cs:222`) would throw at that point instead. No behaviour change in the reachable path (the constructor always assigns a non-null `MGUniformBorderBrush`, and the public setter requires a non-null value the same way), so left as-is.
- Fix round (W3-fix, main session, P2 found by the W3 verifier): `MGPaddedFillBrush.Brush`, `MGBorderedFillBrush.BorderBrush`/`FillBrush` and `MGDockedBorderBrush.Left`/`Top`/`Right`/`Bottom` routed through the plain `SetProperty<T>` overload, which compares with `EqualityComparer<T>.Default` — since every value brush now has a by-value `Equals` (W2/W3), assigning a distinct-but-value-equal brush to one of these composite child properties was a silent no-op (old instance kept, no `PropertyChanged`, a later mutation of the newly assigned instance could never reach the element), exactly the `VisualStateSetting<T>` slot hazard the W2-fix round already fixed with `UIBrushEquality.ForSlots<T>()`. Decision: added a `SetProperty<T>(ref T field, T value, IEqualityComparer<T> comparer, ...)` overload to `UIFreezableBrush` and routed all seven properties above through it with `UIBrushEquality.ForSlots<T>()` (reference equality for a brush-typed `T`), matching the slot rule exactly. `MGDockedBorderBrush`'s four setters also gained an explicit `ThrowIfFrozen()` call before the `value ?? throw new ArgumentNullException(...)` null-check (a second, independent P4 in the same review: a write to a frozen instance with a `null` argument reported `ArgumentNullException` instead of the frozen error, because the null-check ran before `SetProperty`'s own `ThrowIfFrozen`); `MGProgressBarGradientBrush.ProgressBar` got the same reordering (not a brush-typed property, so its comparer is unchanged). `MGUniformBorderBrush.Brush` needed no change (read-only, no public setter). Also addressed (P3): `Docs/animation-architecture.md` and `Docs/drawing-architecture.md` claimed no core brush still uses the transitional `ValueEquals` default interface member; `MGHighlightFillBrush`/`MGHighlightBorderBrush` in fact still do (deliberately, per the W3 entry above — reference equality, unchanged since before W3), so both doc sentences were narrowed to name the two exceptions instead of asserting none exist. Full suite green after the fix: see the verification run recorded below.
- Reviewed by the main session after W3 (verifier CONFIRMED after one fix round): the `Brushes` member of `MGCompositedFillBrush` and `MGCompositedBorderBrush` changed from a public `List<T>` field to an `IList<T>` property guarded after `Freeze()`; this is a source and binary API change for an external consumer of MGUI.Core (`AddRange`, `Capacity`, field access), accepted because a frozen composite must refuse mutation of its children list, and recorded here as a change to announce with the V4 release.

### W4

- `ThemeDefinitionBuilder.Build` freezes the produced theme through one new method, `MGTheme.FreezeBrushes()`, rather than hand-listing the 78 brush-typed properties the ADR names: it reflects over `MGTheme`'s own public properties and recurses into every nested settings-group instance (`Window`, `Overlay`, `Graph`, `Docking`, ...), unwraps a `ThemeManagedGetter<T>` (`GetValue(false)`, no clone), walks a `VisualStateFillBrush`'s four slots plus `CheckedValue` (the container itself is never frozen, W3), and walks any `IEnumerable` (`ListBoxItemAlternatingRowBackgrounds`); `_Backgrounds` (a private dictionary, unreachable by reflection over public members) is walked directly in `FreezeBrushes` itself. Chosen over a manual list because the brief's own accuracy history in this ADR already shows two counts that turned out wrong at delivery time (147 vs 143 palette fields, W1/W2; 78 theme properties is itself unverified) -- a reflection-driven sweep cannot miss a property, and `BrushFreezingPolicyTests` proves completeness with an independently written reflection walk rather than re-running the same code path.
- Every brush-typed theme property freezes the instant it is assigned, no exceptions: a property wrapped by `ThemeManagedGetter<T>` (about fifteen of the ~78 -- `SliderForeground`, `ScrollBarOuterBrush`, every entry of `_Backgrounds`, ...) freezes through that wrapper's single `Value` setter; every remaining plain auto-property on `MGTheme` itself (`TreeViewBorderBrush`) and on a nested settings group (`Window.BorderBrush`, `Graph.EdgeBrush`, and the rest of the ~60 other brush properties across the twelve settings-group classes) now has a hand-written backing-field setter that calls `MGTheme.FreezeThemeValue(value)` before storing.
- Fix round (W4-fix, main session, P2 found by the W4 verifier): the first delivery left every plain auto-property un-intercepted, freezing them only through `FreezeBrushes()`'s end-of-`Build` sweep; `MGTheme.Copy()` never called that sweep either (`ApplyFrom` relies on `ShareOrCopy`/per-property assignment instead), so a theme customised after `Build` via a supported public API (`theme.Window.BorderBrush = new MGSolidFillBrush(...).AsUniformBorderBrush()`) held an unfrozen, shared-by-reference brush. That mattered beyond the acceptance clause itself: `MGControlTemplateCatalog` hands `Theme.Window.BorderBrush` to every window's `MGBorder` by reference, and W4's own new subscription (`MGBorder.ResyncBorderBrushSubscription`) attaches a live `PropertyChanged` handler to any unfrozen border brush with no teardown path other than replacement -- one unfrozen theme border brush would have accumulated one handler per window ever created and rooted every one of those `MGBorder` instances for the theme's lifetime. Fixed by converting every one of the ~60 remaining plain brush-typed properties (`MGTheme.TreeViewBorderBrush` and every brush property of `MGThemeWindowSettings`, `MGThemeOverlaySettings`, `MGThemeContextMenuSettings`, `MGThemeContextMenuItemSettings`, `MGThemeListBoxSettings`, `MGThemeListViewSettings`, `MGThemePropertyGridSettings`, `MGThemeComboBoxSettings`, `MGThemeToolTipSettings`, `MGThemeTabControlSettings`, `MGThemeGraphSettings`, `MGThemeDockingSettings`) from a plain `{ get; set; }` auto-property into a private backing field plus an explicit property whose setter calls `MGTheme.FreezeThemeValue(value)` before storing -- the exact same helper `FreezeThemeObjectGraph`'s reflection sweep already calls on each property's value, so the two paths can never disagree. `FreezeBrushes()`'s reflection sweep is now a no-op for every brush reachable this way (every setter it invokes indirectly through `Property.GetValue` was already frozen) and stays in place both as a safety net for any future property that forgets the pattern and as the mechanism the reflection-based `BrushFreezingPolicyTests` completeness probe still exercises. The narrowing this replaces was pinned by `BrushFreezingPolicyTests.Assigning_An_Unfrozen_Brush_To_A_Plain_Theme_Property_Freezes_Only_After_FreezeBrushes`, renamed to `..._Freezes_It_Immediately` and rewritten to assert the brush IS frozen right after assignment (both `MGTheme.TreeViewBorderBrush` and `MGThemeWindowSettings.BorderBrush`), matching `..._ThemeManaged_Property_Freezes_It_Immediately`: there is now exactly one freezing timing across the whole theme, not two.
- `MGTheme.ApplyFrom` (backing `Copy()`) replaces `Source.X?.Copy()` with a new private generic `ShareOrCopy<T>(T brush) where T : class, IUIFreezable, ICloneable` for every plain (non-`VisualStateFillBrush`, non-`VisualStateColorBrush`) brush-typed property (about 27 call sites across `TreeViewBorderBrush`, `ToolTip`/`Window`/`Overlay`/`ContextMenu`/`ListBox`/`ListView`/`PropertyGrid`/`ComboBox`/`TabControl`/`Graph`/`Docking`): shares the frozen instance by reference, falls back to `Copy()` (still unfrozen afterwards, per the brush contract) only for the residual case where a brush cannot freeze. `VisualStateFillBrush`/`VisualStateColorBrush`-typed properties keep calling their own `.Copy()`/`.GetCopy()` unchanged: that copy constructor already shares frozen slots since W3, so wrapping it in `ShareOrCopy` would have been redundant.
- `MGResources.AddStaticResource`/`SetStaticResource` freeze a brush value (or, less commonly, each non-null slot of a whole `VisualStateFillBrush` registered as a resource) through a small private `FreezeIfBrush` mirroring `MGTheme.FreezeThemeValue`'s brush/container cases, duplicated rather than shared: `MGResources` and `MGTheme` have no common base to hang a shared helper on, and each walk is a handful of lines. `UIResourceReferenceApplicator` needed no change (it already hands out the stored instance by reference; that is now safe because the instance is frozen).
- Notification design: `VisualStateFillBrush` tracks, per slot (`NormalValue`, `SelectedValue`, `FocusedValue`, `DisabledValue`, `CheckedValue`), which brush instance it currently holds an active `PropertyChanged` subscription on (`_SubscribedXxxValue` fields) rather than deriving the answer from the slot's current value on demand -- a slot can go from one frozen brush to another, and only the fields let the resync tell "never subscribed" apart from "was subscribed, now must unsubscribe". The container self-subscribes to its own `PropertyChanged` (`HandleOwnSlotReferenceChanged`) to catch a slot *reference* changing (a real `NormalValue = otherBrush` assignment) and resync that one slot's subscription; a subscribed slot brush's own mutation is relayed through `HandleSlotBrushMutated` as a distinct container-level notification, `SlotBrushMutatedPropertyName` ("SlotBrushMutated"), never one of the four slot-reference names -- so `MGElement.HandleBackgroundBrushContainerPropertyChanged`'s existing `switch` (unchanged, no new `case`) falls through its own `default: break;`, exactly satisfying the brief's "the store is NOT rewritten for an in-place mutation". `MGBorder` mirrors this with a single `BorderBrush`-shaped subscription (`ResyncBorderBrushSubscription`/`HandleBorderBrushMutated`), relaying a mutation as a plain `NotifyPropertyChanged(nameof(BorderBrush))` -- confirmed safe to reuse (not a new distinct name) by reading every one of the fifteen-odd `OnBorderBrushChanged` subscribers in the codebase: each only re-raises its own `PropertyChanged`, none touches the store or layout, so replaying it for a mutation carries no risk of the "layout/store work" the brief warns against; `OnBorderBrushChanged` itself (the `Previous`/`Current` event) is deliberately NOT re-raised for a mutation, since no reference actually changed.
- No drawing-invalidation call was added anywhere for a slot/border mutation, and none is needed: a grep of the rendering path (`NeedsRedraw`, `IsDrawValid`, `InvalidateDraw`, `MarkDirty`) turns up nothing -- MGUI never caches a drawn frame, so `IFillBrush.Draw`/`IBorderBrush.Draw` already reads the mutated brush's live field values on the very next frame regardless of any notification. The subscription's actual job is lifecycle correctness (no leaked handler once a slot/border is replaced) and being able to prove "zero subscriptions when every brush is a frozen theme default" (`BrushFreezingPolicyTests`), exactly as the brief's acceptance criteria ask for -- not triggering a redraw that was always going to happen anyway.
- Bug found and fixed during delivery (not a design choice): a theme background definition is built as a *freshly constructed, unfrozen* `VisualStateFillBrush` inside `ThemeDefinitionBuilder.ApplyBackgrounds`/`ApplyVisualStateFillBrush` (the XAML DTO's `ToFillBrush()` always returns an unfrozen brush) and only frozen afterwards, at the very end of `Build`, by the new `FreezeBrushes()` sweep. Because that same container instance is stored directly into `MGTheme._Backgrounds` (never cloned for that first write), its own self-subscription had already subscribed to the not-yet-frozen `NormalValue` brush by the time `FreezeBrushes()` ran; freezing the brush does not itself raise a notification, so the container never learned its slot had become safe to leave unsubscribed, and the stale subscription lived forever on the shared, now-frozen, palette-style brush -- surfacing as `BrushFreezingPolicyTests.ElementOnThemeDefaults_Has_Zero_Subscribers_On_Every_Background_Slot` reporting 1 subscriber instead of 0 on an otherwise-correctly-frozen brush. Fixed by adding `VisualStateFillBrush.ResyncSlotSubscriptionsAfterExternalFreeze()` (internal), called by `MGTheme.FreezeThemeValue`'s and `MGResources.FreezeIfBrush`'s `VisualStateFillBrush` case immediately after freezing each of its slots: it re-runs the exact same per-slot resync the container already does on every ordinary slot-reference change, which now correctly drops a subscription whose target just became frozen. This is a general fix to the actual invariant ("never subscribed to a frozen brush", not just "never subscribes to an already-frozen brush"), not a one-off patch for the theme-build path alone -- the identical hazard exists for any `VisualStateFillBrush` a caller freezes after assigning it unfrozen slots.
- Test file location: `MGUI.Tests/Architecture/BrushFreezingPolicyTests.cs`, not `MGUI.Tests/Drawing/...` as the plan's literal path names -- same reasoning W1 already recorded (no `Drawing` folder exists in the test project; every other brush test already lives under `Architecture/`), kept for consistency rather than creating a one-file `Drawing/` folder for this slice alone.
- `BrushFreezingPolicyTests`'s completeness probe (`EnumerateReachableBrushes`) is a second, independently written reflection walk rather than a call into `MGTheme.FreezeThemeValue`/`FreezeThemeObjectGraph`: reusing the production walk to verify the production walk's own output would only prove the code is internally consistent with itself, not that it actually reaches every brush a theme can hold.
