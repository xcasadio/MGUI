# ADR-0010: XAML editor V1: text as the source of truth, loader source positions, separate MGUI.Editor library

- **Status**: Proposed
- **Date**: 2026-09-17
- **Source**: this chantier: the author's request of 2026-09-15 (a XAML editor with hot rendering, element selection without mouse manipulation, and a property grid whose changes edit the XAML node; a separate project of the MGUI solution that the CasaEngine editor can embed; `EditorRichTextBox` to evolve), a read-only discovery over five surfaces at HEAD `05de9ac`, the author's answers of 2026-09-17 to four grouped questions, a fresh-context review of the plan against the code (four reviewers, every blocking finding re-checked by a second agent) and two throwaway probes outside the repository. Plan: `Docs/Tasks/xaml-editor-tasks.md`. Target architecture: `Docs/editor-architecture.md`.

## Context

Facts verified at HEAD `05de9ac`:

- MGUI.Core targets the Windows framework only, which defines `UseWPF`, so `XAMLParser.cs` compiles its `using System.Xaml;` branch and the loader calls WPF's `System.Xaml.XamlServices.Parse`. The `Portable.Xaml` `#else` branch is compiled by no project today but must keep compiling.
- The loader (`XAMLParser.ParseDefinition`) prepares the markup and calls `XamlServices.Parse`. With `SanitizeXAMLString=true` the markup is trimmed, given namespaces and re-serialised with indentation, so positions in the prepared markup no longer match the source text. The samples are loaded unsanitized and declare their namespaces themselves. `ReplaceLinebreakLiterals` replaces the literal `\n` with `&#x0a;`, which shifts columns on the affected line only.
- Strict mode validates element and attribute names on an `XDocument` parsed with line info and reports `XamlLoaderDiagnostic` (code, message, line, column). No position reaches the DTO (`Element`) or the `MGElement`; the DTO is discarded after `ToElement`. Control templates and themes are loaded through `ParseObjectDefinition`, not `ParseDefinition`. A `ContentTemplate` declared in a document is cloned once per generated item.
- Probes (throwaway console projects, 2026-09-17): replacing `XamlServices.Parse` with a `XamlXmlReader` + `XamlObjectWriter` loop yields an identical object graph on eleven cases under `System.Xaml`, including three full sample files (73, 153 and 79 elements). The sequence of `StartObject` nodes whose type derives from `Element`, the sequence of `BeforePropertiesHandler` calls, and the document-order sequence of `XDocument` elements whose name resolves to a DTO have the same length and order. `BeforePropertiesHandler` fires once per instance on both libraries; `AfterBeginInitHandler` fires on Portable.Xaml only for `ISupportInitialize` instances, which the DTOs are not. Line numbers and positions are 1-based and the position points at the first character of the element name. An element materialised by a type converter (`Content="text"`) appears in none of the sequences. Every API of the loop exists under the same name in Portable.Xaml 0.26.0.
- `MGXAMLDesigner` (MGUI.Core) already renders XAML at runtime through `UIToolingService.LoadPreview`, from a plain `MGTextBox` or a watched file, shows a loader exception as text, and has no selection, no property grid and no link between an element and its markup.
- `MGRichTextBox.ApplyTextEdit` goes through `SetText`, which records no undo state, and the undo members of `MGTextBox` are private: a programmatic edit cannot be undone. `MGRichTextBox` normalises line endings to LF and raises no notification when the user moves the caret. Syntax highlighting is pluggable (`IRichTextSyntaxHighlighter`, underlined spans supported); there is no XAML tokenizer or highlighter.
- `MGPropertyGrid` reflects a CLR object or an `ICustomTypeDescriptor`, shows one value per row, silently drops a descriptor whose type is not `bool`, an integer, `float`, `double`, `string` or a colour type, and has no enum editor.
- There is no public hit test, but the runtime containment path (`ConvertCoordinateSpace`, `ToLocalUnscaledPoint`, `ContainsUnscaledInputPoint`) is reachable from `UIToolingService`; `IsComponent` / `ComponentParent` tell template parts from declared elements; adorners follow a target element and are layered as a z-ordered child of an `MGOverlayPanel`. `CaptureElementDebugView(...).ValueOrigins` covers five paths only (`Background`, `TextForeground` or `Foreground`, `BorderBrush`, `BorderThickness`, `Padding`).
- An `MGWindow` lays itself out at its own `Left` / `Top` and ignores the allocation of a presenter.
- The only MonoGame hosts are `MGUI.Samples` and `MGUI.MiniGame`; `MGUI.Tests` is the single test project. MGUI.Core's MonoGame package reference is private and does not flow to referencing projects; its built content does.

## Decision

1. **Projects.** The editor is a library, `MGUI.Editor` (Windows target framework; project reference to `MGUI.Core` only, plus a private `MonoGame.Framework.DesktopGL` package reference because MGUI.Core's public API is XNA-typed), and a thin executable, `MGUI.Editor.Host`, built on the `GameRenderHost` pattern of `MGUI.Samples/Game1.cs` so that native text input is wired. The CasaEngine editor embeds the library: a `XamlEditorSession` (document, design data context, diagnostics, selection) and a `XamlEditorView` (the composed UI). The view is built in code, not from embedded XAML. `MGUI.Tests` references `MGUI.Editor`; no second test project.
2. **The XAML text is the single source of truth.** There is no DTO-to-XAML serialiser. A property grid change is an attribute-level text edit (replace the value span, insert ` Name="value"` before the end of the start tag, or remove the attribute), applied through `MGRichTextBox.ApplyTextEdit`; everything else (preview, tree, grid) is recomputed from the text. The edited document is loaded unsanitized: it must declare its namespaces, like the sample files.
3. **Loader source positions.** `XAMLParser.ParseDefinition` replaces `XamlServices.Parse` with the equivalent reader/writer loop (line info forwarded to the writer, as `XamlServices.Transform` does), records the line info of every `StartObject` node whose type derives from `Element` and every `Element` instance seen by `BeforePropertiesHandler`, and, once the loop is over, assigns `XamlSourcePosition(SourceName, Ordinal, LineNumber, LinePosition)` to the k-th instance from the k-th recorded node (`SourceName` is `XamlDocumentSource.DisplayName`, the value already carried by `XamlLoaderDiagnostic.SourceName`). The code is shared by both compilation branches; `AfterBeginInitHandler` is not used. `ApplyBaseSettings` copies the position to `MGElement.Metadata` under a tooling key; `UIToolingService.TryGetXamlSourcePosition` reads it. `(SourceName, Ordinal)` identifies a document node, where `Ordinal` is the document-order rank among the XML elements that resolve to an `Element` DTO; the editor computes the same ordinal on its own `XDocument` through the new public `UIToolingService.TryResolveXamlElementType`. The relation is one node to N elements: a `ContentTemplate` declared in the document is deep-cloned per item and every cloned DTO keeps its own position, so the generated roots carry the position of the template content node and their descendants the position of their own node inside the template. Control template parts, theme content and converter-created elements carry no position. Because stamping happens after the loop, a divergence between the two counts stamps nothing at all: a missing position is acceptable, a wrong one is not.
4. **Preview.** The preview lives in the same desktop as the editor. It is a full re-parse in strict mode, debounced on the update loop (no thread), and it keeps the last valid root when the text does not load. A `Window` root is shown inside the preview pane: the host re-anchors it to the pane's top-left corner after each preview update and each change of the pane bounds, keeps the declared size, and lets the pane clip the overflow (no resize, no scroll in V1). The previewed subtree receives no input unless `IsInteractive` is set.
5. **Selection.** Selection is geometric: a new public `UIToolingService.HitTest(root, screenPoint)` returns the deepest visible element under a point, components included. It reuses the runtime containment path, so window scale, scroll origin, clipping and render transforms apply, it ignores `IsHitTestVisible`, and it knows nothing about source positions. The editor then walks up the `Parent` chain (which `AddComponent` also sets for components) to the first element carrying a position of the edited document, so template parts, their children and converter-created content all resolve to the declared node that owns them. There is no input capture layer and nothing is injected into the previewed tree. The tree view, the preview click and the caret all select the same document node; a bounds adorner marks one representative element; the selection persists across re-parses by ordinal. The caret-to-node direction is a poll of the public `MGRichTextBox.CaretIndex` on the editor window's update tick: V1 adds no caret event to MGUI.Core.
6. **Property grid.** The grid shows a proxy of the XAML node (`ICustomTypeDescriptor`), not the `MGElement`: one row per XAML-settable property of the DTO type. Every descriptor is string-typed in V1 (the attribute as written, empty meaning absent), because the grid drops descriptors of other types; the real DTO type is kept by the proxy and used to validate through the property's `TypeConverter` before any text edit. A read-only section lists the five runtime value origins exposed by `UIToolingService.CaptureElementDebugView`. `MGPropertyGrid` itself is unchanged.
7. **Text pane.** The XAML tokenizer and syntax highlighter are delivered in `MGUI.Core/UI/TextEditing/Xaml/` (tasks 3 and 7 of `Docs/Tasks/richtextbox-autocomplete-tasks.md`, delivered out of that file's order). Loader diagnostics are rendered as underlined spans at their line and column. `MGTextBox` gains a non-public undo hook and `MGRichTextBox.ApplyTextEdit` records an undo state: this is a behaviour change (a programmatic edit, completion acceptance included, becomes undoable).
8. **Design-time data.** `XamlEditorSession.DesignDataContext` is an injection point, null by default, passed to `LoadPreview`. No stub is generated from binding paths.
9. **Files.** File access lives in `MGUI.Editor`. The session text is always LF because the text pane normalises it; the original line ending and byte order mark of the file are session state, captured by `LoadFile` and restored by `Save`, so that an untouched file round-trips byte for byte.
10. **Removal of `MGXAMLDesigner`.** Once the editor is delivered and validated by the author, `MGXAMLDesigner`, its XAML DTO `XAMLDesigner`, `MGElementType.XAMLDesigner`, the sample `XAMLDesignerWindow` and the README paragraph with its image are deleted. This is a public API removal, decided by the author. The two architecture tests that read the designer source are renamed and retargeted to the editor's preview host, and the entry point of scenario `SCN-MARKUP-001` becomes the editor host.

Out of scope for V1: XAML completion (the remaining tasks of the RichTextBox backlog), typed grid editors (enum, vectors, colours: property grid backlog), mouse manipulation, drag and drop, multi-selection, node insertion or deletion from the tree, a preview rendered to a texture or in a second desktop, resizing or scrolling a `Window` root larger than the pane, source positions for control templates and themes, a line-number gutter, generated design data, and editing styles, resources or templates from the grid.

## Consequences

- MGUI.Core gains only generic, testable tooling: source positions on loaded elements, a public element-type resolver, a geometric hit test, a XAML tokenizer and highlighter, and undoable programmatic text edits. It gains no editor logic and no file access.
- Forwarding line info to the object writer also gives `XamlObjectWriterException` a line and a column, which the loader did not have before; diagnostics for conversion and setter failures become more precise.
- The document must be well-formed XML for selection and grid edits to work. While the text is invalid, highlighting and typing keep working, the last valid preview and document model stay in place, and the error is marked in the text.
- Every row of the grid is a string in V1, colours included. Typed editors plug in later through the property grid backlog without changing the text-edit path. The runtime section shows five value paths only; `Margin` and the other pilot paths need an MGUI.Core change that V1 does not make.
- The ordinal pairing depends on the XAML stack creating `Element` instances in `StartObject` order. The probes confirmed it on both libraries for every case tried; the plan still keeps it as an acceptance criterion with a stop condition, and the fallback on divergence is to stamp nothing.
- A re-parse rebuilds the previewed tree, so runtime state inside the preview (scroll offsets, checked states) is lost on each edit. This is accepted for V1.
- A `Window` root larger than the pane is clipped, not scaled; the clipped part may stay input-sensitive in interactive mode, and a `Window` root may not receive input at all as pane content. Both are recorded as known limits rather than blockers, since selection and editing do not need interactive mode.
- Caret synchronisation costs one integer comparison per update tick; an MGUI.Core caret event would replace the poll later.
- Consumers of `MGXAMLDesigner` lose it at the end of the program and must host `XamlEditorView` instead. Removing `MGElementType.XAMLDesigner` shifts the implicit values of the following members; the only numeric use in the repository is a relative-order assertion that the removal preserves.
- The replacement of `XamlServices.Parse` applies to element definitions only; themes and control templates keep the existing path.
