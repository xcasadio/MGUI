# ADR-0010: XAML editor V1: text as the source of truth, loader source positions, separate MGUI.Editor library

- **Status**: Proposed
- **Date**: 2026-09-17
- **Source**: this chantier: the author's request of 2026-09-15 (a XAML editor with hot rendering, element selection without mouse manipulation, and a property grid whose changes edit the XAML node; a separate project of the MGUI solution that the CasaEngine editor can embed; `EditorRichTextBox` to evolve), a read-only discovery over five surfaces at HEAD `05de9ac`, the author's answers of 2026-09-17 to four grouped questions, a fresh-context review of the plan against the code (four reviewers, every blocking finding re-checked by a second agent) and two throwaway probes outside the repository. Plan: `Docs/Tasks/xaml-editor-tasks.md`. Target architecture: `Docs/editor-architecture.md`.

## Context

Facts verified at HEAD `05de9ac`:

- MGUI.Core targets the Windows framework only, which defines `UseWPF`, so `XAMLParser.cs` compiles its `using System.Xaml;` branch and the loader calls WPF's `System.Xaml.XamlServices.Parse`. The `Portable.Xaml` `#else` branch is compiled by no project today but must keep compiling.
- The loader (`XAMLParser.ParseDefinition`) prepares the markup and calls `XamlServices.Parse`. With `SanitizeXAMLString=true` the markup is trimmed, given namespaces and re-serialised with indentation, so positions in the prepared markup no longer match the source text. The samples are loaded unsanitized and declare their namespaces themselves. `ReplaceLinebreakLiterals` replaces the literal `\n` with `&#x0a;`, which shifts columns on the affected line only.
- Strict mode validates element and attribute names on an `XDocument` parsed with line info and reports `XamlLoaderDiagnostic` (code, message, line, column). No position reaches the DTO (`Element`) or the `MGElement`; the DTO is discarded after `ToElement`. Control templates and themes are loaded through `ParseObjectDefinition`, not `ParseDefinition`. A `ContentTemplate` declared in a document is cloned once per generated item.
- Probes (throwaway console projects, 2026-09-17): replacing `XamlServices.Parse` with a `XamlXmlReader` + `XamlObjectWriter` loop yields an identical object graph on eleven cases under `System.Xaml`, including three full sample files (73, 153 and 79 elements). The sequence of `StartObject` nodes whose type derives from `Element`, the sequence of `BeforePropertiesHandler` calls, and the document-order sequence of `XDocument` elements whose name resolves to a DTO have the same length and order. `BeforePropertiesHandler` fires once per instance on both libraries; `AfterBeginInitHandler` fires on Portable.Xaml only for `ISupportInitialize` instances, which the DTOs are not. Line numbers and positions are 1-based and the position points at the first character of the element name. An element materialised by a type converter (`Content="text"`) appears in none of the sequences. Every API of the loop exists under the same name in Portable.Xaml 0.26.0.
- `MGXAMLDesigner` (MGUI.Core) already renders XAML at runtime through `UIToolingService.LoadPreview`, from a plain `MGTextBox` or a watched file, shows a loader exception as text, and has no selection, no property grid and no link between an element and its markup.
- `MGRichTextBox.ApplyTextEdit` goes through `SetText`, which records no undo state, and the undo members of `MGTextBox` are private: a programmatic edit cannot be undone. `MGRichTextBox` normalises line endings to LF and raises no notification when the user moves the caret. Syntax highlighting is pluggable (`IRichTextSyntaxHighlighter`, underlined spans supported); there is no XAML tokenizer or highlighter.
- `MGPropertyGrid` reflects a CLR object or an `ICustomTypeDescriptor`, shows one value per row, silently drops a descriptor whose type is not `bool`, an integer, `float`, `double`, `string` or a colour type, and has no enum editor.
- There is no public hit test, but the runtime containment path (`ConvertCoordinateSpace`, `ToLocalUnscaledPoint`, `ContainsUnscaledInputPoint`) is reachable from `UIToolingService`; `AddComponent` sets both `Parent` and `ComponentParent` on a component, so every element of a tree, components included, is reachable by walking `Parent`, while `ComponentParent` is null for the children of a part; adorners follow a target element and are layered as a z-ordered child of an `MGOverlayPanel`. `CaptureElementDebugView(...).ValueOrigins` covers five paths only (`Background`, `TextForeground` or `Foreground`, `BorderBrush`, `BorderThickness`, `Padding`).
- An `MGWindow` lays itself out at its own `Left` / `Top` and ignores the allocation of a presenter.
- The only MonoGame hosts are `MGUI.Samples` and `MGUI.MiniGame`; `MGUI.Tests` is the single test project. MGUI.Core's MonoGame package reference is private and does not flow to referencing projects; its built content does.

## Decision

1. **Projects.** The editor is a library, `MGUI.Editor` (Windows target framework; project reference to `MGUI.Core` only, plus a private `MonoGame.Framework.DesktopGL` package reference because MGUI.Core's public API is XNA-typed), and a thin executable, `MGUI.Editor.Host`, built on the `GameRenderHost` pattern of `MGUI.Samples/Game1.cs` so that native text input is wired. The CasaEngine editor embeds the library: a `XamlEditorSession` (document, design data context, diagnostics, selection) and a `XamlEditorView` (the composed UI). The view is built in code, not from embedded XAML. `MGUI.Tests` references `MGUI.Editor`; no second test project.
2. **The XAML text is the single source of truth.** There is no DTO-to-XAML serialiser. A property grid change is an attribute-level text edit (replace the value span, insert ` Name="value"` before the end of the start tag, or remove the attribute), applied through `MGRichTextBox.ApplyTextEdit`; everything else (preview, tree, grid) is recomputed from the text. The edited document is loaded unsanitized: it must declare its namespaces, like the sample files.
3. **Loader source positions.** `XAMLParser.ParseDefinition` replaces `XamlServices.Parse` with the equivalent reader/writer loop (line info forwarded to the writer, as `XamlServices.Transform` does), records the line info of every `StartObject` node whose type derives from `Element` and every `Element` instance seen by `BeforePropertiesHandler`, and, once the loop is over, assigns `XamlSourcePosition(SourceName, Ordinal, LineNumber, LinePosition)` to the k-th instance from the k-th recorded node (`SourceName` is `XamlDocumentSource.DisplayName`, the value already carried by `XamlLoaderDiagnostic.SourceName`). The code is shared by both compilation branches; `AfterBeginInitHandler` is not used. `ApplyBaseSettings` copies the position to `MGElement.Metadata` under a tooling key; `UIToolingService.TryGetXamlSourcePosition` reads it. `(SourceName, Ordinal)` identifies a document node, where `Ordinal` is the document-order rank among the XML elements that resolve to an `Element` DTO; the editor computes the same ordinal on its own `XDocument` through the new public `UIToolingService.TryResolveXamlElementType`. The relation is one node to N elements: a `ContentTemplate` declared in the document is deep-cloned per item and every cloned DTO keeps its own position, so the generated roots carry the position of the template content node and their descendants the position of their own node inside the template. Control template parts, theme content and converter-created elements carry no position. Because stamping happens after the loop, a divergence between the two counts stamps nothing at all: a missing position is acceptable, a wrong one is not.
4. **Preview.** The preview lives in the same desktop as the editor. It is a full re-parse in strict mode, debounced on the update loop (no thread), and it keeps the last valid root when the text does not load. A `Window` root is shown inside the preview pane: the host re-anchors it to the pane's top-left corner after each preview update and each change of the pane bounds, keeps the declared size, and lets the pane clip the overflow (no resize, no scroll in V1). The previewed subtree receives no input unless `IsInteractive` is set.
5. **Selection.** Selection is geometric: a new public `UIToolingService.HitTest(root, screenPoint)` returns the deepest visible element under a point, components included. It reuses the runtime containment path, so window scale, scroll origin, clipping and render transforms apply, it ignores `IsHitTestVisible`, and it knows nothing about source positions. The editor then walks up the `Parent` chain (which `AddComponent` also sets for components) to the first element carrying a position of the edited document, so template parts, their children and converter-created content all resolve to the declared node that owns them. There is no input capture layer and nothing is injected into the previewed tree. The tree view, the preview click and the caret all select the same document node; a bounds adorner marks one representative element; the selection persists across re-parses by ordinal. The caret-to-node direction is a poll of the public `MGRichTextBox.CaretIndex` on the editor window's update tick: V1 adds no caret event to MGUI.Core.
6. **Property grid.** The grid shows a proxy of the XAML node (`ICustomTypeDescriptor`), not the `MGElement`: one row per XAML-settable property of the DTO type. Every descriptor is string-typed in V1 (the attribute as written, empty meaning absent), because the grid drops descriptors of other types; the real DTO type is kept by the proxy and used to validate through the property's `TypeConverter` before any text edit. A read-only section lists the five runtime value origins exposed by `UIToolingService.CaptureElementDebugView`. `MGPropertyGrid` itself is unchanged.
7. **Text pane.** The XAML tokenizer and syntax highlighter are delivered in `MGUI.Core/UI/TextEditing/Xaml/` (tasks 3 and 7 of `Docs/Tasks/richtextbox-autocomplete-tasks.md`, delivered out of that file's order). Loader diagnostics are rendered as underlined spans at their line and column. `MGTextBox` gains a non-public undo hook and `MGRichTextBox.ApplyTextEdit` records an undo state: this is a behaviour change (a programmatic edit, completion acceptance included, becomes undoable).
8. **Design-time data.** `XamlEditorSession.DesignDataContext` is an injection point, null by default, passed to `LoadPreview`. No stub is generated from binding paths.
9. **Files.** File access lives in `MGUI.Editor`. The session text is always LF because the text pane normalises it; the original line ending and byte order mark of the file are session state, captured by `LoadFile` and restored by `Save`, so that an untouched file round-trips byte for byte.
10. **Removal of `MGXAMLDesigner`.** Once the editor is delivered and validated by the author, `MGXAMLDesigner`, its XAML DTO `XAMLDesigner`, `MGElementType.XAMLDesigner`, the sample `XAMLDesignerWindow` and the README paragraph with its image are deleted. This is a public API removal, decided by the author. The two architecture tests that read the designer source are renamed and retargeted to the editor's preview host, and the entry point of scenario `SCN-MARKUP-001` becomes the editor host.

Out of scope for V1: XAML completion (the remaining tasks of the RichTextBox backlog), typed grid editors (enum, vectors, colours: property grid backlog), mouse manipulation, drag and drop, multi-selection, node insertion or deletion from the tree, a preview rendered to a texture or in a second desktop, resizing or scrolling a `Window` root larger than the pane, source positions for control templates and themes, a line-number gutter, generated design data, and editing styles, resources or templates from the grid.

## Consequences

- MGUI.Core gains only generic, testable tooling: source positions on loaded elements, a public element-type resolver, a geometric hit test, a XAML tokenizer and highlighter, and undoable programmatic text edits. It gains no editor logic and no file access.
- Forwarding line info to the object writer also gives `XamlObjectWriterException` a line and a column, which the loader did not have before; diagnostics for conversion and setter failures become more precise.
- The document must be well-formed XML for selection and grid edits to work. While the text is invalid, highlighting and typing keep working, the last valid preview and document model stay in place, and the error is marked in the text.
- Every row of the grid is a string in V1, colours included. Typed editors plug in later through the property grid backlog without changing the text-edit path. The runtime section shows five value paths only; `Margin` and the other pilot paths need an MGUI.Core change that V1 does not make.
- The ordinal pairing depends on the XAML stack creating `Element` instances in `StartObject` order. The probes confirmed it on both libraries for every case tried; the plan still keeps it as an acceptance criterion with a stop condition, and the fallback on divergence is to stamp nothing.
- A re-parse rebuilds the previewed tree, so runtime state inside the preview (scroll offsets, checked states) is lost on each edit. This is accepted for V1.
- A `Window` root larger than the pane is clipped, not scaled; the clipped part may stay input-sensitive in interactive mode, and a `Window` root may not receive input at all as pane content. Both are recorded as known limits rather than blockers, since selection and editing do not need interactive mode.
- Caret synchronisation costs one integer comparison per update tick; an MGUI.Core caret event would replace the poll later.
- Consumers of `MGXAMLDesigner` lose it at the end of the program and must host `XamlEditorView` instead. Removing `MGElementType.XAMLDesigner` shifts the implicit values of the following members; the only numeric use in the repository is a relative-order assertion that the removal preserves.
- The replacement of `XamlServices.Parse` applies to element definitions only; themes and control templates keep the existing path.

## Decisions taken during delivery

Each slice of the plan appends its decisions here.

- **X0, author, 2026-09-17: shape of `XamlEditorView`.** (The `Root` grid described here is superseded by the X1b decision below; the composing-class shape stands.) It is a composing class, not an `MGElement`: `XamlEditorView(MGWindow window, XamlEditorSession session)` builds the tree against the hosting window and exposes `Root` (the three-column grid) and the four panes. A host calls `window.SetContent(view.Root)`; a docking host returns `view.Root` from `DockableDefinition.ContentFactory`, whose element is created against the hosting window. Rejected: an `MGElement` subclass typed `MGElementType.Custom` (abstract layout and drawing members to implement for a plain composition) and a view that owns its own `MGWindow` (not embeddable in a dock pane).
- **X0, author, 2026-09-17: editor window of `MGUI.Editor.Host`.** A chrome-less `MGWindow` that covers the whole client area and follows the size of the game window (initial size 1600 x 900, as `Game1`). From X7 the file name and the dirty state go to the title of the game window (`Game.Window.Title`).
- **X0, 2026-09-17: `XamlEditorSession.SourceName` default format.** `"untitled-" + Guid.NewGuid().ToString("N") + ".xaml"`, generated once per instance at construction. Guarantees uniqueness across sessions without touching the file system and needs no counter or registry to stay collision-free. `XamlDocumentSource.FromString(markup, displayName)` takes it as a plain display name and imposes no format.
- **X0, 2026-09-17: editor tests reuse `GraphTestRuntime`.** `MGUI.Tests/Editor/XamlEditorViewTests.cs` builds its headless desktop with the shared `GraphTestRuntime` (`MGUI.Tests/Graph/GraphTestRuntime.cs`), the same runtime used by `ScrollViewerLayoutTests` for a `MGWindow`/`MGGrid` layout under test. Rejected: a dedicated `XamlEditorTestRuntime` (as `PropertyGridTests.cs` uses its own `PropertyGridTestRuntime`), unnecessary here since the view under test needs no runtime behaviour beyond what `GraphTestRuntime` already provides.
- **X0, 2026-09-17: `XamlEditorView`'s splitter columns.** (Superseded by the X1b decision below: the grid and its splitters are gone.) Each `MGGridSplitter` sits alone in its own pixel-length column, sized `GridLength.CreatePixelLength(12)` to match `MGGridSplitter.Size`'s default (`MGGridSplitter.cs`); the three content columns are weighted (`GridLength.CreateWeightedLength(1)`), following the pattern in `MGUI.Samples/Dialogs/Debugging/Debug1.xaml`'s commented-out `ColumnLengths="1*[50,150],16,1.5*[50,60],1.2*"` sample, which likewise gives the splitter its own fixed-width column between weighted content columns.
- **X1, 2026-09-17: line info is forwarded to the writer (first dropped, then restored).** The first X1 commit (`5e06b3b`) captured line info on the reader but did not push it onto the `XamlObjectWriter`, blaming the forwarding for two failures in `XamlAnimationTests`. A fresh-context verification could not reproduce that reason: those tests assert substrings of the inner exception's message, which forwarding does not change; the failures came from disposing the writer in a `finally` (next bullet). The follow-up fix restores the forwarding exactly as `XamlServices.Transform` does (`IXamlLineInfo.HasLineInfo`, `IXamlLineInfoConsumer.ShouldProvideLineInfo` and `SetLineInfo` before each `WriteNode`; the same names exist in Portable.Xaml 0.26), with no existing test modified. Measured behaviour, covered by `XamlLoaderLineInfoTests`: for a failure raised by the writer (a value that cannot be converted, a setter that throws, a malformed `Thickness`), the reported position is 1-based, the line is the line on which the failing attribute is written (the attribute's own line in a multi-line start tag, not the line of the element's start tag) and the column is the first character of that attribute's name; it is expressed in the prepared markup, so each literal `\n` earlier on the same line shifts it by four columns. In compatibility mode the raw `XamlObjectWriterException` now carries a non-zero `LineNumber` and its own message gains the line and position, the behaviour change announced in the Consequences above.
- **X1, 2026-09-17: known limit outside the slice, diagnostic codes depend on the machine's language.** `XamlLoaderDiagnostics.Classify` picks a `XamlLoaderDiagnosticCode` by looking for English words in exception messages. Only `System.Xaml` messages are localised (the .NET base library stays in English), and `Width="abc"` is reported as `ParseFailure` rather than `InvalidValueConversion` in every language, because no keyword matches. Pre-existing, not changed by this program; the new tests assert positions, not the code, for those cases. Lifted: `4b51ca6` (branch `fix/xaml-diagnostics-culture`) classifies diagnostics without reading localised messages and reached this branch with the merge of `develop` on 2026-09-18, so `Width="abc"` is reported as `InvalidValueConversion` in every language and X3 can show the code as is.
- **X1, 2026-09-17: the writer is disposed only after a successful loop.** Disposing a `System.Xaml.XamlObjectWriter` that failed mid-write throws its own `XamlObjectWriterException` ("XAML node stream: CurrentObject missing before EndObject"); thrown from a `finally` block while the real failure (for example the `Transition.Property` setter's `InvalidOperationException`) is already unwinding, it silently replaces that real failure, which broke the same two tests above with an unrelated message. `ParseWithSourcePositions` therefore disposes the reader and the writer only on the path that returns a result, never in a `finally`; only the `StringReader` (whose `Dispose()` never throws) is disposed unconditionally. `XamlServices.Parse` sidesteps the same trap by never disposing its writer at all.
- **X1, 2026-09-17: `SourcePosition` cannot be set from markup.** `Element.SourcePosition`'s setter is `internal`. An XML attribute named `SourcePosition` therefore resolves, through the loader's own member lookup, to no writable public member of the DTO -- the same failure any other unknown attribute name produces (an `XamlObjectWriterException`/`XamlLoaderException` at parse time), never a silent no-op and never a value that reaches the DTO. Covered by `XamlSourcePositionTests.SourcePosition_CannotBeSetFromMarkup`.
- **X1, 2026-09-17: `UIToolingService.TryResolveXamlElementType` is the sole definition of "counts for the ordinal".** It wraps the loader's internal `XAMLParser.ResolveElementType` (alias resolution included) and returns `true` only when the resolved type derives from `Element`; a name that resolves to a non-`Element` DTO (`Style`, `Setter`, a brush, `ContentTemplate`) or that does not resolve at all returns `false` with a null `dtoType`. Both the loader's `Ordinal` and `MGUI.Editor.Document.XamlDocumentNode.DtoType`/`.Ordinal` are computed from this one method, which is what makes the two ordinals agree by construction rather than by coincidence (`XamlSourcePositionTests.LoaderOrdinal_And_DocumentModelOrdinal_AgreeOnTheSameNodes_*`).
- **X1, 2026-09-17: `XamlDocumentModel`'s tag ranges come from one raw-text scan, not a second `XmlReader` pass.** `XDocument` (with `LoadOptions.SetLineInfo | LoadOptions.PreserveWhitespace`) gives every element's and attribute's *start* position and the attribute's decoded value, but never an end-tag position. Rather than replaying a second `System.Xml.XmlReader` pass to recover `EndElement` positions, `XamlDocumentModel` walks the already-known-well-formed text once with a small hand-written scanner: it tracks quote state (so a literal `>` inside a quoted attribute value, legal in XML, never closes a start tag early), skips comments/CDATA/processing instructions outright, and matches end tags to the innermost open start tag with a plain stack -- correct even for nested elements sharing a local name. The scanner visits nodes in the same document order `XDocument`'s own recursive walk already built them in, so the two lists are paired by a simple running cursor. Attribute name/value ranges and the quote character are found the same way, by scanning forward from the attribute's known start position (`IXmlLineInfo`) to the next `=`, quote, and matching closing quote.
- **X1b, author, 2026-09-17: the editor shell is hosted by the docking manager.** The author asked for MGUI's docking manager instead of the fixed grid of X0. `XamlEditorView` stays a composing class but no longer builds a grid: it builds five panes without a parent (text, preview with its presenter, document tree, property grid, diagnostics placeholder) and exposes five `DockableDefinition` (`xaml-editor.text`, `.preview`, `.tree`, `.properties`, `.diagnostics`) whose content factories return those panes, plus `CreateDockHost()`, which returns an `MGDockHost` with a registry and a private default layout. A plain host calls `window.SetContent(view.CreateDockHost())`; a docking host such as the CasaEngine editor registers `Dockables` in its own `MGDockHost`, so there is no nested docking. V1 choices: panes are not closable (no "View" menu to reopen one), auto-hide is allowed, every pane may float except the preview, the diagnostics list is a fifth dockable, layout persistence and layout reset are out of V1. Facts that shaped it, all checked in the code by three fresh-context reviews of the slice: a dockable registry only sees a panel as visible after `MGDockHost.RegisterPanel`, and its `OnHidden` event is never raised while `OnActivated` covers neither floating windows nor auto-hide drawers, so the editor relies on `MGElement.OnParentChanged` instead; the content of an inactive tab or of a closed auto-hide drawer is detached (`Parent == null`) and keeps stale bounds; the name index of an `MGWindow` is fed only by the `MGContentHost` add/remove chain, which dock tab groups bypass, and a duplicate key throws during a dock host rebuild, so editor panes carry no `Name` and are reached through the view's properties; a previewed `Window` root is a nested window of the editor window, so floating the preview pane would require moving it between parent windows, which V1 does not do; a floated panel used to re-dock as a tab of the first visible group because its emptied source group was removed; since the merge of `develop` on 2026-09-18 (placeholder groups, ADR-0012) the emptied group is kept and the panel returns to its exact place.
- **X1b, 2026-09-17: delivery choices and docking behaviours the editor must live with.** `CreateDockHost()` assigns the registry, then `LayoutModel = new DockLayoutModel(root)`, then calls `RegisterPanel` once per panel (the registry only becomes aware of the panels at that last step, so the order of the first two does not matter); a second call on the same view throws `InvalidOperationException`, because the pane instances are shared and two hosts would fight over their `Parent`. The five dockables keep `DockableType.Tool`, the default: nothing exercised today branches on it, but `DockableDefinition` documents that tools only tab with tools, so the pane titled "Document" is a tool pane, not a document of a future document area. Measured on a tab switch: `DockTabGroupNode` raises two property notifications per change, so the pane that becomes inactive gets one `OnParentChanged` (detach) while the pane that becomes active gets three (attach, then a redundant detach and re-attach): any handler the editor hangs on `OnParentChanged` must be idempotent and must read the final `Parent`. Measured on float and re-dock at delivery time: every cycle sent the panel to the first visible group, so repeating it on several panes progressively collapsed the layout into a single tab group, without any exception or error placeholder. ADR-0012's placeholder groups, merged from `develop` on 2026-09-18, fix that: a probe on the editor's own layout shows "Properties" returning to its original group with identical bounds after a float and re-dock. Both behaviours belong to MGUI.Core's docking manager and are not changed by this program.
- **X1b, author, 2026-09-17: the host runs with the Dark theme and FontStashSharp.** At the author's request, `MGUI.Editor.Host` references `MGUI.FontStashSharp` and, right after `LoadDefaultResources` and before creating its editor window, sets `Desktop.Resources.DefaultTheme = new MGTheme(MGTheme.BuiltInTheme.Dark, Desktop.DefaultFontFamily)` and makes a `FontStashSharpTextEngine` the desktop's text engine, following `MGUI.Samples/Game1.cs`: Normal (with the `byte[]` overload), Bold and Italic from `Content/Fonts/ttf` (`arial.ttf`, `arialbd.ttf`, `ariali.ttf`), then `MatchSpriteFontSizing` against the renderer's `FontManager`. The registered family is read from `Desktop.DefaultFontFamily` ("Arial") rather than written as a literal, so it cannot drift from the family the theme and the controls ask for; bold-italic text resolves to Arial Normal because only three styles are loaded, as in `Game1`. If the setup throws, the reason goes to the debug output and the renderer's SpriteFont engine stays in place: the editor still starts. Both assignments happen before any element exists, because changing the theme of existing elements triggers known pre-existing defects. The library `MGUI.Editor` sets neither a theme nor a text engine: those are host choices, and the CasaEngine editor makes its own. A headless probe confirmed that, with the Dark theme, the dock tab items, splitters, auto-hide strips and drawer and the drop indicators take their `Dark.*` templates (it checked template names, not painted colours, and so missed the defect of the next bullet); `MGDockHost`, `MGDockTabGroup` and `MGDockPreviewOverlay` have no Dark mapping in `BuiltInThemes.xaml` and keep their default templates, which read the theme's docking colours. Fonts: the repository tracks only the four Arial files of `MGUI.Core/Content/Fonts/ttf`; JetBrains Mono, Tahoma and Arial Narrow files found in local output folders come from stale, untracked intermediate content and are not used, so a monospace font for the XAML pane remains a follow-up.
- **X1b, author, 2026-09-17: the chrome-less editor window gets the theme's window background.** At the first launch with the Dark theme the author saw the game's clear colour (cornflower blue) in the Preview and Diagnostics panes and in every tab strip. Cause: `WindowStyle.None` makes a window's background transparent by design (`MGWindow.MakeBackgroundChromeless`, meant for HUD-like windows that paint their own content background), and the dock tab groups, the preview pane (`MGOverlayPanel`) and the diagnostics pane (`MGContentPresenter`) paint no background of their own; the docking sample does not show it because its window uses `WindowStyle.Default`, whose opaque theme background sits behind those areas. Decision of the author: fix it in the host only. `MGUI.Editor.Host` assigns `Window.BackgroundBrush = Desktop.Theme.GetBackgroundBrush(MGElementType.Window)` right after making the window chrome-less; a whole-container local write removes the transparent local sub-slots written by `WindowStyle.None` (rule R1 of `MGElement.SetBackground`), and a background written while chrome-less is kept (`ResolvedBackgroundPilotTests`). A probe outside the repository replicating the host sequence gives a transparent background in the four states without the line, and rgb(30,30,30) with it, identical to a standard Dark window, also after a resize. `MGWindow`'s chrome-less behaviour is unchanged. The library stays theme-neutral: a host that embeds the editor panes in a transparent window must provide an opaque background itself.
- **X2, 2026-09-18: the preview host lives on the editor window's update tick.** `XamlPreviewHost(XamlEditorView view)` subscribes, in its constructor, to the session's `TextChanged` and `DesignDataContextChanged` (each marks the document dirty) and to `MGWindow.OnBeginUpdate` on the editor window, which is the only clock: the debounce compares the tick's `UpdateBaseArgs.TotalElapsed` with the time of the last request, so a burst of edits produces exactly one re-parse and no thread or system timer exists anywhere in `MGUI.Editor`. `OnBeginUpdate` rather than `OnEndUpdate` because an `MGWindow` lays itself out inside its own begin-update handler: a root anchored there is laid out in the same frame. `XamlEditorView` only gains a `PreviewHost` property and one construction line.
- **X2, 2026-09-18: anchoring and hidden panes are polled, not evented.** Every tick the host compares the preview pane's `LayoutBounds` with the last anchored value and its `Parent` with null, instead of subscribing to `OnParentChanged`. Polling the final state is naturally idempotent, which the three `OnParentChanged` events a re-activated pane receives (X1b) would otherwise make delicate. A `Window` root is re-anchored with `Left`/`Top`, then `QueueLayoutRefresh = true` and `ValidateWindowSizeAndPosition()`, because the position setters alone do not invalidate layout; the anchor memory is cleared on every root replacement. Measured by a probe outside the repository: the root's top-left corner follows the pane through an editor window move, a docking splitter drag and a hidden-then-reactivated tab, while `Left` and `Top` declared in the document never place it and its declared size never changes.
- **X2, 2026-09-18: a failure never breaks the editor, and the root keeps the visibility the document declared.** A `XamlLoaderException` keeps the previous root displayed and publishes its diagnostic; any other exception (the loader wraps only failures raised while parsing the markup, not those raised while instantiating the elements) is caught too and published as a `ParseFailure` diagnostic, since a text the user typed must never crash the editor. `PreviewVersion` counts every completed cycle, including a failed one and an empty text, which is what the debounce tests count. While the pane is detached the root is `Hidden`; when the pane comes back the root returns to the visibility the document declared, not to `Visible` (a fresh review found the forced `Visible`; the main session fixed it and proved the fix by mutation).
- **X2, author, 2026-09-18: the previewed window keeps the position its document declares.** The slice shipped what decision 4 said -- a `Window` root pinned to the pane's corner, its `Left` and `Top` ignored -- and the author asked for the opposite once he saw it: the pane's corner is the preview's origin, and the window sits at its declared offset from that corner, the way it would sit at that offset from the corner of a desktop. The host keeps the declared `Left`/`Top` at load (anchoring overwrites them) and adds the same offset to the presenter's margin, so the presenter's clip, which is what keeps the preview inside the pane, still covers the window where it now sits; the margin is cleared when the next root is not a window, a stale offset the tests caught. Measured: a window declared `Left="50" Top="20"` is laid out 50 and 20 pixels from the pane's corner, keeps that offset when the editor window moves and when the pane is resized, and a document with no `Left`/`Top`, like a root that is not a window, sits exactly on the corner.
- **X2, author, 2026-09-18: the preview stays faithful to the document, even when that hides things.** Two questions raised once the offset worked, both answered "leave it as it is": a root whose declared `Left`/`Top` carries it out of the pane is not brought back, so it can be partly or entirely invisible until the document or the pane changes; and a `Window` root keeps the chrome its style gives it (title bar, close button), because that is what the document describes and what the running application would show. Neither is a defect to fix later: they are the preview's contract. The known-limits list of the architecture page records both.
- **X3, 2026-09-18: one palette, extended, and stable classifications.** `MGRichTextSyntaxPalette` gains `ElementName`, `AttributeName`, `Punctuation` and `MarkupExtension`; `String` and `Comment` are reused. Additive only: nothing renamed or removed, `Default` unchanged, the C# highlighter's own tests still green. A dedicated XAML palette type was rejected because `MGRichTextBox` exposes a single `SyntaxPalette` property, so a second type would mean a second property on a public control. Every span carries a stable lowercase classification (`xaml.element-name`, `xaml.attribute-name`, `xaml.punctuation`, `xaml.string`, `xaml.comment`, `xaml.markup-extension`, plus `xaml.diagnostic` for an underline on text the highlighter left plain), which a later slice can look for.
- **X3, 2026-09-18: error markers are a decorator, because a text box holds one highlighter.** `XamlEditorTextPane` gives the text pane a decorator that calls `XamlSyntaxHighlighter` and then adds the diagnostics' underlines, echoing `context.Version` so a stale result is still discarded. `MGRichTextBox` does not merge overlapping spans -- it clips a later one to nothing -- so the decorator splits the existing spans at each underline boundary and merges with `MGRichTextStyle.MergeOver` (the diagnostic style sets no foreground, so the token keeps its colour and only gains the underline), leaving a flat, non-overlapping list. A diagnostic's index comes from `new MGTextPosition(LineNumber - 1, LinePosition - 1 - correction)` then `MGTextBuffer.TryGetIndex`, where `correction` counts four columns per literal `\n` earlier on that line; the span covers the token starting there, or the rest of the line. A diagnostic with no line or column, or one whose position falls outside the current text, underlines nothing and never throws -- the second case really happens, because the pane's text changes at once while the diagnostics only refresh on the debounced preview update.
- **X3, 2026-09-18: a programmatic edit is undoable, and so is a completion.** `MGTextBox` gains `private protected void PushUndoState()`, which reuses the existing private machinery, and `MGRichTextBox.ApplyTextEdit` calls it before applying the edit. `TryUndo` therefore restores the text and the caret of an edit made from code, which slice X6 needs for the property grid. Since completion acceptance goes through `ApplyTextEdit`, accepting a completion became undoable too: that is the behaviour change the plan announced, covered by a test. Unchanged and out of scope: typing or deleting a single character without a selection still records no undo state at all.
- **X3, 2026-09-18: the diagnostics list and what a click does.** `DiagnosticsPane` holds an `MGListBox<XamlLoaderDiagnostic>` refreshed on `PreviewUpdated`; selecting an entry moves the caret to the diagnostic's index and focuses the text pane, but does not activate the "XAML" dockable when that pane is an inactive tab or in a closed drawer, since the view does not own the dock host (X1b). The caret is simply set and is where the user left it when the pane comes back. The sample's XAML mode has no completion, because no XAML completion provider exists yet (task 6 of the RichTextBox backlog).
- **X2, 2026-09-18: the preview presenter never stretches its content.** The author's second run showed a `Window` root declared 200 x 100 filling the whole pane. Cause: the presenter stretched, so it allocated the pane's whole surface to the root, and an `MGWindow` (whose own alignment is forced to `Stretch`, and which is laid out by its parent when it is content rather than a desktop or nested window) took that allocation instead of its declared size -- `WindowWidth` and `WindowHeight` still read 200 x 100, which is why the slice's own test, written on those properties, passed. `PreviewPresenter` is now aligned Left/Top, so the pane allocates what the presenter asks for and the presenter asks for the root's own size. Measured outside the repository: a 200 x 100 root is laid out 200 x 100 at the pane's corner, a 500 x 800 root keeps its size in a 630 x 668 pane and overflows into the pane's clip, and a plain element root (not a `Window`) is shown at its natural size at the same corner instead of being stretched. The test now asserts `LayoutBounds`, not the window properties, and fails when the alignment goes back to `Stretch`.
- **X2, 2026-09-18: the text pane holds the session's text.** The author's first run showed nothing: typing in the "XAML" pane rendered no preview, because no slice had ever said who writes `XamlEditorSession.Text`. `XamlEditorView` now binds the two, both ways, behind one re-entrancy flag: a keystroke in `TextPane` writes `Session.Text` (the value the preview, and later the document model and the diagnostics, work from), and writing `Session.Text` from code -- opening a file in X7, an attribute edit from the grid in X6 -- writes the pane back. `MGRichTextBox` normalises line endings to LF, so the session's text is always LF, as the architecture page already required. A session whose text is set before the view exists reaches the pane and asks for a first render, which also lifts the "no initial refresh" limit noted the same day. Proven by mutation: with the binding removed, the three tests that type into the pane, write the session and pre-fill it all fail.
- **X2, 2026-09-18: known limit carried forward.** An oversized root is expected to be clipped by the presenter's own draw-time clip rather than by any new mechanism; that reasoning is not covered by a headless test, since the test runtime draws through a no-op transaction, and is confirmed by the author's manual pass.
