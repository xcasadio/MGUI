# ADR-0036: The dock host keeps one drop target

- **Status**: Accepted
- **Date**: 2026-11-16
- **Source**: CasaEngine plan `ai-agent/tasks/mgui-nonalloc-suite-tasks.md`, decision D18 (open point O11), recommended by the agent and decided on 2026-11-16, task T5.7

## Context

During a tab drag, `MGDockHost` computes the drop target under the mouse each time the mouse has moved 5 pixels (`UpdateDragPreview`). Read in the code and measured on 2026-11-16:

- `DockDropTarget` is a public class with eight public settable fields: `TargetNode`, `Zone`, `HitRect`, `PreviewRect`, `TabIndex` (-1 unless computed), `IsHostEdge`, `IsSplitterDrop` and `SplitterNode`. It has no value equality. `MGDockHost.CurrentDropTarget` is public, with a private setter that raised `PropertyChanged` when the reference changed.
- Every computation made a new object: `DockDropCalculator` created the five zones of a group (`CalculateDropZones`, a list and five targets) or the four edges of the host (`CalculateHostEdgeZones`), and the host created the centre target (`GetDropTargetForZone`) and the reorder target (`GetDropTarget`). Measured over the drag, per frame of update (draw is 0): the centre of another group 80 B, a split zone, the proximity band and a splitter bar 576 B, a host edge 408 B, the centre of the group of the dragged tab 480 B (a split zone computes a list and five targets; the reorder case also allocates in the LINQ of the tab index and of the preview line, below).
- Not every field is written by the code that creates the target: the calculator fills `TargetNode`, `Zone`, `HitRect` and `PreviewRect` only, and the host writes `IsSplitterDrop` and `SplitterNode` afterwards on the object it got for a splitter bar, and `TabIndex` (and `PreviewRect`) on a centre or a reorder target. The other fields have their default (`TabIndex` -1, `IsHostEdge` false, `IsSplitterDrop` false, `SplitterNode` null) only because every target was a new object. A target that is filled again must write all eight fields, or a field written after the last fill survives into the next one.
- `CalculateTabIndex` and `CalculateTabReorderPreviewRect` (called for a centre target during a drag, and for the reorder target) walked the tab items with `GetChildren().FirstOrDefault()`, `GetChildren().OfType<>().ToList()`: 400 B per frame over the centre of the group of the dragged tab.
- Readers and keepers, searched in both repositories (MGUI, `CasaEngine`, `CasaEngine.Editor`, `CasaEngine.EditorServices`, the demos and the tests): outside `MGDockHost`, `DockDropCalculator` and `DockDropTarget`, no code reads `CurrentDropTarget`, calls `GetDropTarget`, uses `DockDropTarget` or `DockDropCalculator`, or subscribes to `PropertyChanged` of an `MGDockHost`. The only readers are the tests of `MGUI.Tests` (`CurrentDropTarget.Zone` after a drag, `CalculateHostEdgeZones` in `DockPlaceholderGroupHostTests`), which read the value at once. Nothing keeps a `DockDropTarget` beyond a call: no field, collection or closure of the type. `MGDockHost.PerformDrop` reads `CurrentDropTarget` once and passes it to `ExecuteDrop`, then `EndDrag` sets it to none. (`DragDropManager.CurrentDropTarget` is another property, of `MGElement`.)

## Decision

`MGDockHost` keeps one `DockDropTarget` for `CurrentDropTarget`. Its values are written again at each computation, and `PropertyChanged` is raised only when a value changes or when the target appears or disappears.

- `CurrentDropTarget` is null, or the one instance that the host keeps. A computation copies the eight fields of the target it found into that instance. When there is no target the property becomes null and the fields of the instance are left as they were (a drop that is being applied still reads them).
- `PropertyChanged` for `CurrentDropTarget` is raised when the property goes from null to a target, from a target to null, and when a field of the target changes (references of nodes compared by reference, rectangles by value). It is not raised when a computation finds the same eight values. Before, it was raised each time the reference changed, that is at every computation.
- `GetDropTarget(Point)` returns that same instance (or null), as it also sets `CurrentDropTarget`.
- Lifetime of what a caller reads: the instance keeps its identity for the life of the host, and its fields are the target of the last computation. A caller that needs a target after the next computation (the next mouse move of a drag, the next call of `GetDropTarget`) copies the fields it needs. A reference kept from before a target disappeared still shows the last values.
- Every fill of a kept target writes all eight fields as a new object would have them (`DockDropTarget.Set`, internal): `TargetNode`, `Zone`, `HitRect`, `PreviewRect`, `TabIndex` at -1 unless the caller computes it, `IsHostEdge` false (true for the host edges), `IsSplitterDrop` false and `SplitterNode` null (written by the host for a splitter bar, after the fill). This applies to the calculator slots, the centre target, the reorder target and the instance of `CurrentDropTarget`.
- The zone lists of the calculator are kept by the host and filled by two new internal overloads, `DockDropCalculator.CalculateDropZonesInto` and `CalculateHostEdgeZonesInto` (they reuse the targets the list already holds, create the missing ones and trim the list to the zones of the call). The public static `CalculateDropZones` and `CalculateHostEdgeZones` keep their signatures and results; they call the overloads with a new list.
- `ExecuteDrop` reads the zone, the tab index, the host-edge flag and the target node of the target once at its start, so that nothing that runs during the drop can change what is applied.
- Needed for the drag to allocate nothing over the reorder case: the walk of the tab items of `CalculateTabIndex` and `CalculateTabReorderPreviewRect` uses `AddChildrenTo` into a list that the host keeps (new internal overloads taking the list; the public methods keep their signatures and results and use a new list). The tab items found are the same, in the same order.

## Consequences

- Observable behavior change: two computations that find the same target no longer give two objects and two notifications, and a reference to `CurrentDropTarget` taken earlier shows the later targets. External code that kept a target for later must copy its fields; a subscriber that relied on one notification per computation (for example to follow the mouse) now gets one per change of value. The two repositories have no such code (see Context).
- Public API: `CurrentDropTarget` loses its private setter (a getter only, as seen by callers); `DockDropTarget`, `DockDropCalculator`, `GetDropTarget` and the public static calculator methods keep their signatures; the new members are internal. `GetDropTarget` and `CurrentDropTarget` return the same object at each call instead of a new one.
- Measured after the change, per frame of update and of draw over the drag, the mouse alternating between two positions of the same target ten pixels apart (`DockDropTargetAllocationTests`): 0 and 0 for the centre of another group, the four split zones, the four host edges, the two kinds of splitter bar, the centre of the group of the dragged tab (reorder), the proximity band and no target. The phase 2 test of the drag (`DockHostDuringATabDrag_Update_AllocatesNothing`) asserts 0 where it asserted the 80 bytes of the target.
- Only a change of value allocates (the event arguments of `PropertyChanged`), which is bounded by the moves of the mouse that change the target.
- Proof of equivalence: `DockDropTargetReplayTests` replays scripted drags that go through every kind of target (the centre of another group, the four split zones, the four host edges, both halves of both splitter bars, the tab headers, the centre of the group of the dragged tab, the proximity bands, no target, release outside the host, cancel) and records the eight fields of `CurrentDropTarget` as values at each frame, and the layout after each drop (230 lines). Its expectation was recorded on the code that made a new target at each computation, and the host that keeps one instance reproduces it identically. It contains the two sequences where a field written afterwards could survive: a splitter bar next to a group G on side S, then the zone S of the same group G, then the drop; and a centre target with a computed `TabIndex`, then a centre target without index (another group, and `GetDropTarget` outside a drag). `DockDropTargetReuseTests` pins them (the target of the zone after a splitter bar is not a splitter drop, its splitter node is null, the layout is the frozen one; the index of a target never appears in the next one), together with the identity of the instance, the return of `GetDropTarget` and the notifications (appearance, value change, disappearance, and nothing for an identical computation).
- Mutations, checked then undone: not resetting `IsSplitterDrop` and `SplitterNode` in the fill fails the replay and seven tests of `DockDropTargetReuseTests`; not resetting `TabIndex` fails the replay and two tests of `DockDropTargetReuseTests`.
- `IsSplitterDrop` and `SplitterNode` are not read by `ExecuteDrop` (a splitter drop applies the zone to the target node, as a split zone does): they are visible through `CurrentDropTarget` only, which is what the tests read.
- Not part of this decision: a mouse that alternates between two groups (the first positions tried for the host edges of the allocation test) still allocated 96 to 128 bytes per frame of update after the change; the cause was not searched (the host shows the joystick of the group under the mouse when it changes). The allocation test keeps both positions of a case inside one group.
