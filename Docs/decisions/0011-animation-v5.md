# ADR-0011: Animation V5: awaitable animations, smooth scrolling, texture frames, layout transitions, enter and exit animations

- **Status**: Proposed
- **Date**: 2026-09-17
- **Source**: this chantier: the backlog `Docs/Tasks/animation-v5-tasks.md` written on 2026-09-15 after the V4 program, the author's answers of 2026-09-17 to four grouped questions (scope C1, C2, C3, C4 and C10; leftovers of ADR-0008 and ADR-0009 untouched; theme group extended to windows and popups only; AUTO delivery), a read-only discovery over six surfaces at HEAD `5e06b3b` on branch `animation-v5`, and a fresh-context review of the plan against the code (five reviewers, every blocking finding re-checked by a second agent). Plan: `Docs/Tasks/animation-v5-tasks.md`.

## Context

Facts verified at HEAD `5e06b3b` (V1 to V4 delivered by ADR-0006 to ADR-0009):

- One `UIAnimationManager` per desktop ticks at the head of `MGDesktop.Update`, before layout. One animation runs per (element, path); a replacement cancels the previous one with `KeepCurrent`; restarting the same instance raises no `Cancelled`. `Completed` and `Cancelled` are exclusive; `Seek` raises no event; the engine catches no exception thrown by a subscriber; a composite completes on its own timeline whatever happens to its children. Nothing in the engine uses `Task` or a `SynchronizationContext`. The fluent `Play()` lives on the non-generic `UIAnimationBuilder` base.
- The target registry is closed and its list of paths is pinned by `TargetApplicabilityTests`. Families: store pilots, simple observable targets (transitions require one), simple non-observable targets with a required owner type, and brush targets cloned once per run (`IUIBrushAnimationTarget<T>`, which inherits the store-backed contract). A property animation also accepts an explicit, unregistered target. Interpolators exist for `float`, `double`, `int` (rounded, no stepping) and others; the key frame engine has no discrete mode; the serializer's value codec already handles `float` and `int`.
- `UpdateLayout` captures the previous layout bounds in a local, assigns the new ones, lays out components and children, and only then raises `OnLayoutUpdated` and `OnLayoutBoundsChanged`: an ancestor finishes its `UpdateLayout` after all its descendants. A window runs the pass when its layout is invalid and runs it again in the same tick when an invalidation raised during a pass queued a refresh. `LayoutBounds` is in unscaled screen space and includes the window position: a window move goes through `TranslateAllBounds`, not through `UpdateLayout`. Scrolling never changes `LayoutBounds`; the scroll viewer shifts its content during update, truncated to whole pixels. The effective render matrix is composed in one place, inverted for hit testing, and a desktop-wide counter of active transforms gates the inverse path. A stack panel has no reorder API: moving a child is a removal followed by an insertion, which detaches it.
- `MGScrollViewer.VerticalOffset` / `HorizontalOffset` are clamped `float` properties with change events; the wheel adds a fixed interval and its guards also decide who consumes the wheel event; `EnsureElementVisible` writes the offsets directly; a smaller maximum re-clamps the offset. The scroll viewer has no keyboard path: keyboard navigation scrolls through `EnsureElementVisible`, except two call sites that write the offset directly (virtualized list box, tree view).
- `MGTextureFillBrush` is freezable and draws `Source.SourceRect` as is, in three paths (rectangle, rounded geometry, tile); its natural size drives the tile step and every stretch mode but `Fill`. `MGTextureData` is a record struct that shares its image by reference. The XAML DTO exposes `SourceName`, `Stretch` and `Color` only. A grid icon sheet already ships with MGUI.Core content.
- `MGWindow.TryCloseWindow` returns false when the window cannot close, raises a cancellable `WindowClosing`, removes the window from its list, calls `MGDesktop.NotifyWindowClosed` (which cancels the window's animations, unregisters it from the modal stack and releases focus) and raises `WindowClosed`. `Desktop.Windows` is a plain public list with no add or remove notification; bringing a window to the front removes and re-adds it; the samples show and hide windows by writing to that list. Nested and modal windows go through `AddNestedWindow` and the modal stack, which notify the desktop; `AddNestedWindow` throws when the window is already listed. The combo box dropdown, the colour picker popup and floating dock windows remove nested windows directly, without `TryCloseWindow`. The desktop rebuilds the active tooltip every update from a queued one and draws it at the mouse position; it draws the active context menu separately, after the windows. A window that is not click-through handles mouse events and occludes what it covers. `MGElement.Visibility` applies at once. `MGThemeAnimationSettings` is read by `MGButton` and `MGToggleButton` only, is disabled in every built-in theme, and every theme value is also listed in an invalidation inventory pinned by a test.
- Thirteen test files read the sources through the absolute path of the main checkout; this branch lives in a separate worktree, so those tests would validate another branch.

## Decision

1. **Tests resolve the repository root from the test assembly** (one shared helper, which also replaces the per-file roots that already exist), so that the source-reading architecture tests validate the branch they run on. No assertion changes.
2. **Awaitable animations return `Task<bool>` and never throw on cancellation.** `StartAsync` / `PlayAsync` resolve to `true` on `Completed` and to `false` on any cancellation (conflict replacement, detachment, window close, `Cancel()`, cancellation token). This departs from the backlog sketch (a cancelled task): cancellation is routine in a UI, and an exception escaping an `async void` handler would bring the game down. For a composite the result is that of the composite itself; restarting the awaited instance makes the task follow the restarted run. A cancellation token never touches the engine from its own thread: its callback posts a request that the manager drains at the very top of its update, before the clock advances and before the zero-delta early return (so a paused clock does not defer it), so the engine stays single-threaded and the task is always resolved on the update thread. One `TaskCompletionSource<bool>` per call, created outside the tick, without `RunContinuationsAsynchronously`: with no synchronization context, as in a MonoGame loop, the continuation runs on the update thread during the tick, like a `Completed` subscriber.
3. **Scroll offsets are simple observable `float` targets** (`ScrollViewer.VerticalOffset`, `ScrollViewer.HorizontalOffset`), clamped by the existing setters. `ScrollTo` clamps its destination, writes directly when the duration is zero, and otherwise starts one `KeepCurrent` property animation per axis from the current value. An external write during a run cancels it (the user always wins); "external" means any write that comes neither from the run nor from the internal re-clamp. Smooth wheel and `EnsureElementVisible` scrolling are opt-in through `ScrollAnimationDuration` (zero by default, behaviour unchanged); wheel notches accumulate on the pending destination, which the wheel guards also read so that event consumption does not change; the two call sites that write the offset directly go through `ScrollTo`, and while a run is in flight they and `EnsureElementVisible` compute and compare against the pending destination, not the mid-flight offset, so repeated key presses are never swallowed; dragging the scroll bar stays direct, and so does the public `VirtualizingWrapPanel.EnsureIndexVisible`, which has no production caller. The pending destination is exposed as read-only `PendingVerticalOffset` / `PendingHorizontalOffset`.
4. **Sprite sheets are a grid on the texture brush, animated through a `float` frame position.** `MGTextureFillBrush` gains `FrameGrid` (`MGSpriteSheetGrid?`, with two-axis spacing and margin) and `FrameIndex`; with a grid the effective source rectangle is the grid cell inside `Source.SourceRect` and the brush's natural size becomes the cell size. The target `Background.Texture.Frame` is a `float` brush target (clone on animate, ADR-0009, no owner type restriction) that writes `FrameIndex = clamp(floor(value), 0, frames - 1)`. A floored `float` gives exact steps with the existing interpolation, easings, key frames and serializer, so no discrete mode is added to the engine. No member of the target builds a texture brush from a number: the store-backed members copy the brush found below the animation, and a run or a visual state setter is refused with an explicit exception when the background is not a texture brush with a grid.
5. **Layout transitions are opt-in and run on a dedicated layout transform.** `MGElement.LayoutTransition` is a settings object, null by default. The animated values live in a separate render object (`UILayoutTransform`: offset and scale), allocated on demand, composed into the effective matrix after the render transform, inverted by hit testing, counted as an active transform while it is not the identity, and separate from `RenderTransform.Translation` / `.Scale` so that application animations coexist. The internal run uses an explicit, unregistered target: no new public path, nothing to declare in XAML, transitions or the serializer. The trigger sits right after the bounds assignment in `UpdateLayout`: previous and new bounds non-empty and different, element opted in, already attached and laid out before this pass. Window moves and scrolling never trigger a transition, by construction; a detached and re-attached element (reorder, recycled virtualized container) never does either, thanks to a per-element "laid out since attached" flag cleared on detachment; no transition runs in a pass where the displaying window changed size. Because the pass completes child-first, an ancestor's displacement reaches its descendants through an ambient pass stack: on a desktop where at least one element opted in (a sticky desktop flag raised by the `LayoutTransition` setter), each element pushes an entry at the top of `UpdateLayout`, updates it right after its bounds assignment and before laying out its children with the displacement visually applied to its subtree, pops it in the `finally`, and an element's effective displacement is its own minus the inherited one. One animation instance per element is reused. Size animation, XAML settings and the sample form a second slice.
6. **Enter and exit animations are driven by visibility and by the window lifecycle, with deferred removal.** An element has optional, lazily allocated settings: an `EnterAnimation` / `ExitAnimation` (any `UIAnimation`, from code) or a predefined `EnterEffect` / `ExitEffect` (`Fade`, `Scale`, `FadeScale`, four slides) with duration, easing, a scale start of 0.9 and a fixed slide distance of 24 pixels, declarable in XAML and in styles. Effects animate the public `Opacity` and `RenderTransform` paths and hold the transform origin at the centre for the duration of a scale. Hiding an element that has an exit keeps `Visibility` at its value in effect until the run completes and exposes the request through `PendingVisibility`; an internal exiting state, never a write to the public `IsHitTestVisible`, removes the element and its subtree from hit testing and input; a cancelled exit applies the request immediately; an exit only starts for an element that has been drawn since it was attached. Windows play their enter when they appear (nested and modal windows in their add path, root windows by a per-frame comparison of `Desktop.Windows` with the previous frame, which bring-to-front does not disturb) and, on `TryCloseWindow`, release focus at once, stop handling input and occluding, play their exit, and only then are removed, `NotifyWindowClosed` and `WindowClosed` following the removal. `RemoveNestedWindow` defers the removal of a nested window that has an exit and `AddNestedWindow` cancels a running exit instead of throwing, so reopening a dropdown mid-exit works; direct modal removal and direct writes to `Desktop.Windows` stay synchronous and play nothing; deferring a modal close means deferring the existing `RemoveModalWindow` call, and an exiting modal keeps blocking its parent until the run ends; floating dock windows are removed without an exit. The desktop keeps an exiting tooltip or context menu in a dedicated slot, draws it with the draw offset captured when the exit started (a tooltip has no position of its own) until the run ends, and finishes that exit at once when another popup of the same kind opens. Declarative storyboards in XAML stay out of scope (backlog C7).
7. **The theme group gains open and close settings for windows and popups only.** `MGThemeAnimationSettings` gains `OpenDuration`, `CloseDuration`, `OpenEasing`, `CloseEasing` and `PopupEffect`, classified as render-only theme values. When `Enabled` is true, `MGWindow`, `MGToolTip`, `MGContextMenu` and the combo box dropdown use them unless the element sets its own; other controls do not read them. The values are read when an enter or exit starts, without any theme-change callback. `Enabled` stays false in every built-in theme.
8. **Delivery.** Ten slices (Y0 to Y9), one commit each on branch `animation-v5`, each capability with its tests, its section of `Docs/animation-architecture.md` (final state only), a section of the `AnimationDemo` sample with an explanation, and its mention in scenario `SCN-ANIM-001`. Existing tests stay untouched except for the rewrites listed in the plan (the sample test registers the sprite sheet; the theme inventory test pins five more values) and for the two closed expectation tables that the tests themselves require to be extended: `TargetApplicabilityTests.Expected` for every new registered path, `AnimationDemoSampleTests.SectionElementNames` for every new sample section, and the line numbers of `ResolvedPilotWriteSitesTests.AllowedLines` whenever code is inserted above a pinned line. The leftovers and open points of ADR-0008 and ADR-0009 are not reopened.

Out of scope: spring interpolation, per-subtree clocks and reduced motion, XAML triggers and declarative storyboards, time markers, path animation, the missing targets of backlog C11 (including an image control frame target), interpolation between two textures, a public hook to skip a layout transition, a keyboard scrolling path on the scroll viewer.

## Consequences

- An element, scroll viewer, brush or window that uses none of the new features keeps its current behaviour; every feature is opt-in and guarded by a null or zero check. Three costs are added for everyone: one test per tick in the manager for pending cancellation requests, a per-frame comparison of the root windows list, and one flag test per `UpdateLayout`. On a desktop where an element opted into a layout transition, every element also pushes and pops one preallocated stack entry per layout pass.
- Code that reads `Visibility`, `NestedWindows` or a window list right after hiding or closing sees the value still in effect while an exit runs. This only concerns elements and windows that opted into an exit, or every window and popup once an application enables the theme group. A direct write to `Desktop.Windows` bypasses enter and exit on removal.
- A closing window removes its nested windows at once: they do not fade with it. A fade or scale on a window does not cover a modal child.
- `PlayAsync` allocates once per call and never per tick; awaiting a `RepeatForever` animation only ends through cancellation; the inline-continuation guarantee holds without a synchronization context.
- While any layout transition or enter and exit scale or slide runs, the desktop-wide transform gate is open, so hover and hit testing take the inverse-transform path for every element of that desktop during the run.
- The element that is moved in a reorder does not glide (it is re-attached); its neighbours do. Content that appears from a collapsed state is an enter animation, not a layout transition. A layout transition with size animation stretches the element's content during the run.
- The frame position is a `float` whose integer part is the frame: tooling that shows the animated value displays a fractional frame. Animated scrolling moves by whole pixels.
- With a transition attached to a scroll offset path, content that shrinks during a run may restart the transition; the zero-allocation guarantee is stated without such a transition.
- Making the tests checkout-independent touches thirteen test files and will conflict textually, in a minor way, with the two tests that the XAML editor branch retargets in its last slice.
- ADR-0010 belongs to the XAML editor chantier on another branch; this record takes number 0011.

## Decisions taken during delivery

- **Y1**: the pending-cancellation queue is a plain `System.Collections.Concurrent.ConcurrentQueue<UIAnimationCompletion>` (lock-free enqueue/dequeue, `IsEmpty` read without a lock on the fast path), not a custom lock-based structure: the backlog left the exact type open and the built-in type already meets the "no lock on the fast path" requirement. The per-call completion releases its `CancellationTokenRegistration` with `Unregister()` rather than `Dispose()`: `Dispose()` blocks until a callback already running elsewhere has returned, which the update thread must never wait on, while `Unregister()` only detaches the callback (and is itself what stops a queued-but-not-yet-drained request from ever reaching an unrelated later run, since the registration for a resolved completion is gone before a stale token can be cancelled).
- **Y2**: the external-write rule needs to tell an explicit `ScrollTo` run apart from a `UITransition<float>` attached to the same scroll-offset path before deciding whether to cancel it; `UIAnimationManager` gained one internal accessor for this, `GetActive(owner, path)`, returning the active animation on a (owner, path) key without walking the active list -- the minimal addition needed, kept internal since nothing outside the engine assembly needs it. The transition is identified by reference (`UITransitionCollection[path]` cast to `UITransition<float>`, compared to the found animation through its own `Animation` property), never by the `"scroll:vertical"`/`"scroll:horizontal"` run names, so a future rename of those names cannot silently break the check. `ScrollTo` reuses one `UIPropertyAnimation<float>` instance per axis per viewer (fields on `MGScrollViewer`, allocated on first use) rather than building a fresh one per call: a wheel notch or a repeated keyboard scroll restarts the same instance, matching the "no allocation past warm-up" budget the rest of the animation engine holds elsewhere. Content shrinking during a run turned out not to need the special case ADR-0011's Consequences anticipated (a transition attached to the path restarting): the `MaxVerticalOffset`/`MaxHorizontalOffset` re-clamp goes through the same internal write path as the animated apply (`SetVerticalOffsetCore`/`SetHorizontalOffsetCore`), which still raises the normal property notification, so a transition retargets to the new bound exactly like it would for any other external change; `MGUI.Tests.Animation.ScrollAnimationTests.TransitionAttachedToTheVerticalPath_ContentShrinkingMidRun_EndsAtTheNewBound_WithoutException` confirms no restart and no exception.
- **Y3**: the plan's XAML attribute list for the sprite-sheet grid (`FrameColumns`, `FrameRows`, `FrameCount`, `FrameSpacing`, `FrameMargin`, `FrameIndex`) omitted the cell size, although `MGSpriteSheetGrid` requires one: `TextureFillBrush` gained a seventh attribute, `FrameCellSize`, required whenever `FrameColumns`/`FrameRows` are both set (a clear `InvalidOperationException` at `ToFillBrush` otherwise, naming the missing attribute); the two-integer attributes (`FrameCellSize`, `FrameSpacing`, `FrameMargin`) parse the same `"x,y"` format `ShapeXamlParser.ParsePoint` already uses for a `Vector2`, just over integers, as a plain string property rather than a new `TypeConverter`-backed struct (no other XAML DTO needed an integer point before this one, and a private parser local to `TextureFillBrush.ToFillBrush` was the smaller addition). `Background.Texture.Frame` is deliberately **not** `IUIObservableAnimationTarget<float>` (only `IUIBrushAnimationTarget<float>`, which already implies `IUIStoreBackedAnimationTarget<float>`): unlike a colour or a gradient, a frame index has no meaningful "value the property would have without the animation" for a transition to retarget from or to, so `UITransition<float>` on this path is refused by its own existing cast in `OnAttached`, with no new refusal code needed. `BeginAnimatedValue` also departs from the four pre-existing brush targets on one point: it never falls back to constructing a fresh brush when no exact base can be recovered (a replaced run already occupying the path) -- it throws `InvalidOperationException` instead, since a frame index alone carries no texture to build one from; `EndAnimatedValue` and the two `SetValue` overloads (named visual state setter and the plain `IUIAnimationTarget<float>` member) share the same "copy the texture-with-grid brush below the animation, or throw naming what was actually found" helper, so nothing on this path ever builds a texture brush out of a bare number. The rounded tile path's existing `isWholeTexture` check (compares the effective source rectangle to the whole image) needed no change to satisfy "never the wrap sampler with a grid": a frame's cell is a strict sub-rectangle of the atlas in every grid but a degenerate `1x1` one, so the check already routes to the atlas-tiling fallback. `ResolvedPilotWriteSitesTests.AllowedLines` gained one entry for `MGSpriteSheetGrid`'s own `Margin` record parameter (the pixel margin of the grid, not the `MGElement.Margin` pilot the regex is built to catch) -- an addition the plan's stated perimeter did not list, needed only to keep that pre-existing completeness guard green after this slice's own line insertion, per the plan's own decision 8 ("the line numbers of `ResolvedPilotWriteSitesTests.AllowedLines` whenever code is inserted above a pinned line").
- **Y4**: the ambient pass stack (`MGDesktop.PushLayoutTransitionEntry`/`PopLayoutTransitionEntry`/`PeekLayoutTransitionEntry`/`SetLayoutTransitionEntryDisplacement`) lives on `MGDesktop`, next to `ActiveRenderTransformCount`, as a backing array of a private `readonly record struct LayoutTransitionStackEntry(Vector2 Displacement, bool WindowResized)` plus a count, not a `Stack<T>`: an indexable array lets `SetLayoutTransitionEntryDisplacement` overwrite the top entry in place (`array[count - 1] = ... with { Displacement = ... }`) without a pop-mutate-push round trip, and `Array.Resize` only runs the one time depth exceeds capacity (starting at 8), never in a steady state. `MGElement.UpdateLayout` reads `MGDesktop.HasLayoutTransitions` into a local once at the top and pushes/pops based on that same local (never re-reading the sticky flag mid-pass), so a flag raised by a sibling mid-pass cannot desynchronize one element's own push and pop. Virtualization recycling turned out to need no change at all: `VirtualizingStackPanel.RecycleItem`/`RealizeItem` and `VirtualizingWrapPanel`'s equivalents already remove and re-add the recycled element through their `ObservableCollection<MGElement>` (`MGMultiContentHost._Children`), which calls `MGElement.SetParent(null)` then `SetParent(this)` on every recycle -- a real parent change both times, already covered by the plan's own attach flag (`_hasLaidOutSinceAttached`, lowered unconditionally in `SetParent` whenever the parent actually changes) with no extra internal method needed in either panel file, contrary to the perimeter's "only if needed" hedge. The layout-offset counter (`MGElement._hasActiveLayoutOffset`, adjusted by `SetLayoutOffset`) is a boolean separate from `HasActiveRenderTransform` and from the state-scale override, exactly like the plan asked, so a layout transition and an application `RenderTransform`/`RenderScale` on the same element adjust `ActiveRenderTransformCount` independently and never cancel each other's contribution. `UILayoutTransitionOffsetTarget.RestoreBaseValue` ignores the `baseValue` it receives and always writes `Vector2.Zero` through the same counting setter (`MGElement.SetLayoutOffset`) as a normal tick, rather than special-casing detach/close: `UIAnimationCollection.Clear()` and `UIAnimationManager.CancelOwnedByWindow` already force `RestoreBaseValue` regardless of the run's own `CancelBehavior`, so the offset and the counter return to their initial state through the existing forced-restore paths with no dedicated detach/close handling in this slice. The `AllowedLines` entry for `MGDesktop.cs`'s local `var MinHeight` moved from line 814 to 861 (the new members were inserted above it, right after `AdjustActiveRenderTransformCount`, per the plan's own decision 8).
- **Y4 fix round 1**: an independent verifier found the flag-lowering claim above incomplete and the resize guard's comparison mismatched. (1) `SetParent`'s recycling/reorder analysis only accounted for the reparented element itself: a container-only element (the normal `MGListBox` shape, whose `ContentPresenter` border is internal and recycled while only the item content can opt in) lowers its own `_hasLaidOutSinceAttached`, but its descendants never go through `SetParent` themselves, so an opted descendant kept its stale flag and its now-meaningless previous `LayoutBounds`, and played a false run off the recycled/reordered container's jump. Fixed by a new `MGElement.ResetLayoutTransitionAttachStateRecursive()` (mirrors `InvalidateLayoutTree`'s visual-children-plus-components walk) called from `SetParent` instead of the single-field reset, but only once `MGDesktop.HasLayoutTransitions` is up: while nobody on the desktop has ever opted in, no layout transition can read the flag, so `SetParent` keeps paying the original one-field write and the recursive walk's cost is never charged to a desktop that has no use for it. (2) `WindowResized` compared `PreviousLayoutBounds.Size` (margin already subtracted) against `Bounds.Size` (the new allocation, margin included): a window with a non-zero `Margin` therefore looked resized on every single pass and silently suppressed every layout transition it contained, resize or not. Fixed by comparing the previous ALLOCATED size instead: `UpdateLayout` now also captures `PreviousAllocatedBounds = AllocatedBounds` at the top of the `try`, alongside `PreviousLayoutBounds`, and `WindowResized` reads `PreviousAllocatedBounds.Size != Bounds.Size` (both including the margin, so a real resize is still caught and a merely-margined window is not). Neither fix changes the mechanism's shape (still the attach flag, still the ambient stack), only closes gaps in how each was applied; no ADR status change.
