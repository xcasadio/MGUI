# ADR-0013: A name identifies one element of a window, and saying so is the loader's job

- **Status**: Proposed
- **Date**: 2026-09-18
- **Source**: this chantier: the author's bug report of 2026-09-18 (a `Window` root whose item template sets `Name` fails to load with `An item with the same key has already been added. Key: ItemLabel`, reported as a bare `ParseFailure` with no line and no column), a read-only discovery over the loader, the window name registry and the template instantiation path at `develop` `e633fea`, the author's answers to three grouped questions, and two fresh-context readiness reviews of the plan. Plan: `Docs/Tasks/duplicate-element-name-tasks.md`.

## Context

Facts verified at `develop` `e633fea`:

- An `MGWindow` indexes the named elements of its tree in `ElementsByName`, fed only by its own `OnDirectOrNestedContentAdded` / `OnDirectOrNestedContentRemoved` chain (`MGWindow.cs:1560-1562`). `Element_Added` calls `ElementsByName.Add(e.Name, e)` (`MGWindow.cs:1973-1976`) and `Element_NameChanged` does the same on a rename (`MGWindow.cs:2038-2041`). The index is what `MGWindow.GetElementByName`, `MGElement.TryGetElementByName` and `{MGBinding ElementName=...}` resolve through (`ISourceObjectResolver.cs:62-82`).
- `Dictionary<string, MGElement>.Add` throws `ArgumentException` on a duplicate key. Its message names the key and nothing else: no element, no type, no position.
- `ContentTemplate.GetContent` deep-copies the declared `Element` DTO once per generated item (`Templates.cs:31`, through `ObjectUtils.Copy`, which copies every field) and `Element.ApplyBaseSettings` re-applies `Element.Name = Name` on each copy (`Element.cs:607-610`). One declared node therefore produces N named elements.
- A `Window` document root is instantiated as a nested `MGWindow` with its own index (`Controls.cs:4150-4162`), and `SingleContentHost.ApplyDerivedSettings` builds the whole child subtree, generated items included, before setting it as that window's content (`Containers.cs:31-38`). `MGContentHost.InvokeContentAdded` then walks the entire subtree, components included (`MGContentHost.cs:46-67`). The duplicate is raised there, during instantiation.
- `XamlLoaderDiagnostics.Execute` wraps parsing only: `XAMLParser.ParseDefinition` runs inside it (`XAMLParser.cs:309-322`) while `Load<T>` calls `ToElement` outside it (`XAMLParser.cs:441-453`). An exception raised while instantiating the parsed DTOs therefore never becomes a `XamlLoaderException`, keeps no `SourceName`, no `FilePath`, no line and no column, and reaches the strict-mode consumers raw: `MGXAMLDesigner.RefreshParsedContent` prints `ex.Message` alone (`MGXAMLDesigner.cs:278-307`), and the XAML editor's preview host (branch `xaml-editor`) turns it into a `ParseFailure` with no position.
- `Element.SourcePosition` is stamped in both loader modes by `XAMLParser.StampSourcePositions` and copied into `MGElement.Metadata` by `ApplyBaseSettings` (`Element.cs:594-599`, `UIToolingService.cs:55`, `:68`). `XamlSourcePosition.Ordinal` ranks the declared node, not the instance, so every clone of one template node carries the same `Ordinal`.
- `XamlLoaderDiagnostics.Classify` deliberately reads no localised message text (the rule set by `4b51ca6`), and `TryGetExceptionIntProperty` already reads `LineNumber` and `LinePosition` by reflection from any exception type that exposes them as `int`.
- `MGUI.Core/UI/Templates/BuiltInControlTemplates.xaml` repeats `PART_Border`, `PART_ScrollViewer` and twenty-two other names from one `ControlTemplate` definition to the next inside a single document. Those names live in `MGElement.TemplateParts`, a per-element table (`MGElement.cs:116`, `:291-320`), not in any window index.

## Decision

1. **A name identifies at most one element of a window, and the window index keeps enforcing it.** No tolerance (`TryAdd`), no template name scope. The rule is unchanged; only its diagnosis changes.
2. **The index throws a dedicated, explainable exception.** `MGDuplicateElementNameException` (public, `MGUI.Core.UI`) carries `Name`, `ExistingElement`, `NewElement`, `LineNumber` and `LinePosition`. `MGWindow.Element_Added` and `MGWindow.Element_NameChanged` raise it instead of letting `Dictionary.Add` throw. It is not a `XamlLoaderException`, because the index also rejects a duplicate produced by a plain `element.Name = "x"` assignment, with no XAML involved.
3. **The message tells the two causes apart.** When both elements carry a `XamlSourcePosition` with the same `Ordinal`, one declaration was cloned by a template and the message says so, with the position of that declaration. Otherwise the name was declared twice, and the message names both element types and the position of the second when it is known.
4. **A name declared twice in one document is a strict-mode loader diagnostic.** New `XamlLoaderDiagnosticCode.DuplicateElementName`, raised by `XamlLoaderDiagnostics.ValidateUniqueElementNames` from `XAMLParser.ParseDefinition` only, at the line and column of the second declaration. Compatibility mode is unchanged.
5. **The validation covers element and window documents, not object definitions.** `ParseObjectDefinition` is not validated: a control template document legitimately repeats part names across its definitions, and those names are validated separately by `ValidateRequiredTemplateParts`. Only XML elements whose local name resolves to a DTO deriving from `Element` count, so `Style`, `ControlTemplate`, `VisualStateDefinition` and `TemplatePart` names are out of scope.
6. **Instantiation failures become located diagnostics in strict mode.** `XAMLParser.Load<T>` and `XAMLParser.LoadRootWindow` run their `ToElement` call inside `XamlLoaderDiagnostics.Execute`, and `Classify` gains a typed branch mapping `MGDuplicateElementNameException` to `DuplicateElementName`, placed before the message-based pass so it stays independent of the machine's language.

## Consequences

- The document of the report still does not load. It now fails with `DuplicateElementName`, a line, a column and a message that names `ItemLabel`, the `TextBlock` it came from and what to change. Making it load would require a name scope per template instance, which decision 1 rejects for V1.
- Decision 6 widens what becomes a `XamlLoaderException` in strict mode: every failure raised while instantiating parsed DTOs, not only a duplicate name, is now classified, located and given the document's `SourceName` and `FilePath`. This is a public surface change. `MGXAMLDesigner` already formats a `XamlLoaderException` and gains from it immediately; an out-of-repository consumer that filters on a precise exception type would see the change. No test in this repository asserted the previous boundary.
- `MGDuplicateElementNameException` and `XamlLoaderDiagnosticCode.DuplicateElementName` are additions: no type, member or enumeration value is renamed or removed, and the new enumeration member is appended so no existing value moves.
- Decision 3 degrades gracefully. When positions were not stamped (the count guard of `StampSourcePositions`, an element built by code, a control template part, a theme element), the second form of the message is used: still correct, only less precise.
- The rule stays a per-window one. A nested `MGWindow` has its own index, so the same name may be used again inside one, exactly as before.
- Known, not addressed here: two controls sharing a XAML `ControlTemplate` whose part carries a `Name` should collide the same way, since `ControlTemplateLoader.BuildStructure` instantiates the declared root per control and `MGElement.ApplyControlTemplate` re-throws. The behaviour is pinned by a test but not changed: decision 1 forbids tolerating it, and unifying template part names with the window index is a separate question.
