# ADR-0013: A name identifies one element of a window, and saying so is the loader's job

- **Status**: Proposed
- **Date**: 2026-09-18
- **Source**: this chantier: the author's bug report of 2026-09-18 (a `Window` root whose item template sets `Name` fails to load with `An item with the same key has already been added. Key: ItemLabel`, reported as a bare `ParseFailure` with no line and no column), a read-only discovery over the loader, the window name registry and the template instantiation path at `develop` `e633fea`, the author's answers to three grouped questions, and two fresh-context readiness reviews of the plan. Plan: `Docs/Tasks/duplicate-element-name-tasks.md`. Context and decision 6 corrected on 2026-09-18 after the mechanism was measured during delivery, and after a four-lens adversarial review of the delivered work.

## Context

Facts verified at `develop` `e633fea`:

- An `MGWindow` indexes the named elements of its tree in `ElementsByName`, fed only by its own `OnDirectOrNestedContentAdded` / `OnDirectOrNestedContentRemoved` chain (`MGWindow.cs:1560-1562`). `Element_Added` calls `ElementsByName.Add(e.Name, e)` (`MGWindow.cs:1973-1976`) and `Element_NameChanged` does the same on a rename (`MGWindow.cs:2038-2041`). The index is what `MGWindow.GetElementByName`, `MGElement.TryGetElementByName` and `{MGBinding ElementName=...}` resolve through (`ISourceObjectResolver.cs:62-82`).
- `Dictionary<string, MGElement>.Add` throws `ArgumentException` on a duplicate key. Its message names the key and nothing else: no element, no type, no position.
- `ContentTemplate.GetContent` deep-copies the declared `Element` DTO once per generated item (`Templates.cs:31`, through `ObjectUtils.Copy`, which copies every field) and `Element.ApplyBaseSettings` re-applies `Element.Name = Name` on each copy (`Element.cs:607-610`). One declared node therefore produces N named elements.
- The duplicate is raised when a built subtree is **attached** into a content host, by `MGContentHost.InvokeContentAdded`, which announces every element of that subtree to the window (`MGContentHost.cs:46-67`). Its traversal passes `IncludeSelf: false`, which also skips the components of the element being attached (`MGElement.cs:6123-6124`), and `MGListBox` keeps its whole items structure in its components (`MGListBox.GetChildren()` returns none). So the generated items of a list box are announced when the list box is *wrapped* by the attached element, and are not announced when the list box *is* that element. Measured: a `Window` root fails, a `StackPanel` root fails, a `ListBox` root loads, and `XAMLParser.LoadRootWindow` never fails on any of them, a root window never being attached into a content host. That, not the kind of root, is what made the report's document fail and its `ListBox`-rooted twin pass.
- `XamlLoaderDiagnostics.Execute` wraps parsing only: `XAMLParser.ParseDefinition` runs inside it (`XAMLParser.cs:309-322`) while `Load<T>` calls `ToElement` outside it (`XAMLParser.cs:441-453`). An exception that is not a `XamlLoaderException` therefore keeps no `SourceName`, no `FilePath`, no line and no column when it reaches a host. The XAML editor's preview host (branch `xaml-editor`) turns such an exception into a `ParseFailure` with no position, which is the symptom the report describes, because it attaches the loaded tree inside its own `try`. `MGXAMLDesigner` does not: it guards only the `LoadPreview` call and attaches afterwards, outside the guard (`MGXAMLDesigner.cs:266-316`), and its presenter is not in the add chain of its owning window anyway, so the collision of the report is never reached there at all.
- `Element.SourcePosition` is stamped in both loader modes by `XAMLParser.StampSourcePositions` and copied into `MGElement.Metadata` by `ApplyBaseSettings` (`Element.cs:594-599`, `UIToolingService.cs:55`, `:68`). `XamlSourcePosition.Ordinal` ranks the declared node, not the instance, so every clone of one template node carries the same `Ordinal`.
- `XamlLoaderDiagnostics.Classify` deliberately reads no localised message text (the rule set by `4b51ca6`), and `TryGetExceptionIntProperty` already reads `LineNumber` and `LinePosition` by reflection from any exception type that exposes them as `int`.
- `MGUI.Core/UI/Templates/BuiltInControlTemplates.xaml` repeats `PART_Border`, `PART_ScrollViewer` and twenty-two other names from one `ControlTemplate` definition to the next inside a single document. Those names live in `MGElement.TemplateParts`, a per-element table (`MGElement.cs:116`, `:291-320`), not in any window index.

## Decision

1. **A name identifies at most one element of a window, and the window index keeps enforcing it.** No tolerance (`TryAdd`), no template name scope. The rule is unchanged; only its diagnosis changes.
2. **The index throws a dedicated, explainable exception.** `MGDuplicateElementNameException` (public, `MGUI.Core.UI`) carries `Name`, `ExistingElement`, `NewElement`, `LineNumber` and `LinePosition`. `MGWindow.Element_Added` and `MGWindow.Element_NameChanged` raise it instead of letting `Dictionary.Add` throw. It is not a `XamlLoaderException`, because the index also rejects a duplicate produced by a plain `element.Name = "x"` assignment, with no XAML involved.
3. **The message distinguishes the two causes by the evidence it has.** When both elements carry a `XamlSourcePosition` with the same `SourceName` and the same `Ordinal`, the message reports that shared position and names a template applying one declared name to every element it generates as the cause to look for. It does not assert that cause: an `Ordinal` restarts at zero for every parse and a `DisplayName` is not required to be unique, so two parses of two documents sharing a display name reach this branch with no template involved, and the message stays true there. Otherwise the name was declared twice, and the message names both element types and the position of the second when it is known.
4. **A name declared twice in one document is a strict-mode loader diagnostic.** New `XamlLoaderDiagnosticCode.DuplicateElementName`, raised by `XamlLoaderDiagnostics.ValidateUniqueElementNames` from `XAMLParser.ParseDefinition` only, at the line and column of the second declaration. Compatibility mode is unchanged.
5. **The validation covers element and window documents, not object definitions.** `ParseObjectDefinition` is not validated: a control template document legitimately repeats part names across its definitions, and those names are validated separately by `ValidateRequiredTemplateParts`. Only XML elements whose local name resolves to a DTO deriving from `Element` count, so `Style`, `ControlTemplate`, `VisualStateDefinition` and `TemplatePart` names are out of scope.
6. **Withdrawn, and why it matters.** This decision read: "instantiation failures become located diagnostics in strict mode", by running the `ToElement` call of `XAMLParser.Load<T>` and `XAMLParser.LoadRootWindow` inside `XamlLoaderDiagnostics.Execute` and giving `Classify` a typed branch for the new exception. Measuring the failure while writing the tests refuted its premise: the collision is not raised while instantiating. `LoadPreview` returns a healthy tree, and the exception is raised later, when that tree is attached into a content host -- outside every loader call. No wrapping inside the loader can therefore classify it. Nothing of this decision is implemented; what to do instead is an open question put to the author (`Docs/Tasks/duplicate-element-name-tasks.md`, O3), and this record will be superseded or completed once it is answered.

## Consequences

- The document of the report still does not load. It now fails with an `MGDuplicateElementNameException` carrying a line, a column and a message that names `ItemLabel`, the `MGTextBlock` it came from and what to change -- not with a loader diagnostic, for the reason given in decision 6. Making it load would require a name scope per template instance, which decision 1 rejects for V1.
- Because decision 6 is withdrawn, the failure of the report reaches a host as a bare `MGDuplicateElementNameException`, not as a `XamlLoaderDiagnostic`: the code, the source name and the file path of a loader diagnostic are not attached to it, only its own message and position. A host that catches it while attaching a preview can still report it at that position, which is what its `LineNumber` and `LinePosition` are for.
- `MGDuplicateElementNameException` and `XamlLoaderDiagnosticCode.DuplicateElementName` are additions: no type, member or enumeration value is renamed or removed, and the new enumeration member is appended so no existing value moves.
- Decision 3 degrades gracefully. When positions were not stamped (the count guard of `StampSourcePositions`, an element built by code, a control template part, a theme element), the second form of the message is used: still correct, only less precise.
- The rule stays a per-window one. A nested `MGWindow` has its own index, so the same name may be used again inside one, exactly as before.
- Measured, and not a second defect: two controls sharing a XAML `ControlTemplate` whose part carries a `Name` do not collide. `ControlTemplateLoader.BuildStructure` does apply the declared name during `ToElement`, then clears it back to null once it has collected the parts by it (`ControlTemplateLoader.cs:225-247`), so a part name never reaches a window's index; it lives in `MGElement.TemplateParts`, a per-element table. Pinned by a test, unchanged.
