# ADR-0015: Containers announce their children through the content-host chain

- **Status**: Proposed
- **Date**: 2026-09-19
- **Source**: this chantier: the author's bug report of 2026-09-19 (dragging a docking panel in `MGUI.Editor.Host` shows `Error building docking layout: Duplicate element name 'Root'. A MGStackPanel already carries that name in this window, and both elements carry the same source position...`), a read-only discovery at `develop` `213f277`, a throwaway reproduction test, three independent adversarial reviews of the diagnosis, the author's answers to four grouped questions, and three fresh-context readiness reviews of the plan. Plan: `Docs/Tasks/dock-name-index-tasks.md`.

## Context

Facts verified at `develop` `213f277` (= `xaml-editor`):

- An `MGWindow` indexes the named elements of its tree in `ElementsByName`, fed only by its own `OnDirectOrNestedContentAdded` / `OnDirectOrNestedContentRemoved` chain (`MGWindow.cs:1563-1565`; `Element_Added` `:1999-2003`, `Element_Removed` `:2029-2033`, `Element_NameChanged` `:2060-2074`). `IndexElementName` throws `MGDuplicateElementNameException` whenever the key is already present, with no identity test (`:1978-1986`); `UnindexElementName` drops an entry only when it is the element's own (`ReferenceEquals`, `:1991-1997`). ADR-0013 decided that this index keeps enforcing "one name, one element of a window" with no tolerance and no name scope.
- The chain is the `MGContentHost` mechanism: `InvokeContentAdded(Element)` (`Containers/MGContentHost.cs:49-66`) announces `Element`, then every element of `Element.TraverseVisualTree(IncludeSelf: false, includeComponents: true, false, false)` -- the subtree present at that moment -- and subscribes to the nested events of `Element` only when `Element` is itself an `MGContentHost`; `InvokeContentRemoved` mirrors it (`:87-104`). `MGSingleContentHost.SetContentVirtual` removes the old content through the chain before adding the new one (`:258-283`). The chain is therefore complete only if every element that holds other elements is an `MGContentHost` that announces every child it takes and every child it releases.
- Two asymmetries live in `MGContentHost` itself: `AddComponent` announces the component (`:14-18`) but nothing overrides `MGElement.RemoveComponent` (`MGElement.cs:1091-1107`), so a component swapped by `EnsureComponentBinding` (`:1110-1140`) is announced on the way in and never on the way out; and the attach-time traversal passes `IncludeSelf: false`, which skips the components of the element being attached (`MGElement.cs:6144-6160`, components are traversed only under `IncludeSelf`). ADR-0013 recorded the second one as the reason a `ListBox` root loads where a wrapped `ListBox` fails.
- The docking containers hold their children outside the chain. `MGDockTabGroup : MGElement` (`Docking/Controls/MGDockTabGroup.cs:16`) parents the active panel content with a bare `SetParent` (`UpdateActiveContent` `:623-666`, the removal guarded by `Parent == this` `:627-629`) and so do its headers panel and buttons (`:373`, `:387`, `:401`, `:426`, `:453`). `MGDockSplitContainer : MGElement` (`MGDockSplitContainer.cs:11`, `FirstChild` / `SecondChild` `:41-49` / `:70-78`) and `MGDockAutoHideDrawer : MGElement` (`MGDockAutoHideDrawer.cs:16`, `RefreshContent` `:329-349`, `Reparent<T>` `:272-280`) do the same. `MGDockHost` itself is an `MGSingleContentHost` (`MGDockHost.cs:13`). Because `InvokeContentAdded` / `InvokeContentRemoved` are protected members of `MGContentHost`, none of the three can announce anything.
- `MGDockHost.RebuildVisualTree` (`:2203-2266`) first calls `Detach()` on every previous `MGDockTabGroup` (`:2208-2213`; `Detach` sets `GroupNode = null`, `:274-277`, which runs `UpdateActiveContent` and silently releases the content), then builds a new tree in which the same cached panel content (`DockPanelNode.GetOrCreateContent`, `DockPanelNode.cs:245-252`) is re-parented into a new tab group, then `SetContent(visualRoot)` (`:2257`); any exception is caught and replaced by an error placeholder (`:2260-2263`, text `:2496`). Every host operation ends in `CommitModelChange` (`:2522-2527`, `SyncFloatingWindows` before `RebuildVisualTree`); a docked-to-docked drop rebuilds twice in one gesture (`ExecuteDrop` `:1031-1037`: the unsuspended model mutation raises `LayoutChanged`, `DockNode.cs:21-32`, `DockLayoutModel.cs:500-517`, then an explicit rebuild). `ActivePanelId` changes are filtered out of `LayoutChanged` (`DockLayoutModel.cs:502-512`): a tab switch releases the outgoing content with no rebuild at all.
- Measured with a throwaway test on the hosted XAML editor view with a preview `<StackPanel Name="Root">` loaded: before any rebuild the editor window does not resolve `Root`; the first `RebuildVisualTree` silently indexes it (the whole new tree is traversed by `SetContent`); the second shows the error placeholder; floating and redocking *another* panel shows it at the redock. The mechanism: the old tree's traversal at removal no longer contains the panel content (released silently by `Detach`), so nothing is unindexed, and the new tree's traversal offers it again. In the editor the stale entry is usually a *previous* root: `XamlPreviewHost.ReplaceRoot` swaps in a brand-new root on every successful parse through the presenter's own `SetContent` (`MGUI.Editor/Preview/XamlPreviewHost.cs:168-172`), which the tab group above it does not relay, so the index keeps the dead root and refuses the live one -- with the same message, since `MGDuplicateElementNameException` chooses the "same source position" wording on equal `(SourceName, Ordinal)`, not on identity (`MGDuplicateElementNameException.cs:63-78`, ADR-0013 decision 3). Reordering `RebuildVisualTree` or making the index idempotent on the same instance would not cover that variant, nor the tab switch, nor the float path; all three reviewers rejected them.
- Every model operation removes the panel from its current group before adding it to the target one (`DockOperation.DockAsTab` `:35-47`, `SplitDock` `:56-70`, `SplitDockAtRoot` `:298-311`, `FloatPanel` `:726-731`), `DockTabGroupNode.Panels` is an `ObservableCollection` (`DockTabGroupNode.cs:15`) and the visual tab groups react during the mutation (`MGDockTabGroup.OnPanelsCollectionChanged` `:714-719`). A model-backed floating window therefore releases its content through the model before the host stops tracking it (`RedockPanel` `MGDockHost.cs:1725-1738`, `ClosePanel` `DockOperation.cs:873-909`); a standalone floating window (public constructor, `FloatingGroup` null, `MGFloatingDockWindow.cs:59-80`) does not: its group still holds the panel when `CloseFloatingWindow` stops tracking it (`MGDockHost.cs:1608-1612`), and nothing calls `Detach()` on its tab group.
- `MGListBox<T> : MGElement` (`MGListBox.cs:33`) keeps its whole structure in components bound by `AttachControlTemplateStructure` (`:1182-1250`), below which the items panel chain is made of content hosts; `MGChatBox : MGElement` and `MGChatBoxMessage : MGElement` (`MGChatBox.cs:16`, `:271`) keep theirs in components too. Their late additions (an item, a message) never reach a window, and the items of a directly attached list box are never announced at all.
- Only `MGContentHost.cs:61/99`, `MGElement.cs:335/589` and `XAML/Containers.cs:35` branch on the host type, the last three on `MGSingleContentHost` only; nothing instantiates the docking controls from XAML. `MGUI.Samples/Features/DockingDemo.cs` sets no `Name` on any panel content.
- The XAML editor's preview presenter is a public `MGContentPresenter` inside an `MGOverlayPanel` pane (`MGUI.Editor/XamlEditorView.cs:85-95`); `ReplaceRoot` removes the previous root's data bindings, then attaches the new root, then updates `PreviewRoot` (`XamlPreviewHost.cs:168-183`), so an attach that throws leaves the presenter on a half-announced root while `PreviewRoot` still points at the previous one. `XamlPreviewHostTests.cs:139-171` pins, as a deliberate tripwire, that the preview's names do not reach the editor window "because the dock group is not in the add chain".

## Decision

1. **Invariant.** Every element that holds other elements announces their arrival and their departure through the `MGContentHost` chain, so that a listener of the chain -- the name index of an `MGWindow` -- sees exactly the elements present in the tree. The mechanism stays `MGContentHost` (its events and its protected `InvokeContentAdded` / `InvokeContentRemoved`); no announcing mechanism is added to `MGElement`.
2. **The docking containers are content hosts.** `MGDockTabGroup`, `MGDockSplitContainer` and `MGDockAutoHideDrawer` derive from `MGContentHost`, and every `SetParent(this)` / `SetParent(null)` of a child is paired with `InvokeContentAdded` / `InvokeContentRemoved`. In `MGDockTabGroup.UpdateActiveContent` the removal is announced as soon as the field changes, unconditionally; only the `SetParent(null)` keeps the `Parent == this` guard, since `SetParent` never clears the previous holder's field and a floating window's group may already have taken the content. No `SetParent` call is added or removed: the editor's tests count `OnParentChanged` exactly.
3. **A floating window releases its content when the host stops tracking it.** `MGDockHost.CloseFloatingWindow` (both branches) and `OnFloatingWindowClosed` call `Detach()` on the window's tab group. For a model-backed window this only drops the visual's model subscriptions, the content having already been released by the model; for a standalone window it is the only release.
4. **Components are announced on both sides.** `MGContentHost` overrides `RemoveComponent` and announces the removal after it, mirroring `AddComponent`.
5. **Attaching an element announces its own components.** `InvokeContentAdded` / `InvokeContentRemoved` traverse `Element.TraverseVisualTree(true, true, false, false)` and skip `Element` itself (announced separately, as before). This supersedes the fourth context fact of ADR-0013: whether a templated control is the root or is wrapped no longer decides anything, a `ListBox` root whose item template carries a `Name` fails at attach exactly like a wrapped one. ADR-0013's seven decisions are unchanged.
6. **`MGListBox<T>`, `MGChatBox` and `MGChatBoxMessage` are content hosts.** They derive from `MGContentHost` (children stay in components; `GetChildren` is empty, `UpdateContentMeasurement` returns the base implementation, `UpdateContentLayout` does nothing), so their components are announced when bound and released when replaced, and the item and message chains below them relay to the window.
7. **The XAML editor keeps the previous preview when attaching the new root fails.** `XamlPreviewHost.ReplaceRoot` attaches the new root first; if the attach throws, the presenter is set back to the previous root and the exception propagates to `Reparse`, which reports it as a `DuplicateElementName` diagnostic; the previous root's data bindings are removed only after a successful attach. The preview's names enter the editor window's index as soon as the preview loads (author's decision of 2026-09-19).

## Consequences

- The reported failure disappears at its root: content that leaves a docked tab group, a split container, a drawer or a floating window is unindexed at that moment, and content that enters one is indexed at that moment, rebuild or not. A rebuild re-parents content whose previous holder has already announced its release, so the same instance is never offered twice, and a preview root replaced between two rebuilds is unindexed by the presenter's own `SetContent`.
- In the XAML editor, a document whose item template applies a `Name` to several elements is refused at attach and shown as a located `DuplicateElementName` diagnostic (ADR-0013 decision 6, "option A"), while the previous preview stays displayed; it used to preview silently. The tripwire test is rewritten as that positive case. Two panes of the editor, or the editor's chrome and the preview, can no longer carry the same element name: `Docs/editor-architecture.md`'s rule "a pane carries no `Name`" becomes a constraint, not a free choice.
- A `ListBox`-rooted document whose item template carries a `Name` now fails at attach like any wrapped one; the test that pinned the opposite is rewritten, and one editor selection test loses an incidental `Name` from its document.
- Components of any directly attached element (a previewed `MGWindow`'s chrome, template parts) are announced. Control template part names are cleared by `ControlTemplateLoader` (ADR-0013, last consequence) and no component of `MGUI.Core` carries an `MGElement.Name`, so no new index entry is expected; the full suite and the samples verify it, and a framework component found indexed twice is reported to the author rather than tolerated (ADR-0013 decision 1).
- `DockingDemo` and every host that builds unnamed panel content see no observable change beyond the announcements themselves.
- Deferred, not decided here: announcing components from `MGElement` itself so that every control with components participates without changing its base class (`MGGridColorPicker`, `MGColorPicker`, `MGRatingControl`, `MGTextBox`, ... carry no user-named content today); `MGXAMLDesigner`, which the XAML editor plan removes; a name scope per previewed document, refused by ADR-0013 and by the author; a tolerance of the index to a repeated announcement of one instance, refused: with the chain complete, a double announcement without an intervening release is an ordering defect to fix at its source.
