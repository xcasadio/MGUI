# ADR-0005: Per-element resolved value store for seven pilot properties

- **Status**: Accepted (2026-09-07, plan `Docs/Tasks/resolved-value-engine-tasks.md` approved by the author after four independent plan reviews)
- **Date**: 2026-09-07
- **Source**: this chantier: grouped questions of 2026-09-07 before executing task 4 of `Docs/Tasks/styling-theme-tasks.md`; program plan `Docs/Tasks/resolved-value-engine-tasks.md`

## Context

Facts verified at HEAD `c7ea9f5`:

- The framework already defines the value model (`MGUI.Core/UI/Styling/UIResolvedValue.cs`, `UIValueResolutionSource.cs`, `UIValuePrecedence.cs`, `UIInvalidationKind.cs`): eleven source kinds ordered DefaultValue 0 < Inherited 10 < Theme 20 < DynamicResource 30 < ImplicitStyle 40 < ExplicitStyle 50 < Template 60 < VisualState 70 < LocalBinding 80 < LocalValue 90 < Animation 100. In production only the `Template` and `Default` sources are ever constructed: the template path stamps `UIResolvedValue<T>` into `MGElement._AppliedTemplateDefaults`, a single-slot, string-keyed cache used solely by the theme-refresh guard of `MGControlTemplateContext.ApplyTemplateValue` (`MGControlTemplate.cs:97-120`).
- Every other write path is untagged and writes through plain setters: constructors (`MGElement.cs:2116-2127`), the ~125 pilot lambdas of `MGControlTemplateCatalog.cs`, twelve `OnThemeChanged` overrides and their helpers (unguarded, run BEFORE the template re-application in `MGElement.NotifyThemeChanged`), the XAML transfer `ApplyBaseSettings` (where a style setter and an explicit attribute are indistinguishable), `DataBinding.TrySetValue` and `UIResourceReferenceApplicator.Apply` (reflection `SetValue`, applied after the XAML literals so a dynamic resource wins over an attribute, the inverse of the declared precedence).
- Margin, Padding, MinHeight (`MGElement`) and BorderBrush, BorderThickness (single real implementation on `MGBorder`, every other declaration a facade, reachable through `MGElement.GetBorder()`) have one physical setter each. `BackgroundBrush` (`VisualStateFillBrush`) and the text foreground (`MGElement.DefaultTextForeground`, `MGTextBlock.Foreground`, both `VisualStateSetting<T>`) are mutable containers written three ways: object replacement, sub-field (`NormalValue`, `SelectedValue`, `DisabledValue`, `FocusedValue`, `FocusedColor`), `SetAll`; instances can be shared between elements and carry no owner reference. `MGTextBlock.ActualForeground` already resolves own value, inherited default and theme by hand.
- Tests build elements with `FormatterServices.GetUninitializedObject` (no field initialisers), reflect into `_AppliedTemplateDefaults` by name, and pin source text of the catalogue and of `MGControlTemplate.cs`.

## Decision

Taken by the author on 2026-09-07:

- Seven pilot properties: Margin, Padding, MinHeight, BorderBrush, BorderThickness, Background, Foreground, with sub-field (slot) tracking for the two containers.
- Explicit tagged setter overloads on the owning types, and explicit migration of every framework write site (constructors, template catalogue, theme callbacks, XAML transfer, bindings, dynamic resources); no ambient "current source" state.
- Style provenance (ImplicitStyle / ExplicitStyle) carried from the XAML parse model into the store now.
- Precedence enforced at write time: the effective CLR value is always the highest set source; accepted behaviour changes: a theme change no longer overwrites a locally set pilot value, and a dynamic resource update no longer overwrites a later local write.

Taken by the author on 2026-09-11 (before slice S7, XAML style provenance):

- A catalogue write that targets the control itself (its own property, the border its `GetBorder()` or public `BorderBrush`/`BorderThickness` facade expose, or the element its XAML DTO writes for the same property, such as the `OuterBorder` that the `PropertyGrid` and `TreeView` DTOs hand their nested `Border` DTO) is a theme default of that control and carries the `Theme` source (20); only writes that target a template part carry `Template` (60). Rationale: templates apply in the constructor, so today every XAML attribute and style setter is written afterwards and wins; tagging styles `ImplicitStyle`/`ExplicitStyle` (40/50) while the control's own defaults stayed `Template` (60) would have made styles inert on templated controls (`TextBox`, `ComboBox`, `Window`, `TabControl`, ...), which the samples contradict. Parts are never XAML style targets, so part defaults keep outranking styles as in WPF.
- `MGSeparator`'s construction-time margin is a `DefaultValue` (the public `Orientation` setter stays `LocalValue` for later changes), so a style margin can reach it.

Derived design (main session):

- Identity of a resolved value: (element owning the CLR property, `UIPilotProperty`, `UIValueSlot`). `Whole` for scalars and container replacement; `Normal`, `Selected`, `Disabled`, `Focused`, `FocusedColor` for container sub-fields. A composite's border resolves on its `MGBorder`.
- `UIResolvedPropertyStore`: allocated lazily per element, one entry per written (property, slot), each entry a compact precedence-sorted list of `UIResolvedValue<T>` (one per set source); read = highest set source; `Unset(source)` removes a contribution and falls back; equal precedence = last writer. Non-pilot properties: no field, no code, no cost.
- Tagged internal API per pilot (`SetPadding(value, source)`, `MGBorder.SetBorderBrush(...)`, `SetBackgroundSlot(slot, value, source)`, ...); the public setter delegates with `LocalValue`, constructors use `DefaultValue`; each call records, resolves the winner, and writes the CLR value and raises the existing notifications only when the effective value changes. Per-property invalidation kind: Measure | Arrange for Margin, Padding, MinHeight, BorderThickness; Draw for BorderBrush, Background, Foreground; the actual invalidation stays the existing setter's.
- Containers: tagged slot writes update both the container slot and the store; untagged sub-field writes are attributed as `LocalValue` to the element holding the container through its `PropertyChanged` (a private suppression flag mutes the subscription while a tagged write is in progress); replacing the container re-applies the winning slots; a shared instance is recorded by every holder (documented limit). Text foreground: pilot on `MGTextBlock.Foreground`, ancestor `DefaultTextForeground` as the `Inherited` source resolved at read time, theme as fallback.
- Composition of the `Whole` slot with the sub-slots (precised for S5, 2026-09-11): a `Whole` write at precedence P removes the sub-slot contributions posed at exactly P (last writer wins at equal precedence, which is how replacing the object discards earlier sub-field edits today), keeps the lower ones dormant and leaves the higher ones effective; whenever the effective container changes (by a write or by an unset), the element re-subscribes and re-applies onto the new container every sub-slot winner whose precedence is at least the effective container's, so a dormant contribution resurfaces when the stronger container is cleared (the tree view's selection visual relies on it: a `VisualState` container shadows the `Theme` transparent slots of the expander and clearing it restores them); a sub-slot write is physically applied only when it is its slot's winner and at least as strong as the effective container; while a sub-slot is dormant, the diagnostic read reports the container's own field value under the container's source.
- `_AppliedTemplateDefaults` and the `ApplyTemplateValue` guard stay in place (bypassed for part defaults after a structure rebuild since 2026-09-12, see below); the store is the source of truth for pilot properties.
- Framework writes made outside the base constructors are classified by intent, never left on the untagged public setter: a constructor writing its OWN pilots, or the pilots of its OWN template parts, before or while its own template applies is `DefaultValue` (its template must win; missing this on the context menu item's part margins made theme-defined margins inert, caught by the S3 verification); an owner configuring an already-templated child or part (the graph node's editing text box, for instance) is `LocalValue` (deliberate owner chrome that must beat the child's template and not follow the theme); a write recomputing chrome in reaction to a theme change (helpers called from `OnThemeChanged`) is `Theme`; an internal visual state (selection, pressed, hover) is `VisualState`; a write reacting to a public property set by the application or the XAML (`MGWindow.WindowStyle`, which must outrank the template that already wrote the same pilots in the window constructor) or made on behalf of the application is `LocalValue`, justified per site. Otherwise construction-time chrome would permanently outrank template and theme defaults, or an application-driven chrome change would silently lose to the template.
- Text pilot carriers (precised for S6, 2026-09-11): the text foreground pilot is carried by two CLR containers that the framework writes independently, `MGTextBlock.Foreground` and `MGElement.DefaultTextForeground` (the template catalogue writes a part's `DefaultTextForeground`, `MGPropertyGrid.ApplyTheme` writes both on the same text block), so the store keys them separately: `UIPilotProperty.Foreground` for the text block's own container and `UIPilotProperty.DefaultTextForeground` for every element's inherited-provider container; the enum therefore has eight keys for the seven pilot properties of this decision. Both containers follow the S5 composition rules (Whole plus `Normal`/`Selected`/`Disabled`/`Focused` sub-slots typed `Color?`, no `FocusedColor`). `MGTextBlock.ActualForeground` keeps its physical chain unchanged (own container for the current state, then the ancestor chain of `DefaultTextForeground`, then the theme fallback), since precedence is enforced at write time; `Inherited` (10) and the theme fallback are reported at read time by the diagnostic only. Raw theme text settings (`Window.TitleTextForeground`, `ContextMenuItem.ShortcutForeground`, `ListBox.TitleForeground`, `ListView.HeaderForeground`) are copied before being handed to an element, for the same rooting reason as the background containers.
- Construction-time theme background (precised on 2026-09-12, after the context menu of the Editor Compact sample kept its `Dark_Blue` background under `EditorCompact`): the `MGElement` constructor records the background it takes from the theme (`MGTheme.GetBackgroundBrush(ElementType)`) as a `DefaultValue` named `MGElement.ThemeBackgroundDefaultName`, and `NotifyThemeChanged` re-evaluates it against the incoming theme, before `OnThemeChanged` and the template refresh. The refresh is skipped once that contribution is no longer the base constructor's (any other `DefaultValue` background write, by a derived constructor or by an owner configuring the element, replaces it without the name; a `DefaultValue` sub-slot would be erased by the whole write under the composition rule above). It is also skipped when the incoming brush is empty and so is every sub-field of the recorded container that no source has written (`UIResolvedPropertyStore.IsWritten`), so that an element type no theme paints keeps its container, including a value kept after its last contribution was removed. Otherwise the refresh is a container swap and, like any other, ends such a kept value: the incoming theme's field shows instead. The value stays a `DefaultValue`: any stronger source keeps winning, and the refreshed default only resurfaces when that source is cleared. `MGWindow.WindowStyle` follows the same rule: the transparent sub-slots written by `None` are named `LocalValue` contributions that `Default` removes, restoring the local sub-slots they had replaced, before putting back a container from the current theme while the window background is still the constructor default (otherwise the container held before `None` is restored as a local value, as before). Without the refresh, a surface built before its scope's theme changed (context menus and windows, XAML or code-built, tooltips, separators, scroll viewers, borders) kept painting the theme of its construction, since no template or theme callback writes those backgrounds.
- Template structure rebuilt by a theme refresh (precised on 2026-09-12, after a combo box and a window built under `Dark_Blue` kept construction values on the parts of their `Dark.*` structures): `_AppliedTemplateDefaults` keys its records by name on the owner, not by target, so the record of a part default describes the part the rebuild replaced, and the guard compared it with the construction value of the new part. The application that follows the instantiation of a structure now carries `MGControlTemplateContext.IsStructureRebuilt`: a part default (`Template`) is applied without consulting its record, while a default of the control itself (`Theme`, `ApplyOwnerThemeDefault`) keeps the guard. This follows the owner/part split decided for S7: the untagged `ApplyOwnerThemeDefault` overload carries the owner's defaults that no store records (`ComboBox.DropdownArrowColor`, `TreeView.IndentSize`, the docking colours, ...), so a rebuild does not overwrite an application value. Before that application, `MGElement.ApplyControlTemplate` carries to the part of the same name the scalar pilot contributions (Margin, Padding, MinHeight, BorderBrush, BorderThickness) that the replaced part held on behalf of the owner: `LocalValue`, `ImplicitStyle`, `ExplicitStyle`, and the `Theme` contributions whose source the owner recorded, such as a window's border; their guard then compares the value the owner still holds, and the border thickness of `WindowStyle.None` survives. Containers are not carried. The catalogue's one-time initialisation of parts runs again on a rebuilt structure. Clearing the records wholesale on a rebuild was rejected: the owner's `Theme` defaults would lose their guard, and a real theme change would replace a retained `Theme` contribution that a local value outranks.
- Border pilots on composites: framework writes go through the inner border's tagged setters (`GetBorder().SetBorderBrush(value, source)`), never through the public facade, which stays the application's `LocalValue` entry point.
- Completeness is enforced by an architecture test scanning `MGUI.Core` for assignments to the pilot properties with a justified allow-list, so no framework write silently stays untagged.
- When the last contribution of a (property, slot) is removed, the entry is empty, the store reports `UIResolvedValue<T>.Unset`, the CLR value is kept and no notification fires (the behaviour of a dynamic resource that no longer resolves today).
- Accepted cost budget: a freshly constructed `MGElement` allocates one store and two entries (Margin, Padding), an `MGBorder` four, two more per element once Background and DefaultTextForeground are wired; a non-pilot write allocates nothing and never touches the store; pinned by tests through an internal entry counter. Measured after S2 (2026-09-08): the store, its 42-reference table and two entries with their two lists each amount to about twelve objects and roughly 700 bytes per plain element (about twenty objects for an `MGBorder`), paid once at construction, never per write or per mouse event. Since S5/S6 the table has 48 references (eight keys) and a plain element allocates four entries at construction (Margin, Padding, Background, DefaultTextForeground), an `MGBorder` six, an `MGTextBlock` five, plus one `PropertyChanged` subscription per held container.
- Rejected alternatives: a thread-ambient source scope pushed by the four entry points (fewer edits, but implicit and mis-tagging risk when theme and template writes nest); tracking the containers at object granularity only (misleading provenance, since XAML, bindings and dynamic resources write sub-fields); deferring styles to the style-refresh task.

## Consequences

- Precedence becomes observable and testable per property; the internal diagnostic read delivered by S9 (`MGElement.TryGetResolvedValueSource(UIPilotProperty, UIValueSlot, out UIValueResolutionSource)`, type-agnostic winner's source honouring the same read-time rules as `TryGetResolvedPilotValue<T>`, and `EnumerateResolvedContributions`, the raw store contents highest precedence first) answers where a value comes from for the pilots; the public, property-path based API on top of it, `UIToolingService.TryGetResolvedValueSource(MGElement, string, out UIValueResolutionSource)` with its covered list `UIToolingService.ResolvedValueSourcePropertyPaths` (pilot CLR paths and the XAML names that target them), was delivered by task 5 of the styling backlog on 2026-09-11.
- Bindings and dynamic resources (S8, 2026-09-11): `UIPilotPropertyResolver` maps a dotted target path rooted at an element (after the XAML `BindingPathMappings`) onto a (key, slot) pair, so `UIResourceReferenceApplicator.Apply` records a `{DynamicResource}` as `DynamicResource` (30) and a `{StaticResource}` as `LocalValue`, and `DataBinding` records every source-to-target write of a binding on a pilot as `LocalBinding` (80), the target-to-source direction staying untagged; a dynamic resource that no longer resolves gives its contribution up (`ClearPilotSource`) and the next source takes over. Non-pilot targets keep the reflection path. Consequence of the table kept as decided: an implicit or explicit style setter (40/50) on the same property outranks a `{DynamicResource}` attribute (30); no sample is in that case.
- The framework write sites become explicit about their source; new code writing a pilot property from a theme, template or binding path must use the tagged overload or be recorded as `LocalValue`.
- Behaviour changes accepted by the author: theme callbacks and dynamic resource updates no longer clobber local values on pilot properties. Corollary: once an application assigns `MGWindow.WindowStyle`, that window's Padding and BorderThickness are pinned at `LocalValue` and no longer follow theme changes (its background is not, see the construction-time theme background above). At XAML parse time a `Padding` declared on the window (attribute or style) supersedes that side effect: the `Window` DTO clears the `LocalValue` contribution left by `WindowStyle` before re-applying the XAML padding under its own provenance (S9), because the store resolves by precedence, not by write order. The clear is kind-scoped, not writer-scoped: it drops whatever `LocalValue` Padding contribution exists at that point of the parse, which today only the `WindowStyle` setter can have written.
- Cost: one lazily allocated store per element that receives a pilot write (constructors write Margin, Padding, Background and DefaultTextForeground, so most elements allocate a small store), a compact list per written slot; nothing for non-pilot properties.
- Known limits: shared container instances (every holder records the same untagged write and, since S5, the holder's `PropertyChanged` subscription keeps each holder alive as long as the shared container lives, so the framework never hands a long-lived shared container such as a raw theme instance or a control-level template brush to `SetBackground` without `Copy()`, and an application-owned container shared between elements stays the application's responsibility), `Animation` and most `VisualState` levels unpopulated by the framework, `_AppliedTemplateDefaults` kept in parallel until a later task retires it (records keyed by name on the owner, not by target: a rebuilt structure bypasses the records of part defaults and carries only the owner's scalar pilot contributions, so an application value held by a container or a non-pilot property of a replaced part is lost, and a pilot attribute that a XAML template declares on a part, recorded as `LocalValue`, is carried like an application value).
- Observed while delivering S5 (2026-09-11), outside this decision's scope: a real theme change re-creates the template structure of `MGTreeView` and leaves its items attached to the discarded items panel, so the theme notification never reaches them; the defect predates S5 (reproduced on `8efa4bb`) and belongs to the template-structure refresh work tracked separately. Fixed on 2026-09-12: `MGTreeView.AttachControlTemplateStructure` moves the root items from the replaced panel to the new one, as `MGListBox` and `MGTabControl` already did; `MGListView` still loses its rows and columns in the same case.
